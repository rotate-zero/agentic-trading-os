# Confirmed Decisions

**Extracted from:** `../architecture/system-design.md` §9 (original numbering preserved for continuity with any existing references).
**Companion documents:** [`../architecture/system-design.md`](../architecture/system-design.md) (how it's built), [`../architecture/trading-intelligence-architecture.md`](../architecture/trading-intelligence-architecture.md) (how it thinks), [`future-ideas.md`](./future-ideas.md) (deferred, not rejected), [`../roadmap/phase-roadmap.md`](../roadmap/phase-roadmap.md) (when things ship).

This is the running log of settled architecture decisions — the "why did we choose X" record, kept in one place instead of scattered as inline asides across growing documents. **New confirmed decisions get appended here, numbered sequentially, as part of the same change that makes them** — not batched up and written after the fact.

1. **Broker order of implementation — REVISED.** Originally Alpaca first, then IBKR (simpler auth). Revised: **IBKR only, for now.** Alpaca requires a US-eligible account and isn't directly open to Bangladesh-resident account holders — this isn't a technical preference, it's an account-opening constraint, so there's no "try Alpaca first" path available. Not building an `AlpacaAdapter` stub for later — per `future-ideas.md`'s own discipline, that's speculative until there's an actual account to connect it to. Revisit if that constraint changes. (`../roadmap/phase-roadmap.md`, Phase 3)
2. **Candle storage** — plain PostgreSQL with native monthly partitioning for v1. TimescaleDB is deferred, revisited only once multi-timeframe backtesting at scale is a real, not hypothetical, requirement — since it's an additive extension, deferring costs nothing later. (`../architecture/system-design.md` §6.1, §4.13)
3. **Scanner cadence** — variable, config-driven schedule keyed to session windows (tight at open/close, sparse midday) rather than a fixed interval. (`../architecture/system-design.md` §4.7)
4. **Redis** — skipped for v1. Revisit if/when agents move to separate processes. (`../architecture/system-design.md` §6)
5. **Context Engine is a composed aggregator**, not a monolithic module — one provider per context question, so growth (news, OPEX, breadth, sentiment) means adding a provider, not editing a growing conditional block. (`../architecture/trading-intelligence-architecture.md` §5)
6. **Governor's decision schema is widened now, implemented narrow.** `GovernorDecision` supports `approved | approved_reduced | delayed | watch_only | rejected`; v1 rule logic only ever produces `approved`/`rejected`. A schema change now avoids a breaking change to every downstream consumer later. (`../architecture/trading-intelligence-architecture.md` §12)
7. **World View is a read-only composite facade**, not a shared mutable world model. Assembles Market State + Portfolio State + Context + Performance Intelligence for consumers that want the whole picture at once (debug tooling, a future LLM reasoning layer). No write path, no state of its own — single-writer-per-domain stays intact. (`../architecture/trading-intelligence-architecture.md` §15)
8. **Event data contracts are formalized before Phase 1 code**, not discovered along the way. (`../architecture/system-design.md` §10)
9. **Event Bus dispatch is two-lane, not multi-tier priority.** Execution-critical events (`OrderFilled`, `PlanRejected`, `GovernorDecision`, `OrderApproved`) get an isolated dispatch lane so they're never delayed behind market-data volume; everything else shares one normal lane. A general N-tier priority framework was considered and rejected as complexity without demonstrated need at this scale (single process, ~100-symbol universe, Scanner-narrowed to a handful). (`../architecture/system-design.md` §4.4)
10. **Stateful engines that need periodic-but-not-constant recompute (Market State Engine, Position Monitor) use a shared `DebounceScheduler` utility** — event-triggered, with a minimum interval (don't recompute more than once per N seconds) and a maximum interval (recompute at least once every M seconds even if nothing changed). Same pattern already used for Scanner cadence and Strategy triggers, implemented once and reused rather than each module inventing its own timer logic. Feature Engine, Governor, and Execution Engine do **not** use this — they react to every event with no debounce, since staleness there is either wrong indicator values or a safety issue. (`../architecture/system-design.md` §8, `core/debounce_scheduler.py`)
11. **`docs/` is the authoritative location for all architecture and design documentation**, organized into `architecture/`, `decisions/`, `diagrams/`, `roadmap/`, and `api/` subfolders. Implementation code stays separate from documentation. Any future architecture change updates the relevant document(s) here as part of the same change that makes the change — not a follow-up task. (`../README.md`)
12. **Partition-boundary literals in migrations must carry an explicit UTC offset (`+00`), never a bare date.** Found via a real local-Postgres run: a bare `'2026-07-01'` literal in `CREATE TABLE ... PARTITION OF` gets interpreted using the DB session's local `TimeZone` setting at migration-run time, not UTC — so the same migration produces a different physical partition boundary depending on who/where runs it (observed: a session with `TimeZone=Asia/Dhaka` produced a boundary six hours off from intended UTC midnight). Fixed in `0001_initial_symbols_and_candles.py` by writing boundaries as `'2026-07-01 00:00:00+00'`. Applies to every future partition-seeding migration, not just this one.
13. **Use `ib_async`, not `ib_insync`, for the IBKR adapter.** `ib_insync`'s original author passed away in 2024 and the library is unmaintained. `ib_async` (github.com/ib-api-reloaded/ib_async) is the community-maintained, API-compatible successor — verified by installing it and introspecting real method signatures (`connectAsync`, `reqHistoricalDataAsync`, `reqMktData`, `placeOrder`, `cancelOrder`, `positions`) rather than trusting training-data memory of the older library. `system-design.md` §6's tech stack table is corrected to match.
14. **IBKR 2FA: switch to IB Key, not SMS; Gateway set to auto-restart, not auto-logoff.** Verified against IBKR's own automation tool (IBC)'s documentation: unattended login with *zero* human interaction isn't possible for any 2FA method — IBC can fill in username/password, but the 2FA step still needs either a typed code or a tap in the IBKR Mobile app. Switching from SMS to IB Key (push notification + biometric/passcode tap) replaces "type a code into a script" with "tap approve on your phone," and combining that with Gateway's auto-restart setting (vs. auto-logoff) reduces how often that tap is needed to roughly once a week instead of once a day. This is a real reduction in friction, not a full bypass — don't oversell it as "headless" in any documentation or code comments referencing this.
15. **`BrokerAdapter`'s `Tick` type includes `symbol`, distinct from the Event Bus's `PriceUpdated` payload (which omits it).** Found while implementing `IBKRAdapter`: `on_tick(callback: Callable[[Tick], None])` (§4.1) passes only a `Tick` to the callback, with no separate symbol argument — but a single adapter instance serves many subscribed symbols, so `Tick` itself has to carry `symbol` for the callback to be usable. `PriceUpdated` (the Event Bus payload) deliberately omits `symbol` because the `EventEnvelope` carries it instead (§10.1) — reusing it directly for `Tick` would have silently dropped symbol identification. `app/broker_adapters/base.py`'s `Tick` is therefore its own small model, not a reuse of `PriceUpdated`; the ingest bridge is what converts one into the other when publishing onto the bus.
16. **Tick-to-candle bucketing lives above the adapter, not inside it.** `BrokerAdapter` (§4.1) has no `on_candle` — only `on_tick`. Building 1-minute candles from a raw tick stream is Market Data Engine's job (§4.2), not a broker-specific concern; putting it inside `IBKRAdapter` would mean every future adapter (a real Alpaca one, a replay adapter, etc.) has to reimplement the same bucketing logic. For Phase 3, `app/services/ibkr_ingest.py` does minimal, explicitly-throwaway bucketing as a stand-in for the real Phase 4 Market Data Engine — it gets replaced wholesale, not extended, when that engine is built.
17. **`is_connected()` is part of the `BrokerAdapter` ABC itself, not an IBKR-specific extension.** Every consumer of a `BrokerAdapter` — routes, health checks, future Market Data Engine — needs to ask "are you connected" regardless of which broker is behind the adapter. Originally added only to `IBKRAdapter`; promoted into the abstract interface once a second route (`GET /market/candles`) needed the same check, rather than leaving it as an untyped, adapter-specific method that happened to work by duck typing.
18. **One shared adapter registry (`app/services/broker_registry.py`), not per-route globals.** `app/api/routes/broker.py` (connect/disconnect) and `app/api/routes/market.py` (candle backfill) both need to know which adapter is currently active. A single global slot, not a dict keyed by broker — Phase 3 is "one adapter, one symbol at a time" by design (the Phase 3 roadmap exit criterion), so multi-broker support isn't a concern yet, and adding that flexibility now would be exactly the kind of speculative build this project avoids.

19. **Participation added as a 7th Market State dimension.** Computed from a new Feature Engine observable (signed volume / uptick-downtick imbalance) and tracked with the same duration/strength/confidence/previous shape as the other six dimensions. Deliberately scoped to the *observable* half of market psychology only — distinguishing panic from short-covering from options-hedging flow needs data (short interest, options gamma) this system has no confirmed source for yet, so that causal-inference layer stays in `future-ideas.md` (#13) rather than being approximated from data that can't support the distinction. (`../architecture/trading-intelligence-architecture.md` §4, §7)
20. **Context Engine v1 provider list expanded: `SectorCorrelationProvider` and `NewsFlagProvider`.** Sector/ETF correlation was a real gap — Decision Engine already checks correlation across a trader's own open positions but nothing read symbol-vs-sector correlation, and a breakout against a falling sector is a different trade than one moving with it. News flag is deliberately a headline-exists boolean/count, not NLP sentiment scoring — full sentiment stays deferred (`future-ideas.md` #13) until there's a way to validate it against real outcomes. (`../architecture/trading-intelligence-architecture.md` §5)
21. **`ContextProvider` is explicitly generalized to arbitrary refresh cadence, not just tick/seconds-scale.** Nothing in the interface ever assumed fast refresh — this makes it explicit, using the same event-triggered pattern already used elsewhere (decision #10) with a much sparser trigger (`EarningsReleased` instead of a volatility threshold crossing). This is what keeps a path open to slower-moving context — fundamentals, macro — for a possible future move into swing/position-holding-period trading, without committing to building any of it now; see `future-ideas.md` #9–#12 for the specific providers this unlocks. No new module, no new abstraction — a documentation change that makes an existing capability explicit and gives it somewhere to grow later. (`../architecture/trading-intelligence-architecture.md` §5)

22. **Manual trading reuses the existing pipeline via a single `plan(TradeRequest) -> TradePlan` interface, gated by a system-wide Execution Mode — not a parallel pipeline.** Manual entries join at Trade Planning Engine, not at Strategy/Opportunity/Decision — there's nothing for those to arbitrate when a human already picked the trade. Both AI- and manual-origin trades construct a `TradeRequest{origin: auto|manual, ...}`; Trade Planning Engine branches internally on origin but keeps one public method, rather than a second method (`plan_manual()`, proposed and rejected) that would need a new entry point per future origin. Governor and Execution Engine require zero new logic — they only ever see the resulting `TradePlan`, never its origin. A single `ExecutionMode` (`auto`/`manual`, account-level, one value system-wide) changes only where Execution Engine calls `BrokerAdapter.place_order`: in manual mode, an approved plan holds in a new Approval Queue for explicit human accept/ignore instead of firing immediately. A dedicated `ManualPlanBuilder` component, also initially proposed, was rejected as redundant once the Input Layer (#23) already owns translating raw input into `TradeRequest`. (`../architecture/trading-intelligence-architecture.md` §18)
23. **Manual trade input is abstracted behind a device-agnostic Input Layer, not built for a specific controller.** Physical input (gamepad, keyboard, Stream Deck, voice) is normalized in the frontend into one shared `InputCommand{command, symbol, order_type, size}` shape, sent over the existing WebSocket Gateway — no new transport, and the trading system never knows which device fired a command, mirroring `BrokerAdapter`'s broker-independence (`system-design.md` §4.1). Quantity is a `size` parameter, not encoded in the command name — a single `SELL` with a `size` parameter scales to any future sizing option without a new enum value, where `SELL_HALF`/`SELL_THIRD` would not. This iteration's command set is entry-only — `BUY`, `SELL` (opens a short, symmetric to `BUY`), `PROPOSE_LONG`, `PROPOSE_SHORT`, `CANCEL_PENDING` (Approval Queue only). Position-management commands (`MOVE_STOP`, closing/reducing an existing position) are explicitly deferred alongside Position Monitor/Trade Management integration for manual-origin positions — see `future-ideas.md` #14. *(Command vocabulary superseded in v1.7 — see #25.)* (`../architecture/trading-intelligence-architecture.md` §18.6)
24. **Hotkey targeting resolves against an explicit, per-tab `FocusedTile`, changed only by deliberate user action — never a background/system event.** Phase 1's multi-tab, 8×8-grid workspace had no "which symbol is currently active" concept; one had to be added specifically because a hotkey needs exactly one unambiguous target. `FocusedTile` is tracked per tab, set only by clicking a tile, and deliberately never moved by an Opportunity, alert, or approaching stop firing in the background — the Input Layer only reads it (same relationship §15's World View has to state it doesn't own), never writes it. With no focus set, symbol-targeted commands are refused outright rather than defaulting to an arbitrary tile. This is a separate concept from the Approval Queue's cursor (which pending plan `ManualConfirmOrder`/`CANCEL_PENDING` act on) — conflating the two would let a chart click accidentally change which trade is about to be confirmed. An idea in the same spirit — letting the system itself redirect focus toward whatever's most urgent — was considered and deferred specifically because it conflicts with this rule; see `future-ideas.md` #15. *(Renamed `TradeTarget` in v1.7 — see #27.)* (`../architecture/trading-intelligence-architecture.md` §18.6, §18.10)
25. **A single `LONG`/`SHORT` action per direction replaces the `BUY`/`SELL`/`PROPOSE_LONG`/`PROPOSE_SHORT` split — the branch moves from "which command was pressed" to "was a size given."** The four-command split encoded an execution decision (fire now vs. review first) into the hotkey itself, duplicating what Governor + `ExecutionMode` already decide, and required `SELL` to carry a footnoted meaning ("opens a short, not a close") to avoid colliding with a future exit verb. Collapsing to one action per direction removes both: `manual_size`'s presence or absence on the `TradeRequest` (decision #22) is what used to be the command choice. One exception preserved on purpose — an unsized request always lands in the Approval Queue for review regardless of `ExecutionMode`, so an algorithmically-sized idea nobody has seen can never fire unreviewed just because the account happens to be in Auto mode. (`../architecture/trading-intelligence-architecture.md` §18.5, §18.6)
26. **Hotkey actions are modeled generically: Action Categories route dispatch, Safety Levels gate commitment, Hotkey Context suppresses input during text entry or an open modal, and bindings map action-to-device rather than button-to-command.** None of these add a new component — they reshape the same amount of code the Input Layer (#23) already needed. Action Category (Trading/Queue/Navigation/UI/Emergency) determines whether an action ever reaches the backend at all — Navigation and UI actions never construct a `TradeRequest`, which is what "the Input Layer knows nothing about trading logic" means concretely. Safety Level (0–3, only 0–1 populated today) replaces a hardcoded arm-then-fire rule with a per-action declaration, leaving room for higher-friction levels a future Emergency action will need without another schema change. Hotkey Context is a real gap this closes — nothing previously stopped a bound action from firing while a text field had focus or a modal was open. Binding-keyed-by-action (not button) means multiple devices can bind the same action simultaneously, which a single button-keyed table couldn't express. (`../architecture/trading-intelligence-architecture.md` §18.10)
27. **`FocusedTile` renamed `TradeTarget`; explicit non-triggers documented.** Same concept as decision #24, renamed because "focus" invites confusion with DOM/keyboard focus, which this state is explicitly not tied to. Non-triggers made explicit in the doc rather than left implicit: not hover, not keyboard tab-order, not mouse position — only a deliberate tile click. (`../architecture/trading-intelligence-architecture.md` §18.6)
28. **Split `BrokerAdapter` into `MarketDataProvider` (base) + `BrokerAdapter(MarketDataProvider)` (adds execution), so pure market-data vendors don't need a broker interface.** IBKR account access is taking longer than expected — a passport renewal added roughly 20 more days on top of the original wait — so Polygon.io API access was obtained in parallel to keep live-data momentum going; this doesn't replace IBKR, which remains the target for execution (Phase 6) regardless of which data vendor is used meanwhile. Before this split, a data-only adapter would have had to implement `place_order`/`cancel_order`/`get_positions` and raise `NotImplementedError` from all three — but for `IBKRAdapter` that error means "not wired up yet, but could be" (a real broker sits behind it, per decision #6's "widen now, implement narrow" pattern), while for a pure data vendor it would mean "can never work." Conflating those two meanings was dishonest interface design. `MarketDataProvider` now holds exactly what a data-only vendor can honestly implement (connect, subscribe, get_historical, on_tick); `BrokerAdapter` extends it with the three execution-only methods. `IBKRAdapter` is unchanged behaviorally — it already implemented everything, now split cleanly across two classes via inheritance. No concrete data-only adapter (e.g. a `PolygonAdapter`) is built yet — see `future-ideas.md` #17 for the vendor evaluation itself. (`../architecture/system-design.md` §4.1)
29. **`ib_async` pinned to `>=2.1,<3.0`, not `<2.0`.** Found via a real failure on Python 3.14: `ib_async<2.0` depends on `eventkit`, which calls `asyncio.get_event_loop()` unconditionally at import time — harmless on Python ≤3.13, but Python 3.14 removed `get_event_loop()`'s implicit loop creation (raises `RuntimeError: There is no current event loop` instead), so merely importing `ibkr_adapter.py` crashed both `pytest` collection and the live server on startup. `ib_async>=2.1.0` depends on `aeventkit` instead — a maintained fork (renamed only because the original `eventkit` PyPI listing is locked behind an inactive account, not a different project) that removed the eager top-level call; confirmed by reading its actual installed source, not assumed from a changelog entry. All method signatures this project depends on (`connectAsync`, `reqHistoricalDataAsync`, `reqMktData`, `placeOrder`, `cancelOrder`, `positions`, `qualifyContractsAsync`) re-verified identical across the version bump — one new optional parameter on `qualifyContractsAsync` (`returnAll`), nothing that affects how this codebase calls it. The original `<2.0` ceiling was set defensively in decision #13 without anticipating a major-version fix would be needed; this corrects it now that Python 3.14 usage has surfaced the gap.
30. **`PolygonAdapter` built around free-tier constraints, not against an assumed real-time feed.** Verified before writing any code: Polygon.io's free/Basic tier gives 15-minute-delayed data, only 5 REST calls/minute, and **no WebSocket access at all** — real-time streaming simply isn't offered at this tier, confirmed across multiple current sources, not assumed. This rules out mirroring `IBKRAdapter`'s push-based `on_tick` design. Instead: a shared `app/core/rate_limiter.py` token bucket (5 calls/60s) gates every REST call the adapter makes — both polling and `get_historical()` backfill draw from the same budget, since Polygon enforces the limit per API key, not per endpoint. `on_tick()` is backed by polling `get_aggs` (confirmed free-tier-available, unlike `get_snapshot`/`get_last_trade`, which have less certain entitlement at this tier) once per `POLYGON_POLL_INTERVAL_SECONDS` (default 60s, matching the underlying 1-minute bar granularity — polling faster would just re-fetch the same bar and waste budget). Each `Tick`'s `exchange_ts` carries the bar's actual (delayed) timestamp from Polygon, not "now" — the delay is reflected honestly in the data itself, not hidden. `get_aggs` returning an empty list for a bad ticker (rather than raising) is the same "silently succeeds" trap `qualifyContractsAsync` had (decision #16's sibling finding) — checked explicitly here too, raising `SymbolNotFoundError`. Auto-connects on app startup if `POLYGON_API_KEY` is set (soft-fail — a missing key or connect error must not crash the app over an optional data source), unlike `IBKRAdapter`, which stays manual-connect-only because it depends on an external Gateway app being already logged in.
31. **`IBKRIngestBridge` renamed `TickIngestBridge`, retyped against `MarketDataProvider`.** Its bucketing logic never actually depended on IBKR — it only ever called `provider.on_tick()`, which is defined on `MarketDataProvider`, not `BrokerAdapter` specifically (decision #28 already put it there). Once `PolygonAdapter` needed the exact same tick-to-candle bucketing, keeping the IBKR-specific name and type would have meant either duplicating the logic or the class lying about what it does. Works correctly for both: IBKR's genuine multi-tick-per-minute stream buckets normally; Polygon's one-tick-per-new-bar polling just means each bucket ends up holding exactly one tick — an honest reflection of that tier's real granularity, not a bug.

**Deferred, not rejected** — Knowledge Engine, Attention Engine, uncertainty propagation across the pipeline, the full write-everywhere World Model, Replay Engine, Simulation Mode, a quarterly-tier `FundamentalsProvider`, an Expectation/Surprise provider, fundamentals-informed sizing, a macro slow-tier provider, causal psychology / market-participant inference, Position Monitor/Trade Management integration for manually-initiated positions, an auto-focus/attention-directing hotkey target, and Emergency actions (`PANIC`/flatten/cancel-all) all live in [`future-ideas.md`](./future-ideas.md) with the reasoning for why each is parked, and what would trigger revisiting it.

32. **`FinnhubAdapter` built for genuine real-time streaming; historical stock candles explicitly not supported.** Verified before writing code: Finnhub's free tier gives real, independently-confirmed real-time WebSocket streaming (an April 2026 third-party latency test found ~150ms, rate limit not hit), unlike Polygon's 15-min-delayed free tier — but `/stock/candle` (historical OHLCV) was moved behind a paywall and returns a real 403 on free keys (confirmed via an actual GitHub issue from a user hitting exactly that, not assumed from older tutorials predating the change). `finnhub-python` ships no WebSocket client at all (confirmed by inspecting the installed package) — the WS layer is built directly on `websockets` (already a dependency), following Finnhub's documented protocol (`wss://ws.finnhub.io?token=...`, `{"type":"subscribe","symbol":...}`, trade/ping message types). `get_historical()` raises the new `HistoricalDataUnavailableError` rather than silently failing or faking data — same honesty principle as `BrokerAdapter.place_order()` raising `NotImplementedError` for a provider with no execution capability (decision #28), just for a capability gap instead of a not-yet-wired one. Verified against a real local WebSocket server mimicking Finnhub's exact protocol (this sandbox can't reach the real `ws.finnhub.io` — not in its network allowlist), since that's meaningfully stronger than mocking the message handler in isolation.
33. **`broker_registry` split into two independent named roles — `streaming` and `historical` — replacing the original single-slot design.** The trigger for this (documented as hypothetical when the single-slot design was built) has now actually fired: Finnhub (streaming-only, real-time) and Polygon (historical-capable, streaming-capable-but-delayed) both need to be connected at once, each doing the job it's actually good at. Fixed priority decided once at startup (`app/main.py`), not dynamic runtime negotiation: Finnhub claims streaming first if configured; Polygon always claims historical, and only also claims streaming as a fallback if Finnhub isn't configured. A single provider can hold both roles (`IBKRAdapter`, once connected, takes over both — manually connecting it is a deliberate action, so it's allowed to override automatic startup ordering). `broker_registry.take_over_streaming()` centralizes the one genuinely tricky part: safely retiring whatever was previously streaming without disconnecting it if it's still needed for the historical role (e.g. Polygon serving both roles as fallback, then Finnhub connects — Polygon must stay connected for backfill, only its streaming "ownership" changes). Unit-tested directly (`tests/test_broker_registry.py`), not just exercised incidentally through route tests.
34. **`main.py`'s auto-connect calls the same shared `connect_polygon()`/`connect_finnhub()` functions the manual `/market-data/connect` and `/finnhub/connect` routes use, rather than constructing adapters inline.** Found via an actual startup test against a running server, not caught by unit tests: an earlier version had `main.py` construct `PolygonAdapter()`/`FinnhubAdapter()` directly and register them into `broker_registry`, which auto-connected successfully (visible in the startup logs) but left `market_data.py`/`finnhub_data.py`'s own module-level `_provider` references still `None` — meaning `GET /market-data/status`, `POST /finnhub/subscribe`, etc. were silently useless after a successful auto-connect, reporting `not connected` for a provider that very much was. Unit tests didn't catch this because they call routes directly, bypassing `main.py`'s lifespan entirely — this needed an actual `uvicorn` process to surface. Fixed by extracting one shared connect function per provider that both the route and the lifespan call, so there's exactly one place "how to connect X" is implemented, and both callers stay in sync by construction rather than by convention.
35. **Frontend mock-swap resumed and completed for `candles.ts`; a new generic `POST /market/subscribe` route added to support it.** The paused plan (from before the IBKR/Polygon/Finnhub detour) is unchanged: `chartObjects.ts` and `opportunities.ts` stay mocked, correctly, per their own file comments (Phase 4/5 producers don't exist yet) — only `candles.ts` was ever in scope. New pieces: `frontend/src/config.ts` (backend URL config), `services/websocket-client.ts` (one shared multiplexed WS connection, reference-counted channel subscriptions, reconnect with backoff — matches system-design.md §4.12's design), `services/api-client.ts` (REST + the one real shape seam: `Candle.time` is unix seconds, backend's `candle_ts` is an ISO string), `hooks/useLiveCandles.ts` and `hooks/useLatestPrices.ts`. `POST /market/subscribe` is new (`app/api/routes/market.py`) — provider-agnostic like `GET /market/candles` already was, so the frontend calls one route regardless of whether Finnhub, Polygon, or IBKR is actually connected, rather than needing to know which. Verified: full TypeScript build (`tsc -b` + `vite build`) succeeds; CORS and error-response shapes checked against a real running backend, not assumed. Two pre-existing, unrelated bugs found and left alone rather than silently fixed as a side effect: `GridPresetPicker.tsx` references a `GRID_PRESETS` export and `preset`/`setPreset` context fields that don't exist anywhere in the codebase — it's also not imported by anything, so it's dead code, not something blocking this or any other build via Vite's actual bundler (only `tsc -b`'s full-project check catches it). Flagged for you to decide whether to fix or delete; out of scope to touch as part of a data-source swap.

36. **`generateMockOverlays` (`mocks/chartObjects.ts`) needed an empty-candles guard, since `useLiveCandles` legitimately starts empty.** Found via a real browser crash on first load, not caught by the TypeScript build (`candles[Math.floor(candles.length * 0.7)].time` with `candles = []` is a runtime `undefined` read, not a type error). The old `generateMockCandles` always returned a full synchronous array — there was never an empty-array case for `generateMockOverlays` to handle before decision #35's swap. Audited `resampleCandles`, `sma`/`ema` (`utils/indicators.ts`), and `ChartWidget.tsx`'s data-setting effects for the same class of bug — all loop/map-based, all degrade to empty output on empty input without crashing. This was the one unguarded direct array index in the whole chain.
37. **`UnhandledExceptionMiddleware` (`app/core/error_handling.py`) added as a plain ASGI middleware, NOT `@app.exception_handler(Exception)` — the two are not interchangeable.** Found via a real browser bug report: `/market/candles` showed a "CORS policy" error while `/market/subscribe` worked fine, both hit at the same time from the same origin — an asymmetry that only makes sense if `/market/candles` was throwing something uncaught (confirmed: the first attempt at a fix used `@app.exception_handler(Exception)`, which *looked* correct and even appeared in `app.exception_handlers`, but a test proving CORS headers were actually present on the resulting response failed — not skipped, actually run and actually failed, twice, before the real mechanism was found by reading Starlette 0.46.2's own source). The root cause: `Starlette.build_middleware_stack()` routes any handler registered for the bare `Exception` class to `ServerErrorMiddleware` specifically, which is unconditionally the *outermost* layer — always wrapping `CORSMiddleware`, never wrapped by it. A response built by that handler is sent via the raw ASGI `send`, bypassing `CORSMiddleware`'s header injection entirely, confirmed by reading `ServerErrorMiddleware.__call__`'s actual source rather than assumed. This is true on a real production `uvicorn` server exactly as much as in a test — not a testing artifact. Fixed with a plain ASGI middleware class instead, registered via `app.add_middleware()` *before* `CORSMiddleware` is added — Starlette's `add_middleware()` prepends, so call-order is the reverse of wrap-order, meaning `CORSMiddleware` ends up wrapping `UnhandledExceptionMiddleware` only with this specific ordering. Reversing it silently breaks the fix again with no error at registration time — this ordering is load-bearing and non-obvious, which is exactly why it's written down here instead of left implicit in the code. Verified: a test asserting the actual `access-control-allow-origin` header is present on a genuinely-thrown, genuinely-uncaught exception's response — not just that a JSON body comes back — against a real running `uvicorn` process as a regression check on top of the `TestClient`-based test.

42. **Chart zoom-reset bug fixed; candle-close latency bug fixed; volume bars made fully customizable; 4h/1d timeframes added; multi-monitor pop-out built.** Five items delivered together; grouped here because they were reported and worked through in one session, not because they're one change.

    **Zoom reset on every live candle (`ChartWidget.tsx`), root-caused rather than patched around.** The data effect was calling `setData()` *and* unconditionally re-running `setVisibleLogicalRange()`/`fitContent()` on every single run — including a live candle refresh, which silently re-pinned the view to the configured candle-count window every time, overriding any zoom/pan set manually. Root cause was that re-pin call, not `setData()` itself (`setData()` alone does not reset zoom). Fix: a new `diffCandles()` distinguishes a genuine reset (symbol/timeframe switch, or the candle-count stepper changing) from a live update (the last bar refreshing in place, or exactly one new bar appended — the only two shapes `useLiveCandles`' `[...prev, candle]` append plus `resampleCandles`' deterministic index-based bucketing can ever produce for the array `ChartWidget` receives). Only a genuine reset still calls `setData()` + re-pin; a live update instead calls `series.update()`, which Lightweight Charts never uses to reset the visible range — and which the library auto-scrolls to reveal *only* when the person is already viewing the live edge, i.e. exactly "fixed zoom, oldest candle pushed off the left when there's no room" as reported, with no special-cased scroll logic needed on this app's side at all. `update()` is also materially cheaper than a full `setData()` re-render on every tick, which matters across however many sub-windows are live at once, though that wasn't the reported problem.

43. **The `candles`/`symbols` tables (scaffolded Phase 2, unused since) now have a writer and a reader — self-recorded intraday history closes the gap decision #39 first flagged, without waiting on a paid data plan.** Reported symptom: with the market open and Finnhub streaming live, a sub-window showed candles only from the moment it connected forward — reconnect, refresh, or open a second sub-window on an already-tracked symbol, and there was nothing before the first live bar, even though this app had already seen and closed earlier candles for that exact symbol in the same run.

    **Root cause wasn't a bug to patch — it was a documented, unbuilt piece of the architecture.** `system-design.md` §4.2 (Market Data Engine) has said "Persist candles/ticks to PostgreSQL via a write-behind recorder (non-blocking)" since it was written; Phase 2 built the `candles`/`symbols` schema and migration for exactly this, and the migration's own TODO said outright: "automate future-partition creation... before this becomes a real operational gap — i.e. before Market Data Engine is actually writing candles." Nothing had ever subscribed to `CandleClosed` to actually write to it. This entry is that piece — pulled forward from the full Phase 4 Market Data Engine (`ConnectionManager` → `Normalizer` → `StateCache` → `Publisher` + `HistoricalWriter` as independent async tasks) into the current Phase 3 pipeline, not a reimplementation of it: `CandleRecorder` (`app/services/candle_recorder.py`) is just the `HistoricalWriter` half, wired directly onto the existing `EventBus` rather than a formal internal queue architecture that doesn't exist yet.

    **New pieces:**
    - `CandleRecorder` subscribes to `CANDLE_CLOSED` and persists every closed 1m candle — TickIngestBridge's fixed bucket size is the only granularity ever recorded, matching the frontend's own "always fetch 1m, resample client-side into 5m/15m/1h/4h/1d" design (decision #35, `resample.ts`) — there's no reason to store anything coarser separately. Non-blocking by construction, not just in name: `EventBus._consume()` `await`s `asyncio.gather()` over every handler for an event before pulling the next one off its queue (`bus.py`), so a slow synchronous DB write done *inside* the subscriber callback would block live price fan-out for every other subscriber on the same lane — the opposite of "non-blocking." The subscriber callback here only pushes onto an in-memory `asyncio.Queue` (no I/O) and returns; a separate background task drains it and performs the actual write via `asyncio.to_thread` (the DB engine is synchronous by design per `app/db/session.py` — same `to_thread` pattern `PolygonAdapter` already uses for its own sync REST calls). `TickIngestBridge`'s own accepted-race note (decision #42) is reused here too: a genuine duplicate `CandleClosed` for the same minute is rare and already accepted, so writes use `ON CONFLICT DO NOTHING`, not a competing `DO UPDATE`.
    - `app/db/partitions.py` — `ensure_month_partition()`, called before every write, closes that exact migration TODO: `candles` is RANGE-partitioned with no catch-all partition (deliberately, for query-pruning), so an unrecognized month rejects every insert outright. This app is running past the two months the original migration seeded (July/August 2026) *today* — this was not a someday concern. Idempotent, self-healing, always ensures the current month and the next one, so a write landing right at a month boundary is never the first thing to discover the next partition doesn't exist.
    - `app/services/candle_store.py` — `get_recorded_candles()`, the read side. `GET /market/candles` (`market.py`) now checks this first, before ever reaching an external provider: for `1m` specifically this is the *only* source that can ever exist at all on a free-tier Polygon/Massive plan (see #39, and this entry's own Massive-rebrand note below), so self-recorded data isn't a fallback, it's the primary path. An external provider is only reached when literally nothing has been recorded yet for a symbol (brand-new ticker, or a freshly-migrated/empty database) — a partial match (recorded history shorter than the requested range) is returned as-is rather than topped up from Polygon, since Polygon structurally can't fill a 1m gap anyway. A DB that's unreachable is treated as "nothing recorded yet" (caught, logged, falls through), not a hard failure — the whole path is an optional enhancement at this phase, same soft-fail posture main.py already applies to a missing Finnhub/Polygon key.
    - `main.py` — `CandleRecorder` starts unconditionally in `lifespan()`, independent of whether Finnhub/Polygon end up connected, right after the Event Bus starts. Stops cleanly on shutdown, same `stop()` pattern decision #42 established for `TickIngestBridge`.

44. **Frontend chart timeframe wiring fixed at the root; backend gained session-local aggregation for 5m/15m/1h; `AFTER_HOURS` added as a real `MarketClock` session; `4h` made an explicit, clean "not yet supported" instead of an unhandled crash.** Reported symptom: `curl`ing `GET /market/candles?timeframe=1d` returned real, correct JSON, but the chart never showed it.

    **Root cause: the chart never called that endpoint with a real timeframe at all.** `useLiveCandles` always requested `timeframe=1m` (the parameter wasn't even threaded through from the caller), and `SubWindow.tsx` derived every displayed timeframe by resampling that 1m buffer client-side via `resampleCandles` — the same index-position-based bucketing decisions #40/#42 already flagged as not calendar/session-aligned, and never wired to request anything else from the backend regardless of the timeframe selector's value. `1d` looked broken because a 240-candle (four-hour) in-memory buffer can never resample into a meaningful daily bar — not because the daily data itself was wrong, which the reported `curl` had already proven.

    **`useLiveCandles(symbol, timeframe)` now requests the real selected timeframe** (`GET /market/candles?timeframe=...`) instead of always `1m`; `SubWindow.tsx` passes `config.timeframe` straight through and no longer calls `resampleCandles` in the live render path. `resample.ts` is left in the tree, unimported, flagged as a removal candidate rather than deleted outright — same "flag for the user to decide" posture decision #35 already took with `GridPresetPicker.tsx`'s dead code. Live updates: the `market.candle` WebSocket channel only ever pushes a freshly-closed `1m` candle (`TickIngestBridge`'s fixed bucket size) — for a `1m` view this is still appended directly, unchanged from before; for any coarser view, appending it directly would inject a spurious 1-minute-wide candle into a 5m/15m/1h/1d series, so instead each `1m` close now triggers a fresh backfill re-fetch for whatever timeframe is currently selected. This keeps bucketing logic in exactly one place (the backend) rather than needing a second, TypeScript reimplementation of session-aware bucketing to keep in sync — and the underlying data can't update more than once a minute regardless of which approach is used.

    **Backend: `candle_aggregator.py` derives `5m`/`15m`/`1h` from recorded `1m` rows on read** (`CandleRecorder` — decision #43 — only ever writes `1m`; nothing coarser was ever going to be self-recorded directly). Built hierarchically (`1m → 5m → 15m → 1h`, each level from the nearest coarser level already computed) rather than every timeframe re-aggregating raw `1m` independently — one bucketing/OHLCV function to get right, proven identical to aggregating straight from `1m` at the same width by a dedicated regression test. OHLCV per bucket: open/close from the first/last member as expected, but **high/low/volume are computed across every member of the bucket, not just the first and last** — an earlier verbal description of this approach (checked and corrected before any code was written) would have missed any spike or dip that happened mid-bucket. `GET /market/candles` tries this after an exact self-recorded match comes back empty and before falling through to an external provider — real, session-aware data beats Polygon's free-tier intraday, which is paywalled entirely regardless (decision #39) and would just fail anyway. `1d` deliberately excluded from aggregation — stays sourced from Polygon's real daily EOD bars rather than reconstructed from however much `1m` history happens to be sitting in the database, per explicit discussion before coding.

    **Session-local, not a continuous 24h clock — the reason this needed real design discussion, not just wiring.** Premarket / regular / after-hours are aggregated as three separate domains, each anchored to `MarketClock.session_bounds()` (new method), so a bucket never straddles a session boundary — e.g. a naive clock-aligned `1h` bucket anchored to midnight would blend `15:30–16:00` regular-session trading with `16:00–16:30` after-hours trading into one misleading bar; proven directly with a regression test asserting a `15:58` tick and a `16:02` tick land in two different buckets. `OPEN`/`LUNCH`/`POWER_HOUR` all resolve to the *same* bounds (market open to market close) — regular session is one continuous aggregation domain, not reset at the 11:30/14:30 sub-boundaries `current_session()` still tracks for other callers. None of the three sessions divides evenly by every bucket width: premarket (5.5h) and regular (6.5h) both leave a 30-minute stub bucket at `1h`; after-hours (4h) is the only one of the three that's clean at every width tried here — confirmed with a test, not just asserted. `AFTER_HOURS` (`16:00–20:00` ET) is a genuinely new `Session` value — `market_clock.py` had no representation of it before this at all, only `CLOSED`; checked its only consumer (`GET /health`) before adding it, which just reports the session value rather than pattern-matching specific ones, so this was a safe additive change, not a rewrite. `is_market_open()` is unaffected by design — it still means the regular session specifically, confirmed by a regression test.

    **`4h` made an explicit 400, not left alone as dead code that happened to be unreachable.** `polygon_provider.py`'s `_TIMEFRAME_TO_POLYGON` mapping never had a `4h` entry, and the lookup that would have hit that gap sits outside its own try/except — meaning a `4h` request would have propagated as an unhandled 500, not a clean rejection. Per explicit discussion, `4h` isn't worth a session-boundary design (the regular session's 6.5h doesn't divide evenly by 4h, and nothing in this app uses it yet) — but "unsupported" still has to mean a proper 400 with a clear message, not a crash. Fixed by simply removing `4h` from `market.py`'s own `_MINUTES_PER_UNIT` gate, so it's rejected before ever reaching `polygon_provider.py` — the adapter's own missing mapping is now unreachable dead code via this route, flagged rather than touched, since fixing it would mean inventing the bucket definition this decision explicitly declined to invent.

    **Known limitations, stated rather than silently accepted:** (1) aggregation trusts every non-trailing bucket as complete — a `CandleRecorder` outage mid-session (restart, dropped connection) leaves a gap that silently narrows a bar's high/low with no flag indicating it; revisiting this needs a real trading-calendar source (`market_clock.py`'s own Phase 2 scope note) to know how many `1m` rows a bucket *should* have, not just wall-clock minutes. (2) the `16:00–20:00` after-hours boundary is the common industry convention, not yet verified against what Finnhub/IBKR actually deliver on this account — the recorder simply won't have rows past wherever the live feed actually stops, regardless of where this boundary is drawn; a real-feed check, not a design question, and explicitly not done as part of this entry.

45. **Backend Feature Engine started: server-side SMA, published as `FeaturesUpdated` on every `1m` `CandleClosed` — Phase 4's actual kickoff, and the prerequisite for the (separately discussed, not yet built) Level Interaction Engine.** New package `app/feature_engine/` (`indicators.py` — pure math, `engine.py` — the `FeatureEngine` class), new payload schema `app/schemas/events/features.py` (`FeatureSet`), wired into `main.py`'s lifespan alongside `CandleRecorder`.

    **Deliberately NOT a client→server push of the existing frontend SMA.** `frontend/src/indicators/sma.ts` stays exactly what decisions #40/#41 already scoped it as — a stateless, view-only chart overlay nothing downstream reads. Recomputing server-side from persisted `1m` candles (`CandleRecorder`, decision #43) was simpler, not just "safer": there was no push mechanism to build, no two-tabs-disagree case to define behavior for, and it keeps "Strategy/Decision Engine only ever read the one canonical Feature Engine output" (system-design.md §1) true in practice, not just in the doc.

    **Scoped to `1m` only in this pass — stated explicitly, not silently assumed to cover more.** `CandleClosed` only ever fires for `1m` today (`TickIngestBridge`'s fixed bucket size); `5m`/`15m`/`1h` are still derived read-side only (`candle_aggregator.py`, decision #44), with no "aggregated candle closed" event yet for this engine to hook. Extending SMA to those timeframes is real follow-up work, due whenever the Level Interaction Engine actually needs multi-timeframe levels (per the parallel Trading Intelligence design discussion) — not built ahead of that need.

    **State model: in-memory rolling window per `(symbol, timeframe)`, not a DB read on every candle.** Initially considered mirroring `candle_store`'s read pattern — re-querying recent closes on every `CandleClosed`, the same way the route layer reads for chart requests. Rejected before writing it: `FeatureEngine` and `CandleRecorder` both subscribe to the same `CandleClosed` event, each decoupled via its own internal queue (same shape, deliberately, as `CandleRecorder`'s own write-behind design) — nothing guarantees `CandleRecorder`'s write of the *current* candle lands before `FeatureEngine` would try to read it back, a genuine ordering race, not a hypothetical one. Fixed by never depending on it: the current candle's close is already known synchronously from the event payload itself; a DB read (new `candle_store.get_recent_closes()`) only ever happens once per `(symbol, timeframe)`, lazily, backfilling *prior* closes — which by construction already finished closing, with a full candle-interval to be durably recorded, before the current one arrived. Same "has memory, rebuilt from persisted history on startup" shape `trading-intelligence-architecture.md` §4 already specified for Market State Engine, applied here for the first time in actual code.

    **Numerical posture, discussed explicitly rather than defaulted:** full recompute of the mean from the window on every close, not an incremental running sum — removes floating-point drift as a possibility entirely for a long-running, ~100-symbol process, rather than bounding or tolerating it (`indicators.sma()`'s own docstring). Warm-up returns `None`, never `0.0` or an exception, so "not enough history yet" and "a real computed value of zero" stay distinguishable. A duplicate or out-of-order `CandleClosed` for a `candle_ts` already applied to a symbol's window (the same rare race decision #42 already accepts as known/rare at the DB layer) is dropped rather than silently double-counted, since this in-memory window has no DB unique constraint to lean on the way `CandleRecorder` does. Per-item failures (bad candle, DB hiccup, insufficient history) are caught and logged individually inside `FeatureEngine`'s own worker loop, on top of (not instead of) the Event Bus's own existing per-subscriber isolation (`EventBus._safe_call`) — one bad symbol/candle can't stall the other ~100 behind it in this engine's queue.

    **`feature_snapshots` deliberately NOT written to in this pass.** system-design.md §4.5 already specifies feature values get persisted "at decision time," when a strategy actually acts on them — not on every candle close. Since Strategy Engine doesn't exist yet, writing every computed `FeatureSet` to that table now would mean guessing at a schema ahead of the module that defines what it actually needs, the same reasoning `app/models/market_data.py`'s own docstring already gives for every other not-yet-populated table. 46. **Level Interaction Engine built: touch/holding/rejected/conquered tracking for any level FeatureEngine publishes, not just SMA.** New package `app/trading_intelligence/level_interaction_engine.py` (`LevelInteractionEngine`, `classify_zone()`), new payload schema `app/schemas/events/level_interaction.py` (`LevelInteractionChanged`), new tables `level_interaction_state`/`level_interaction_events` (migration `0002`), new small helper `MarketClock.trading_day()`. Wired into `main.py`'s lifespan alongside `FeatureEngine`. This is the concept discussed and pinned down over several rounds before any of it was written: Aura (a symmetric %-band around a level, default 0.2%), Touch (a below/above → inside-Aura transition), Holding, Rejected (exits the side it entered from), Conquered (exits the opposite side), with a per-touch counter, dwell time, and distance anchored at the level's value when the touch began.

    **Generic by construction, not SMA-specific — the "reusable unit" ask from the original discussion.** The engine subscribes to `FeaturesUpdated` and runs the identical state machine against every key in `FeatureSet.features`, whatever it's called. It doesn't know "SMA" exists as a concept. When Feature Engine starts publishing `ema_9`, `vwap`, or pivot levels under their own keys (decision #45's stated follow-up work), this engine tracks them immediately, with zero code changes — verified directly, not just asserted: `test_multiple_level_keys_tracked_independently` runs `sma_9` and `sma_20` through the same `FeaturesUpdated` event and confirms they're tracked as fully independent state machines.

    **`FeatureSet` (decision #45) gains a `close` field.** Needed both a level value AND the raw price to classify a zone against it. Considered having this engine separately subscribe to `CandleClosed` for the price and correlate it against `FeaturesUpdated` for the level value by `candle_ts` — rejected for the identical reason decision #45 rejected re-querying `candle_store` on every candle: two decoupled subscribers to two different event types, published at two different times, with no ordering guarantee between them. Folding `close` into `FeatureSet` instead makes `FeaturesUpdated` self-contained, so this engine never needs to correlate anything. No other consumer of `FeaturesUpdated` exists yet to break.

    **Trigger and precision: candle-close only, as confirmed.** No tick stream in this setup, so a "touch" is only ever observed at whatever granularity `CandleClosed` fires at (`1m`, matching Feature Engine's own current scope) — durations are inherently quantized to that step size, not sub-candle-precise. **No debounce/cooldown, also as confirmed:** rapid re-touch is treated as real information (a level being repeatedly tested), not noise to filter out, so every raw zone transition counts.

    **Distance, as confirmed:** anchored at `touch_anchor_price` — the level's value at the candle where the touch began — and NOT re-anchored to the live level each subsequent candle, so a drifting SMA during a multi-candle hold doesn't get conflated with price actually moving.

    **State model, same shape as decision #45, one level deeper:** in-memory live state per `(symbol, timeframe, level_key)` is the fast path; a DB row is read once, lazily, only the first time this process sees that key — restart survival, per `trading-intelligence-architecture.md` §4's "rebuilt from persisted history on startup" pattern, now proven in code a second time. Unlike `FeatureEngine`, this engine's DB *writes* also only happen on an actual zone transition — a steady "still below the level" candle costs nothing beyond an in-memory comparison, keeping writes at touch-rate rather than candle-rate. A duplicate/out-of-order `FeaturesUpdated` for a `candle_ts` already applied to a `(symbol, timeframe)` is dropped, same posture as decision #45.

    **Two edge cases resolved by explicit judgment call — flagged back, not silently decided, per Saqib's own "customize per your understanding, then tell me" instruction:**
    - **Gap-through:** a candle closes `below`, the very next closes `above` (or vice versa), with no candle ever closing `inside_aura` in between. By definition this can only be `conquered` — a rejection requires exiting the side you entered from, which is impossible in a single jump. `seconds_in_zone=0`, `entered_ts=None`, and — since there's no discrete "touch began" candle to anchor to — `anchor_price` uses the CURRENT (arrival) candle's level value rather than the prior one. Tagged `observed_via="gap"` vs. `"dwell"` so a consumer can tell "clean break with no test at all" apart from "ground through the level over several candles." **Worth confirming this anchor choice matches intent** — the alternative (anchoring to the last-known level value *before* the gap) would give a different `distance_pct` for the same event.
    - **Cold-start-unknown-origin:** this process's very first observation of a `(symbol, timeframe, level_key)` is already `inside_aura` — no prior zone recorded, so no known entry side. The touch is still counted and tracked, but on resolution `outcome` is left `None` (`status="unclassified"`, `observed_via="cold_start_unknown_origin"`) rather than guessing which side it "really" entered from.

    **Emits `LevelInteractionChanged` on touch START and RESOLUTION only** — not on every candle while still holding. A live "holding for N seconds, updating each candle" read (closer to a literal read of Saqib's original "holding for 20 seconds" framing) is real, easy follow-up work, deliberately not built in this pass to keep this step's surface area bounded and testable — flagged rather than silently included or silently dropped.

    **Same soft-fail posture as `CandleRecorder`, with one consequence worth naming explicitly:** a DB write failure here is caught and logged, not raised — the engine keeps running and keeps emitting live `LevelInteractionChanged` events off in-memory state even if Postgres is unreachable. The real cost of that choice: if the DB stays down through a restart, whatever was mid-touch at the moment of the outage is invisible to the next process (no persisted row to rebuild from) — same trade-off `CandleRecorder` already accepted for candle data (decision #43's "an unreachable DB must not crash the pipeline"), applied here for the first time to state that can't be re-derived from re-fetching history afterward.

    **Verified:** the two new tables created via a real `alembic upgrade head` (migration `0002`) against the same local Postgres. Full backend suite: **108 passed** (up from 98; 10 new in `test_level_interaction_engine.py`) — 1 pure (`classify_zone()` boundary math, no DB), 9 against real Postgres covering: touch→rejected, touch→conquered, gap-through, cold-start-unknown-origin, `touch_count_today` incrementing across multiple same-day touches, `touch_count_today` resetting on an ET trading-day rollover, a genuine restart-survival test (persist a touch via one engine instance, resolve it correctly via a **brand-new** instance with zero in-memory state), independent tracking of two level keys from the same event, and duplicate-event dropping.     **Three real, unrelated shutdown bugs found chasing one flaky test, not by inspection — worth recording in full since two of them are conceptually significant beyond this feature:**

    1. **`stop()` on all three engines (`CandleRecorder`, `FeatureEngine`, `LevelInteractionEngine`) was fire-and-forget.** `task.cancel()` only *schedules* cancellation — it doesn't block until the task actually unwinds. A cancelled task blocked inside `asyncio.to_thread(...)` (any of these engines' DB calls) can't be interrupted until that thread finishes, so `stop()` could return, and a caller could reasonably believe shutdown was complete, while a write was still in flight. Fixed: all three `stop()` methods are now `async def`, `await`-ing the cancelled task (catching `CancelledError`, which in practice never actually fires — the loops already swallow it internally — but this still correctly blocks until the task is truly done).

    2. **Shutdown order was backwards.** Engines were stopped before the Event Bus. While `CandleRecorder.stop()` was still draining, the bus was STILL dispatching fresh `CandleClosed` events to `FeatureEngine` (not yet told to stop) and, transitively, fresh `FeaturesUpdated` to `LevelInteractionEngine` — so "await engine.stop()" was correctly waiting for an ever-refilling queue with no natural bound. Fixed: `main.py`'s lifespan now stops the bus FIRST, cutting off new dispatch at the source, so each engine's own drain afterward is a fixed, bounded backlog.

    3. **`lifespan()` had a bare `yield`, no `try`/`finally`.** This is the one that actually explains most of the observed flakiness. An exception raised anywhere inside `async with app.router.lifespan_context(app):` — which is exactly how this app's own async tests exercise real engine behavior (see `test_intelligence_routes.py`) — gets thrown INTO the generator at the `yield`. With no `try`/`finally`, that exception propagates straight out, skipping every shutdown line entirely: the bus and all three engines are simply abandoned mid-run, still touching the database, with nobody watching. Surfaced as "Task was destroyed but it is pending!" warnings, often during an unrelated LATER test. Fixed: `yield` wrapped in `try`/`finally` so shutdown always runs, exception or not.

    **A fourth, non-code cause, found last:** `backend/tests/conftest.py`'s singleton-reset fixture was updated to include the two new engines back in decision #46's own work — but that edit was made in a staging copy and never actually copied into the real `backend/tests/conftest.py`. The two engines' module-level singletons were never being reset between tests this whole time, which was the dominant cause of the flakiness actually observed (confirmed directly: instrumenting the real failing test showed the SAME `EventBus`/`FeatureEngine` object identity reused across supposedly-independent tests, and a queue genuinely bound to a stale event loop from an earlier test — precisely the failure mode that fixture's own docstring already describes). Fixed by actually applying the edit this time. The three shutdown bugs above are real and worth having fixed regardless, but this was the specific bug primarily responsible for what was observed.

    **Test-level fix, on top of all the above:** `test_intelligence_routes.py`'s multi-symbol test was letting the lifespan block exit — and shutdown begin — while only ONE of two published symbols had been confirmed processed. Fixed by waiting for both. Separately, waiting for `FeaturesUpdated`-derived data (`sma_9` appearing) is NOT a valid proxy for "`CandleRecorder` is also done" — they're deliberately independent, concurrent subscribers to the same event (decision #45's own design), so a new `_wait_until_candles_persisted()` helper polls the DB directly rather than inferring one engine's completion from another's.

52. **EMA added to Feature Engine — Stage 3's first indicator (decision #50), resolving D3: full-window recompute over a bounded history, not true incremental recursion.** EMA is mathematically a recursion over all history since inception, unlike SMA's exact finite window — there's no bit-identical finite substitute. Resolved by seeding with the SMA of the OLDEST `period` closes in a bounded window sized `period * seed_multiplier` (default multiplier 5), then applying the standard recursion forward through the rest of that window — the exact same algorithm `frontend/src/indicators/ema.ts` already uses (seed with SMA of the first `period` closes, then recurse), just bounded instead of recomputing from every candle currently loaded on the chart. This keeps EMA restart-safe the same way SMA already is: no incrementally-carried EMA value survives a process restart to drift or need reconstruction — only raw closes are ever stored, and those are cheap to backfill from persisted history.

    **The approximation is named, not hidden.** The seed value isn't the "true" EMA from inception, so early bars in the window carry a residual bias that decays geometrically at rate `(1 - k)` per bar (`k = 2/(period+1)`) — at the default multiplier, below `0.8^40 ≈ 0.00013` of its starting size for a 9-period EMA, negligible at any price this system trades, but explicitly not a guarantee of bit-identical output against a party that's carried the recursion since inception. `indicators.py::ema()`'s own docstring carries the full math; this isn't asserted only here.

    **Stricter warm-up than SMA at the same period, on purpose.** `ema()` returns `None` until `period * seed_multiplier` closes exist — not just `period`, the way `sma()` needs. Publishing an under-converged EMA (seeded but without enough bars to decay that seed's influence away) would be a materially biased number, not merely an early one, and this module doesn't publish those silently. Proven directly against the boundary in `test_ema_warmup_is_stricter_than_sma_at_the_same_period`, and end-to-end through a real `EventBus` in `test_sma_and_ema_coexist_in_the_same_featureset_with_independent_warmup` — `ema_2` genuinely absent from `features` for 4 straight candles where `sma_2` is already present, then both correct together on the 5th.

    **One shared window, not a second data structure.** `FeatureEngine._windows` already held raw closes per `(symbol, timeframe)` for SMA; EMA reads from the exact same deque, just slicing a longer trailing portion when it needs one. The deque's capacity (`_window_capacity`, replacing the SMA-only-named `_max_period`) is now sized to whichever family needs more history — `max(sma_max_period, ema_max_period * seed_multiplier)` — so a single symbol+timeframe's cold-start backfill (`candle_store.get_recent_closes()` for `1m`; `candle_aggregator.aggregate_from_recorded()` for `5m`/`15m`/`1h`, per decision #51) satisfies both families in one query, not two.

    **New settings:** `feature_engine_ema_periods` (default `[9, 20]` — the two legacy chart presets from `WorkspaceContext.tsx`'s `EMA9`/`EMA20`, not copied from `feature_engine_sma_periods`, since chart usage never included an EMA50) and `feature_engine_ema_seed_multiplier` (default `5`).

    **Test isolation fix applied while implementing, not planned upfront:** every existing `FeatureEngine(bus, sma_periods=...)` test-construction site (9 of them, across both SMA-only and Stage 2's aggregated-timeframe tests) now explicitly passes `ema_periods=[]`. Without it, EMA's `[9, 20]` default would have silently pulled `_window_capacity` up to 100 for every one of those tests — including three from Stage 2 that were specifically written to stay DB-independent by keeping the window small (`sma_periods=[1]` → `_window_capacity=1` → cold-start backfill skipped entirely) — turning them into DB-dependent tests without that being a deliberate choice anywhere.

    **Verified:** full backend suite — **126 passed** (up from 122; 4 new — a hand-computed golden-value test for the recursion itself, the stricter-warmup boundary test, an invalid-input test, and the shared-window coexistence test above) — stable across 3 consecutive runs against the same real local Postgres used for decision #51. **Not verified:** same caveats as #51 — synthetic events on a real bus, not a real tick; the Chart still doesn't consume any of this. Also not verified: EMA's actual numerical closeness to the frontend's own unbounded-window `ema.ts` output on a real, long-running symbol — the convergence math above is analytical, not cross-checked against a live side-by-side comparison, which would need Stage 1 (Chart consumption) to even be possible.

53. **VWAP added to Feature Engine — Stage 3's second indicator (decision #50). Genuinely different shape from SMA/EMA, not a third variation on the same pattern, and treated that way rather than forced into the rolling-window abstraction.** Keyed by SYMBOL alone, not `(symbol, timeframe)`: VWAP is a session-level statistic — the same number regardless of which chart timeframe someone happens to be looking at, matching how real trading platforms behave (a 5m chart and a 15m chart of the same session show the same VWAP line, not two slightly different ones). Computing it separately per timeframe from that timeframe's own coarser bars would have produced a slightly different number for the "same" value depending on timeframe — exactly the kind of divergence this whole migration exists to eliminate. Computed once, from `1m` bars only (the finest granularity this engine ever directly receives), and the SAME current value is attached to every `FeatureSet` a given `1m` close produces — the `1m` one and any `5m`/`15m`/`1h` ones that happen to complete on it — proven directly in `test_vwap_is_identical_across_1m_and_5m_featuresets_on_the_same_close`, not just asserted.

    **A monotonically growing accumulator (`cumulative_pv`, `cumulative_volume`), reset at the regular session's start — not a bounded sliding window.** There's no "oldest value to drop" the way SMA/EMA have, so there's no equivalent of their subtract-oldest/add-newest drift concern to design around: every addition to the accumulator across a session is the same sequential-summation operation whether done incrementally (`total += x`) or by re-summing a stored list from scratch — the two are numerically identical, unlike SMA's sliding window, where subtraction genuinely introduces a different (and worse) rounding path than a fresh mean. Reset detection: whenever the incoming candle's session-open timestamp (`MarketClock.session_bounds()`) differs from what's currently tracked for that symbol — covers both the routine daily rollover and a process restart identically, one code path.

    **Regular-session-only, matching `frontend/src/indicators/vwap.ts`'s own convention exactly, not a new policy invented for the backend.** A new `MarketClock.is_regular_session()` method (`OPEN`/`LUNCH`/`POWER_HOUR` → `True`; `PRE_MARKET`/`AFTER_HOURS`/`CLOSED` → `False`) gates accumulation — pre-market and after-hours volume never contributes, unlike aggregated SMA/EMA (decision #51), which happily buckets pre-market/after-hours candles too, just kept in their own separate buckets. A candle outside regular session simply doesn't get a `"vwap"` key in its `FeatureSet.features` at all, the same "not ready, not silently 0.0" convention SMA/EMA's warm-up already established.

    **Warms up far faster than SMA/EMA — one bar of nonzero regular-session volume, not nine or more — and now publishes independently of them.** `_apply_close()`'s shared "seed window, compute, publish only if warmed up" path (built for SMA/EMA — decision #52) gained an `extra_features` parameter, merged in AFTER the SMA/EMA computation but BEFORE the "nothing ready yet" check, so a symbol whose SMA/EMA are still warming up still publishes once VWAP alone is ready, rather than waiting on the slower indicator. Proven directly: `test_vwap_publishes_even_while_sma_is_still_warming_up` uses `sma_periods=[50]` — nowhere close to satisfied — and the FeatureSet still publishes with `{"vwap": ...}` alone.

    **Cold-start backfill reuses the exact same "prior, already-persisted, already-closed" reasoning as SMA/EMA's own** (decisions #45, #51) — `candle_store.get_recorded_candles()` for whatever's already recorded between the session's open and the current candle, strictly before it. A known-narrower accumulator if `CandleRecorder` had a gap earlier in the session, same accepted trade-off `candle_aggregator.py`'s own docstring already carries for its read-side aggregation — not treated as a new problem here.

    **Verified:** full backend suite — **134 passed** (up from 126; 8 new — 3 pure-function tests for `typical_price()`/`vwap_from_accumulator()`, and 5 through a real `EventBus`: pre-market exclusion, cross-session reset, `1m`/`5m` cross-timeframe identity, publishing independently of SMA's warm-up, and a real-Postgres cold-start backfill) — stable across 3 consecutive runs. **Not verified:** same standing caveats as #51/#52 — synthetic events on a real bus, not a real tick, and the Chart still consumes none of this (Stage 1 remains the open dependency, not addressed by this entry). Also not verified: `typical_price()`'s H/L/C weighting specifically through the engine end-to-end — the engine-level tests above all use flat (open=high=low=close) synthetic candles for hand-verifiability, so VWAP reduces to a plain mean of closes in every one of them; the H/L/C-weighted case is covered only at the pure-function level (`test_typical_price_is_high_low_close_average`), not cross-checked against a real candle with genuine intrabar range.

59. **Daily Levels — concept locked across a three-way review (Saqib + Claude + Grok + ChatGPT), direction recorded before any code, same pattern as decision #50's chart-migration lock.** Full plan: `docs/architecture/daily-levels-design.md` (new living document, mirroring `feature-engine-chart-migration.md`'s staging/open-decisions-table format). **No application code in this entry.**

    **The concept:** cluster the open/close prices of up to `daily_levels_lookback_days` (default 180, tunable) 1D candles into support/resistance zones — two points within `daily_levels_cluster_pct` (default 0.2%) of each other's eventual cluster average count toward the same level; a level's price is the cluster average, its strength is the count of contributing points. Once drawn, each level gets full `LevelInteractionEngine` tracking (touch/reject/conquer), same as every other level type. Level *calculation* and level *interaction* are kept deliberately separate throughout — the interaction engine never influences what counts as a level.

    **A real arithmetic error caught and corrected before it could ship, not after — worth recording in full, same as decision #48's "verify forwarded AI claims" precedent.** An initial clustering proposal tested each new candidate point against the cluster's *stale* running average. Re-deriving the arithmetic directly on the proposal's own worked example (points 100.10/100.20/100.40, 0.2% tolerance) showed it does NOT produce the claimed 3-point, ~100.23 level — 100.40 is 0.25 away from the then-current average of 100.15, and 0.2% of 100.15 is only ≈0.2003, so the stated rule would actually reject it, leaving a 2-point level and a discarded singleton. Corrected rule: test the WHOLE tentative cluster (old members plus the candidate) against the average it would produce if accepted, requiring every member to pass — not just the newest one. Re-run against the same example, this correctly produces the intended 3-point, ≈100.23 level. Full derivation and pseudocode: `daily-levels-design.md` §1.

    **Same-candle validity gate, confirmed:** a candle's own open and close landing within tolerance of each other must not manufacture a strength-2 "level" from a single candle — contradicts the original "minimum 2 1D candles" spec. Resolved: each cluster tracks `distinct_candle_count` alongside `strength` (total point count); validity requires `distinct_candle_count >= 2`. A same-candle pair can still contribute to a larger cluster's strength once a second candle's point also joins it — it just can't stand alone.

    **Resolved, explicitly, per Saqib's own direct question: no bias/relaxation mechanism for a point that fails to cluster.** The algorithm already gives every point a full, fair evaluation — as a join candidate for the cluster ahead of it in sorted order, and as the seed of its own fresh cluster attempt against everything after it. A point surviving both with no partner has no confirming price point anywhere in the lookback window, which is the correct signal to discard it, not a gap to patch. Forcing inclusion would pull a cluster's average toward a price nobody actually revisited within tolerance, diluting what strength (and later, the touch aura) means. The two real, visible levers if too few/too many levels form in practice are `daily_levels_cluster_pct` and `daily_levels_lookback_days` — both config, not a hidden per-point exception.

    **Data source: a genuine precedent break, approved and isolated behind an interface.** Confirmed directly against `market.py`: `"1d"` always routes to Polygon's real EOD bars, never self-recorded or `candle_aggregator`-derived (decision #44), and Feature Engine's live engine has never once reached an external provider directly — every indicator built so far (decisions #45, #51–53, #56–57) sources exclusively from local `candle_store`/`candle_aggregator`. Daily Levels will be the first with a hard Polygon dependency, since waiting for 180 self-recorded trading days would make the feature useless for the better part of a year. Approved, but kept behind a new `DailyHistoryProvider` interface (`DailyLevelCalculator` never imports Polygon directly) so IBKR's historical role can supply the same data later without the calculator changing — and cached per `(symbol, trading_day)`, refreshed once per new 1D bar close, not re-fetched on every Feature Engine tick. **Not yet done, flagged as a Stage 1 prerequisite:** an empirical check of what Polygon/Massive's free tier actually returns for a 180-bar daily request (depth, pagination, rate limits) against the real key — the 180-vs-90-day default should come from that result, not a guess, same standing practice as decisions #32/#39.

    **Schema: a new `daily_levels: list[DailyLevel]` field on `FeatureSet`, not a hack on the flat dict.** Every existing indicator (decision #50) is a scalar; Daily Levels is a variable-length, day-to-day-reshaping list of `(price, strength)` pairs. Encoding it into fake flat-dict keys (`daily_level_1_price`/`daily_level_1_strength`) would leak strength values into `LevelInteractionEngine`'s generic key-iteration as if they were levels themselves. Symbol-keyed, not `(symbol, timeframe)`-keyed — same reasoning as VWAP (#53) and PDH/PDL/Camarilla/VPOC (#56–57): the same list attaches to every timeframe's `FeatureSet` on a given close.

    **Identity: persistent `level_id`, proximity-reconciled day to day — explicitly NOT rank-based.** A rank-based key (`daily_level_1` = strongest today) was considered and rejected: if rank order changes day to day, the same key can silently point at a physically different price zone, and `LevelInteractionEngine`'s touch history for it would look continuous when it isn't — confirmed against the code, since its whole state model assumes a `level_key` means the same thing every time it's seen. Instead, every level gets a durable, opaque `level_id` whose *price* evolves while its identity doesn't; each new 1D bar close, today's fresh clusters are matched to yesterday's surviving levels by nearest price within `daily_levels_identity_match_pct` (starting default: same 0.2% as the clustering tolerance, kept as its own separate setting since day-over-day drift and within-cluster spread are different questions that happen to share a starting value). A matched level carries its `level_id` forward; an unmatched survivor is archived, not deleted; an unmatched new cluster mints a fresh id. Needs a new `daily_levels_state` table (not built in this pass) — distinct from `level_interaction_state`, which will separately key its own rows by this same `level_id` once built.

    **`LevelInteractionEngine` needs a real, scoped extension — the first time its "zero code changes for a new level type" property (true since #46, reproven in #56) doesn't hold.** `daily_levels` is a separate list field, not dict entries, so the engine needs a small, explicit addition to also walk that list (keyed by `level_id`, valued by `price`) alongside its existing `features.items()` loop. Everything else about the engine — aura, the state machine, gap-through/cold-start-unknown-origin handling, daily reset — is reused completely unmodified; only the iteration surface grows. Recorded as a deliberate, acknowledged exception, not something to let happen quietly in a diff.

    **Frontend: explicitly out of scope for the first pass, not yet confirmed.** Checked directly: `frontend/src/indicators/` has no clustering/daily-level equivalent at all, unlike every other Feature Engine indicator, which ported an existing frontend implementation and got the "(local)" fallback pattern essentially for free. Recommended (D3 in `daily-levels-design.md`, not yet signed off): scope the first build to backend calculation + persistence + Level Interaction integration only, with chart rendering — including how "too many levels" gets handled, which Saqib's own plan is to filter/toggle in the UI rather than cap algorithmically — as its own later, explicitly scoped stage.

63. **Daily Levels Stage 2 built and tested — persistent, price-proximity-reconciled level identity, and restart survival, against real local Postgres.**

    **Reconciliation (design doc §4), confirmed NOT rank-based, matching what was already decided:** greedy nearest-price matching between today's freshly clustered zones and yesterday's still-`active` persisted rows, within `daily_levels_identity_match_pct` (decision #60's own config knob, sitting unused until now).     **`indicators/regression.py`** — OLS fit of the trailing `period` closes against an equally-spaced bar index. Two degenerate-case conventions spelled out rather than picked silently, and deliberately opposite from each other: a perfectly flat window still publishes `r2 = 1.0` (a constant series is trivially, perfectly explained by its own mean — residuals are all exactly 0 too) while omitting only `_slope_norm` (its own denominator, the window's close stdev, is 0); KAMA's own Efficiency Ratio (below) takes the OPPOSITE convention for its own 0/0 case, mapping to the WORST value (0) rather than the best — both documented in-place so neither reads as an oversight.

72. **LiveTickRelay — throttled "tick fluidity" for the chart's currently-forming 1m bar, on a small (max 8), explicitly-set active-symbol set. New standalone Event Bus subscriber, not an extension of `TickIngestBridge`.**

    **The ask, pinned down over several turns:** show the CURRENTLY FORMING candle breathing with real trades rather than only jumping once a minute — not a new candle resolution (a separate, still-open idea from earlier in the same discussion, deliberately not built here), and not full-tick-rate pushes to the frontend. Final shape: at most one update per symbol every 5 seconds (`flush_interval_seconds`, configurable), across at most 8 symbols at a time (`max_active_symbols`) — sized for "whatever a scanning process currently flags as most active," not the full ~100-symbol universe. Which 8 symbols are active is explicit and external to this component: `set_active_symbols()` / `POST /market/active-symbols`, callable by anything (a manual call today; Market Scanner once it exists) — LiveTickRelay itself has no opinion on how the 8 are chosen.

    **Deliberately NOT built into `tick_ingest.py`.** That module is explicitly documented (decision #16) as Phase-3-throwaway, "replaced wholesale, not extended" once the real Phase 4 Market Data Engine exists. A throttle patched into its internals would be a direct, avoidable conflict with that decision. Instead, `live_tick_relay.py`'s `LiveTickRelay` is a second, fully independent subscriber to the SAME `PriceUpdated` events `TickIngestBridge` already publishes — its own per-symbol bar accumulator (`_LiveBar`), its own minute-rollover detection (computed the same way `TickIngestBridge` does, but independently — no shared state, no import of its internals). Zero coupling either direction: `TickIngestBridge` can be replaced wholesale later without this file changing, and this file can be deleted or folded into the real Market Data Engine without touching `tick_ingest.py`.

    **New EventType (`PRICE_SNAPSHOT`) and its own channel (`market.tick.snapshot`), not reused on the existing `market.tick`.** `market.tick`/`PriceUpdated` already has a real consumer at raw-tick frequency — `useLatestPrices` (the watchlist). Throttling that same channel to 5s would have silently changed the watchlist's update rate as a side effect of a chart-only feature. `PriceSnapshot` (schemas/events/market_data.py) deliberately mirrors `CandleClosed` field-for-field (open/high/low/close/volume/candle_ts/timeframe) rather than reusing that model directly — same reasoning as decision #15's Tick-vs-PriceUpdated split: conflating "closed" and "in-progress" into one type would make every future `CandleClosed` consumer newly responsible for checking which kind it received. The matching field shape is what lets the frontend reuse `toCandle()` (api-client.ts) and the chart's existing `update_last` path with zero new type plumbing.

    **Honest-state discipline applied at 5s granularity, same convention as everywhere else in this codebase:** a symbol with no new ticks since the last flush is skipped that cycle, never re-published as a stale duplicate (proven directly in `test_quiet_symbol_is_not_republished_on_the_next_flush`) — no fabricated flat bar, ever. A minute rollover starts a genuinely fresh bar rather than carrying over the prior minute's high/low/volume (`test_minute_rollover_starts_a_fresh_bar_not_a_carried_over_one`). `set_active_symbols()` rejects (`ValueError` → `400`) rather than silently truncates a set larger than `max_active_symbols` — a caller expecting all N symbols tracked finds out immediately, not via a buried log line.

    **Frontend: `useLiveCandles` gained an optional `liveTick` param (`SubWindowConfig.liveTick: boolean`, decision #72), and a real pre-existing gap got fixed as part of wiring it in.** The hook's `candles` array previously only ever held CLOSED bars — nothing represented the in-progress bar at all, so a naive "subscribe to `market.tick.snapshot` and update the last element" wouldn't have worked correctly the first time a new minute's first snapshot arrived (there'd be no matching last-element timestamp to revise). Fixed with a shared `_upsertLast` helper — same-timestamp revises in place, newer-timestamp appends provisionally, older/stale is dropped — used by BOTH the snapshot handler AND the existing `market.candle` (`CandleClosed`) handler, which previously did an unconditional append. That append had to change too: once a provisional snapshot bar can already occupy the array's last slot, the real `CandleClosed` for that same minute must replace it, not duplicate it, or `liveTick` would produce visibly doubled bars on every close. `ChartWidget.tsx` itself needed NO changes — its existing `diffCandles`/`update_last` logic (confirmed by reading it directly before writing any of this) already handles a same-length, same-last-timestamp array revision correctly.

    **UI: "Tick" lives in the same Timeframe menu list as 1m/5m/15m/1h/4h/1d (`SubWindowMenu.tsx`), not a separate section** — matches how it was actually asked for ("alongside timeframes... where logically suited best"). Selecting it sets `{ timeframe: "1m", liveTick: true }` together in one call; selecting any real timeframe sets `liveTick: false` — the two can never end up in an inconsistent combination through the UI. `useLiveCandles` also defensively no-ops the tick subscription if `timeframe !== "1m"` at the moment a snapshot arrives, rather than trusting that pairing to always hold.

    **Tested at the same tiers as the rest of this codebase:** 6 new tests in `test_live_tick_relay.py`, real in-process `EventBus` (not mocked), matching `test_tick_ingest.py`'s own style — throttled-collapse-to-one-snapshot, inactive-symbol-never-published, quiet-symbol-not-republished, minute-rollover-fresh-bar, over-max rejection, and removed-symbol-drops-its-bar. All 6 pass; full suite (excluding the Postgres-dependent tests, no local DB in this sandbox) shows zero regressions. `conftest.py`'s singleton-reset fixture (decision #38's own fix) was extended to also reset `live_tick_relay._live_tick_relay` — the same event-loop-binding hazard that fixture already exists to prevent for `_event_bus`/`_feature_engine`/`_level_interaction_engine` would otherwise apply here too the first time a route-level test exercises `POST /market/active-symbols` through the real app lifespan. `npx tsc -b` (filtered for the known pre-existing `GridPresetPicker` errors) and `npx vite build` both clean.

    **Not verified — no real live trading day, no real browser session** (same standing limitation as every other frontend change in this codebase): the actual visual "breathing" behavior on a real chart against real Finnhub ticks hasn't been seen, only reasoned through against the exact code read directly from the repo and proven at the unit level. `POST /market/active-symbols` itself is also new and unverified against a real running server — same "reasoned from the real code, not yet seen live" caveat.

73. **Chart Style — candlestick vs. OHLC bar, as a native `lightweight-charts` series toggle. Global default + per-sub-window override, extensible to future styles. Purely frontend; no Feature Engine or backend involvement.**

    **Native library support, no custom renderer.** The already-installed `lightweight-charts` v4.2.3 ships `chart.addBarSeries({ upColor, downColor })` alongside `addCandlestickSeries` — its defaults (`thinBars: true`, `openVisible: true`) render the requested OHLC style (high-low stick, left open tick, right close tick) with zero configuration beyond the same `upColor`/`downColor` already used for candles, so BULL/BEAR stay visually consistent across both styles. Same OHLC data shape either way (`{time,open,high,low,close}`) — zero backend or Feature Engine changes.

    **`ChartStyle = "candlestick" | "bar"`** (`types/workspace.ts`) is a plain string union, not a config object — this is one scalar choice, same shape as `backgroundColor`/`gridColor` rather than the nested-object pattern `VolumeBarsConfig`/`DailyLevelsConfig` use for genuinely multi-field settings. Deliberately extensible: a future third style is one more union member and one more branch in the two `addXSeries` ternaries below, not a new mechanism.

    **Global default + per-sub-window override, matching the existing pattern exactly — not a new concept.** `DEFAULT_CHART_STYLE = "candlestick"` is applied everywhere `WorkspaceContext.tsx` constructs a new `SubWindowConfig` (all inline constructors plus `makeDefaultSubWindows`'s templated one), backfilled in `normalizeSubWindow` for layouts saved before this field existed (old sessions keep rendering candlesticks — the only backfill value that doesn't silently change an old layout's appearance), and overridden per-instance via the existing `updateSubWindow(id, { chartStyle })` mechanism from a new `SubWindowMenu` screen — the same three-site wiring `volumeBars`/`dailyLevelsConfig`/etc. already use, confirmed by reading `WorkspaceContext.tsx` directly before touching it rather than assumed.

    **`ChartWidget.tsx` — live style switching without recreating the chart, so zoom/pan survive a toggle, same reasoning already documented for symbol/timeframe switches.** `candleSeriesRef` widened to `ISeriesApi<"Candlestick"> | ISeriesApi<"Bar"> | null` — safe because every downstream consumer (overlays, horizontalLevels, dailyLevels effects) only calls the series-agnostic subset of the API (`createPriceLine`, `setMarkers`, `priceToCoordinate`, `removePriceLine`), confirmed against `lightweight-charts`' own typings before widening, not assumed; **proven by a real `tsc -b`/`vite build` pass, not just argued** — both come back clean (only the known pre-existing `GridPresetPicker` errors, decision #35). A new effect (`currentChartStyleRef` tracks which style is currently live) does `removeSeries` + `addXSeries` + `setData` when the `chartStyle` prop changes, mirroring the add/remove shape the indicator-line-series effect already uses.

    **A real coordination bug found and fixed while implementing, not left latent:** the overlays/horizontalLevels/dailyLevels effects draw onto `candleSeriesRef.current` but didn't originally depend on `chartStyle`, so a style swap would silently orphan their price lines/markers on the just-removed old series until some unrelated prop change happened to re-trigger them (self-healing within seconds during live ticks in most cases, but not guaranteed, and worse after-hours or in a static test session). Fixed by adding `chartStyle` to those three effects' own dependency arrays and placing the swap effect immediately after the mount effect — React's cleanup-then-setup ordering (all cleanups top-down, then all setups top-down, in declaration order) means the swap effect's setup reassigns `candleSeriesRef.current` to the new series before those three effects' setups run in the same commit, so they reattach to the right series with no visible gap. Reasoned through against the actual effect declaration order in the file, not assumed correct.

    **UI:** new "Chart Style" row in `SubWindowMenu`'s root screen (between Candles and Background), its own screen with a 2-option segmented control (`CHART_STYLES.map(...)`, same visual pattern `volumeBars`' color-mode toggle already uses) plus a reset-to-default row.

    **Not verified:** no real browser click-through session (same standing gap every frontend change in this codebase already carries) — the live series-swap behavior (zoom/pan preservation, overlay/level reattachment) is reasoned through against the actual code and proven at the type level via a real `tsc -b`/`vite build`, not seen rendering in a live browser.
