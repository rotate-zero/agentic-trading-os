91. **Market State Engine's v1 shape locked: score-first representation, explicit per-symbol/cross-symbol split, SPY/QQQ/IWM pulled forward from Phase 5 scaffolding to the current build.** Three threads converged into one decision: Saqib's original concept (Market State watching SPY/QQQ/IWM "like symbols," Context handling calendar/news/economic factors/fundamentals/sectors) turned out to already be half-specified in `trading-intelligence-architecture.md` §4 as deferred Phase 5 scaffolding — not new architecture, but worth promoting to now rather than leaving on the shelf. Consulted-Chat review then proposed representing every Market State dimension as a bounded 0–100 score rather than a categorical tag, which both Saqib and Claude independently converged on as a real improvement, not just a stylistic preference.

    **Every Market State dimension is a `<dimension>_score`, 0–100, not a label — decision, not proposal.** `trend_score: 82`, not `trend: BULLISH`. **Scores are normalized state measurements, not probabilities or predictions** — `82` means "this dimension's current measured state sits at 82 on its own 0–100 scale," never "82% chance of X." 0–100 rather than 1–100 specifically so both ends of the scale are real, reachable values, not an awkward off-by-one. Directional dimensions (Trend, VWAP relationship) run bearish→bullish across the full range; magnitude-only dimensions (Volatility, Volume) run quiet→extreme with no bearish pole — the same numeric range means something different on each, and any future band mapping has to carry two shapes, not one.

    **v1 ships scores only — no bands, no tags, no duration-in-band, no confidence, no `previous`/`changed_at`.** The original duration/strength/confidence/previous shape (`trading-intelligence-architecture.md` §4, pre-existing) is the eventual destination, not abandoned — but duration specifically can't be defined against a raw score without wobbling on every recompute, and duration needs a classified band to key off, which doesn't exist yet. Rather than ship a half-working memory layer, v1 keeps only the rolling window already needed to compute **Acceleration** (a score's own rate of change over that window), promoted to its own peer dimension rather than staying a nested "Strength" sub-field the way the original shape had it. Full band/classification system deferred — `future-ideas.md` #22. **The score is the only thing ever persisted to `market_state_history`; a tag is always computed live from whatever the current band config says, never stored** — a stored tag would silently go stale the moment a boundary is retuned, a fourth versioning problem alongside `strategy_version`/`schema_version`/`data_version`/`feature_version`. Two independent reasons for this sequencing: band boundaries are a guess until real score distributions exist to set them from evidence, not assumption; a tag throws away exactly the information a score exists to preserve — 81 and 89 both round to `Bullish`, and nothing downstream can tell them apart once that happens. No overall/composite score across dimensions either — kept independent until real evidence shows combining them adds value, not before.

    **Per-symbol dimensions, v1:** Trend, Volatility regime, Volume regime, VWAP relationship, Session type, Acceleration — each an independent `<dimension>_score`, computed identically for any tracked symbol, including SPY/QQQ/IWM. `Market breadth` is removed from this list — it was never actually a per-symbol property, just mis-filed as one; full breadth (advancing/declining counts, universe-wide) is deferred, `future-ideas.md` #23. Participation is unaffected by any of this and stays exactly as blocked as before — Feature Engine still has no signed-volume/uptick-downtick raw signal to compute it from (`future-ideas.md` #13) — it joins the list above as another `<dimension>_score` once that signal exists, no design change needed.

    **Cross-symbol dimensions, v1 — kept deliberately small, no correlation matrices, no sector rotation engine, no full breadth.** SPY, QQQ, IWM tracked as always-on subjects, same Feature Engine → Market State pipeline as any other symbol, tighter `DebounceScheduler` ceiling (~3–5s vs. ~10s) since broad-market state is what everything else gets compared against. Each gets its own full per-symbol score set; Market State Engine synthesizes a small composite set on top: `spy_direction_score`, `qqq_direction_score`, `iwm_direction_score`, `trend_alignment_score`, `risk_on_score`, `qqq_leadership_score`, `iwm_confirmation_score`. Full shape in `trading-intelligence-architecture.md` §4. Composite state persists as a synthetic sentinel row (`symbol = "__MARKET__"`) inside the existing `market_state_history` mechanism — no new table, same reasoning `strategy_outcomes` already applies to live/backtest rows sharing one schema rather than two.

    **The four-part governing rule for the whole intelligence layer, added to `trading-intelligence-architecture.md` §2 itself so it doesn't drift:** *Feature Engine measures. Market State interprets. Context Engine describes the world outside the market. Strategy decides.* Synthesized from two near-identical formulations both Claude and consulted-Chat independently produced across this conversation — worth locking in exactly because two independent passes converged on the same four-part shape without coordinating on it.

    **One item explicitly still open, not resolved by this decision:** whether the restart-rebuild-from-history behavior the original §4 Implementation note locked in (rebuild duration on backend restart, don't reset to zero) still applies now that duration-in-band is deferred. v1's rolling window is short enough that a cold start on restart is treated as an acceptable simplification for now, not silently dropped — but the original restart decision was written before score-first existed and deserves a real re-look once bands actually get built, not an assumption that it still applies unchanged.

    **No application code in this entry** — same Stage-0 pattern as decisions #87–#90.

92. **Context Engine's M1 slice built — `ContextProvider` interface, `ContextEngine` aggregator, `ContextChanged` event schema, and `CalendarProvider`, the only provider buildable before M0's Finnhub spike results land.**

    **Scope, and why only this much.** M0's Finnhub spike scripts (`M0-SPIKE-NOTES.md`) haven't run against live keys yet — `FundamentalsProvider`'s `symbol_fundamentals` shape and `NewsFlagProvider`'s per-article-timestamp assumption both depend on those results, so both stayed out of this slice rather than being built against numbers that might still move. `CalendarProvider` has no such dependency — it wraps `MarketClock`, already built and tested — so it's the whole v1 provider list for now.

    **Two deliberate deviations from §5's original interface, both flagged rather than silently decided:**
    - `ContextProvider.evaluate()` drops the `market_state: MarketState` parameter the architecture doc specifies — `MarketState` is Market State Engine's (M2, not yet built) type, and typing this against a guessed-at shape risked exactly the kind of rework M0's providers are being held back to avoid. Goes back on once M2 exists and there's a real type to put there.
    - `ContextEngine`'s v1 trigger is a session-boundary loop (`MarketClock.next_session_boundary()`), not the `MarketStateChanged`-driven trigger §5's component table implies — `MarketStateChanged` doesn't exist yet either. `CalendarProvider` is the one provider whose own stated cadence ("changes on session/day boundaries," §5) matches this loop directly; `FundamentalsProvider`/`NewsFlagProvider` will likely want their own cadence-specific triggers rather than being forced onto Calendar's loop when they join, per §5's own "providers refresh at whatever cadence their underlying reality actually changes at" principle.

    **`CalendarProvider`'s Fed-day gap, closed.** `MarketClock` has holiday/session/half-day logic but no Fed-day awareness at all, despite §5 naming "Fed days" as part of this provider's job. Added as a small hardcoded 2026 FOMC-date set living in `CalendarProvider` itself, not `MarketClock` — same "small hardcoded set now, real calendar source before Phase 5+" scope note `MarketClock`'s own `_HOLIDAYS_2026` already carries, kept out of `MarketClock` because Fed-day-ness is Context's own question, not something session-mechanics callers (candle aggregation, VWAP) have any use for.

    **`ContextChanged` schema fixed to match decision #90, not the stale doc example.** `system-design.md` §10.3's `providers: {calendar, gap, levels, volatility_regime}` example predates #90's cut of `GapProvider`/`LevelsProvider`/`VolatilityRegimeProvider` — updated to `providers: {calendar: {...}}` in the same commit as the code, per the docs-and-code-together rule.

    **Where it's built:** `backend/app/context_engine/provider.py` (`ContextProvider` ABC), `backend/app/context_engine/engine.py` (`ContextEngine`, `get_context_engine()` singleton — same lazy-singleton pattern as `get_level_interaction_engine()`), `backend/app/context_engine/providers/calendar.py` (`CalendarProvider`), `backend/app/schemas/events/context.py` (`ContextChanged` payload — `EventType.CONTEXT_CHANGED` was already reserved in `envelope.py`, unused until now). Wired into `main.py`'s lifespan, unconditional start — `CalendarProvider` only touches `MarketClock`, no external API, so there's nothing to soft-fail on.

    **Shutdown ordering, one small departure from decision #47's precedent.** `LevelInteractionEngine` et al. stop AFTER the bus — they're `FeaturesUpdated` subscribers, and stopping the bus first bounds their drain to a fixed backlog instead of an ever-refilling queue (#47). `ContextEngine` is a pure publisher, not a subscriber, so it stops BEFORE the bus instead — nothing depends on draining a backlog, and stopping first avoids publishing into a bus already mid-shutdown.

    **Verified:** `pytest tests/test_calendar_provider.py tests/test_context_engine.py` (10 new tests, all pass) plus the full existing suite (208 passed, 65 skipped, 31 failed — all 31 pre-existing `psycopg2.OperationalError: Connection refused` failures in `test_daily_levels.py`/`test_feature_engine.py`/`test_scanner_universe.py`/`test_vwap_ext.py`, none of them files this change touched; this sandbox has no local Postgres, same DB-unavailable posture `test_level_interaction_engine.py`'s own skip-guard already documents). `python -c "import app.main"` confirms the new wiring imports cleanly. **Not verified: a real FastAPI startup, or these tests against a live Postgres** — re-run the full suite locally before treating this as fully clean.

93. **Market State Engine's M2 slice built — per-symbol only. `MarketState`/`MarketStateChanged` schema, `MarketStateEngine`, `market_state_history` migration, and four scoring functions plus Acceleration.**

    **Scope.** Per-symbol dimensions only — cross-symbol synthesis (`CrossSymbolState`, SPY/QQQ/IWM) is M3, not built here, and doesn't block this: this engine is generic over any tracked symbol and never asks whether Polygon/Finnhub serve SPY/QQQ/IWM cleanly, the still-open M0 question (`M0-SPIKE-NOTES.md`).

    **Two deviations from decision #91's six-dimension list, both answered directly rather than guessed at:**
    - `Session type` is dropped from this build entirely. Unlike the other four dimensions, it has no natural directional (bearish↔bullish) or magnitude (quiet↔extreme) reading — rather than force one onto it, it's left unbuilt: `app/market_state_engine/scoring.py` has no `session_type_score` function at all, not a stub. Flagged to revisit, not designed away permanently.
    - `Acceleration` ships scoped to Trend's own rate of change specifically, not one value per dimension (5 extra fields) and not an adaptive pick of whichever dimension moved most this window. Simplest reading of "a score's own rate of change" (§4) that still answers the classic momentum-acceleration question.

    **v1 scoring formulas** (`app/market_state_engine/scoring.py`), each a single already-available Feature Engine field through a calibrated clamp, constants explicitly flagged as adjustable defaults, not derived from real score distributions yet — same caveat §4 already makes about band boundaries generally:
    - Trend: `sma_20_slope_angle` (decision #83's arctan-normalized angle) → `clamp(50 + angle × 50/20°)`.
    - Volatility regime: `atr_14_pct` → `clamp((atr% − 0.3%)/(4% − 0.3%) × 100)`. Weakest of the four — "normal" ATR% varies a lot by symbol character, no per-symbol percentile history exists yet to calibrate against.
    - Volume regime: `rvol` → `clamp(rvol/3.0 × 100)`. Already relative by construction, so no separate baseline needed the way Volatility's is.
    - VWAP relationship: `(close − vwap)/vwap` → `clamp(50 + pct × 50/1.5%)`.
    - Acceleration: `(trend_score_now − trend_score_prev)/elapsed_seconds` → `clamp(50 + rate × 30)` — a full 0–100 trend swing within ~60s saturates. `None` on a symbol's first-ever recompute, not a fabricated neutral 50 — there's genuinely no rate to report yet.

    **Persistence architecture — decision #84 reused deliberately, not reinvented.** `DebounceScheduler.stop()` is a plain `task.cancel()` + `await task` (`app/core/debounce_scheduler.py`) — exactly the shape decision #84 diagnosed as unsafe for any callback doing a blocking `asyncio.to_thread` DB write, because cancelling the awaiting task doesn't stop the underlying thread-pool write, just detaches from awaiting it. #84's own write-up explicitly flagged this as "very likely" present in any engine sharing that shape — building a brand-new one with the same anti-pattern would have walked straight into an already-diagnosed bug. Fixed the same way LevelInteractionEngine already fixed it: each per-symbol `DebounceScheduler`'s callback here does ONLY a fast, synchronous, non-blocking queue put (no I/O), so its cancel-based `stop()` stays safe. A single background worker consumes that queue and owns all the real work (compute, the DB write via `asyncio.to_thread`, the publish), using the identical poison-pill drain `LevelInteractionEngine.stop()` established — enqueue `_STOP_SENTINEL`, await the worker with nothing cancelled, so an in-flight write is guaranteed to finish before `stop()` returns. Verified causally, not just by absence of a crash: the test wraps `_persist` with an artificial delay and asserts `stop()` measurably blocks for it (mirroring `test_level_interaction_engine.py`'s own version of this test almost exactly, including its fix for the same Bus-publish-then-immediately-stop race that made an early version of this test flaky for a reason already diagnosed there — fed the queue directly instead).

    **`EventBus` finding, incidental to this build but worth recording:** `EventBus._safe_call` (`app/event_bus/bus.py`) already awaits a coroutine-returning subscriber handler (`if asyncio.iscoroutine(result): await result`). `_on_features_updated` here is `async def` and calls `await scheduler.trigger()` directly — no fire-and-forget `asyncio.create_task` wrapping needed, unlike an earlier draft of this file. Safe because `trigger()`'s common path is a single non-blocking queue put, never I/O, so the per-lane serialization `_consume` imposes on awaited handlers doesn't become a bottleneck.

    **Rolling window:** the only history v1 needs is one prior `(trend_score, timestamp)` pair per symbol, for Acceleration — nothing longer. §4 is explicit that a cold start on restart is an accepted v1 simplification, not a gap this needs to help close. Held in `_prev_trend`, mutated only from inside the single worker task — no lock needed, unlike `LevelInteractionEngine`'s own state, because there's exactly one consumer processing the queue strictly serially.

    **Two stale doc spots, corrected in this change:** `system-design.md` §10.3's `MarketStateChanged` row still described the pre-score-first shape (`dimension`/`value`/`duration_seconds`/`strength`/`confidence`/`previous_value`/`changed_at`) — decision #91 superseded that before it was ever built. `models/trading_intelligence.py`'s module docstring claimed Market State Engine was "specified to" rebuild from persisted history on restart — also superseded by #91, which explicitly accepts a v1 cold start instead.

    **Where it's built:** `app/market_state_engine/scoring.py` (pure functions), `app/market_state_engine/engine.py` (`MarketStateEngine`, `get_market_state_engine()` singleton), `app/schemas/events/market_state.py` (`MarketState` payload — `EventType.MARKET_STATE_CHANGED` was already reserved, unused until now), `app/models/market_state.py` (`MarketStateHistory`, append-only — structurally `level_interaction_events`' role, not `level_interaction_state`'s), `alembic/versions/0005_market_state_history.py`. Wired into `main.py`'s lifespan — a `FeaturesUpdated` subscriber like `LevelInteractionEngine`, so it stops AFTER the bus in shutdown, not before like `ContextEngine` (decision #92's distinction; see that engine's own docstring).

    **Two real gaps found and fixed along the way, neither hypothetical — both surfaced by actually running the full suite against a live DB, not by inspection:**
    - `tests/conftest.py`'s singleton-reset fixture (the one decision #47 itself established, for exactly this class of problem) was never updated for `ContextEngine`'s singleton when #92 built it, or for this build's `MarketStateEngine` singleton either — pytest-asyncio's per-test event loop meant a cached instance's `asyncio.Queue`, bound to an earlier test's now-closed loop, threw `RuntimeError: ... is bound to a different event loop` the moment `test_intelligence_routes.py` ran a second test through the real app lifespan. Both singletons added to the fixture's reset list; retroactively closes a gap #92 left open, not just one from this build.
    - `market_state_history` is a new FK-referencing table, and `MarketStateEngine` subscribes to `FeaturesUpdated` globally the moment the real app lifespan runs — so `test_intelligence_routes.py`'s own test symbols now pick up rows here too, and its shared `_clean_test_symbol()` teardown (which already had this exact pattern documented for `daily_levels_state`) needed the same one-line addition before its `DELETE FROM symbols` or it hit a real `ForeignKeyViolation`. Fixed there, same convention.

    **One pre-existing flaky test found, confirmed NOT caused by this build, and deliberately left alone.** `test_sma_ema_slope_family_groups_under_the_owning_period_and_is_excluded_from_level_interaction` (and occasionally its neighbor) fails intermittently with varying error shapes (`KeyError`, or a `zone` assertion mismatch) depending on run timing. Isolated via a genuine before/after comparison, not assumed: a fully clean copy of the repo at this build's starting commit, with none of this session's changes present, reproduces the identical intermittent failure across repeated runs. Out of scope for this build — a pre-existing timing sensitivity in `test_intelligence_routes.py`/Level Interaction Engine's own test suite, not touched by anything in #92 or #93 — flagged here rather than silently worked around or silently ignored.

    **Verified:** `pytest tests/test_market_state_scoring.py tests/test_market_state_engine.py` (17 new tests, all pass) against a real local Postgres — installed in this environment specifically to close the "not verified against a live DB" gap decision #92 flagged, not skipped this time. `alembic upgrade head` applies cleanly through `0005`. A full FastAPI lifespan startup-and-shutdown was actually exercised end-to-end (`app.router.lifespan_context`), not just import-checked — logs confirm every engine starts and stops in the intended order, `ContextEngine` before the bus, `MarketStateEngine` after it, no warnings, no orphaned tasks. Full existing suite run against this same live Postgres (a real run, not the DB-unavailable skip decision #92's environment was limited to): 320 passed, 1 failed — the pre-existing flake described above, confirmed unrelated. **Not verified: this migration against a database that already has production data in it** — this environment's Postgres was created fresh for this session.

94. **M0's Finnhub Context Engine spike results locked — `FundamentalsProvider`'s TTM derivation method and Finnhub's real two-bucket rate-limit structure, both found empirically rather than assumed from documentation.**

    **Scope.** Closes M0 items #1 and #2 from the Market State + Context Engine build task list (`M0-SPIKE-NOTES.md`), the dependency decision #92 held `FundamentalsProvider`/`NewsFlagProvider` back on. Evidence gathered via `backend/scripts/check_finnhub_context_data.py` against a real Finnhub free-tier key, run repeatedly against AAPL/TSLA/NVDA/SPY as the script itself was corrected mid-session.

    **`/stock/profile2` and `/stock/financials-reported` both work cleanly for single-name stocks, and correctly return nothing for ETFs.** Confirmed against AAPL/TSLA/NVDA; SPY returns `{}` from profile2 and zero reports from financials-reported — expected, not an error, since ETFs file neither a company profile nor 10-Qs/10-Ks. `symbol_fundamentals`'s profile/financials fields should be left null for ETF symbols, never fabricated, per the project's existing honest-state-over-fabricated-state principle.

    **`financials-reported`'s quarterly figures are fiscal-year-to-date cumulative, not discrete 3-month values — found via a self-consistency check, not assumed from the schema.** The first sign: AAPL's and TSLA's four most recent "quarterly" revenues summed to 124% and 62% MORE than their own most-recent annual (10-K) revenue — structurally impossible for four genuinely discrete, non-overlapping quarters. A first hypothesis (a single 10-Q tagging both a discrete and a cumulative figure under the same XBRL concept, with the check's `_find_concept` dict lookup silently keeping the wrong one) was tested directly by dumping every raw occurrence for the most recent quarter — and refuted: zero duplicates found. The real mechanism, confirmed instead: each `/stock/financials-reported` line item IS the cumulative year-to-date figure as of that quarter's end, resetting at each new fiscal year (TSLA's raw revenue sequence shows this directly — 19.3B → 41.8B → 69.9B climbing through calendar 2025, then dropping to 22.4B the instant FY2026 starts).

    **Derivation method, validated against real numbers, not just derived theoretically.** For each of revenue/net income/operating cash flow: a fiscal year's first quarter is already discrete (nothing to subtract yet); each subsequent same-fiscal-year quarter's discrete value = its cumulative figure minus the previous quarter's cumulative figure; the fiscal year's final quarter (no standalone 10-Q exists — it's embedded in the 10-K) = the annual figure minus the last quarterly cumulative. TTM = sum of the 4 most recent discrete quarters this way, crossing a fiscal-year boundary when needed. Reconstructed AAPL revenue TTM = $451.4B (8.5% above FY2025's $416.2B annual — a sensible growth read, not an artifact); TSLA revenue TTM = $97.9B (3.2% above FY2025's $94.8B annual); AAPL net income TTM = $122.6B (9.4% above FY2025's $112.0B annual), checked as an independent second metric. Concept-tag consistency across quarters (same `us-gaap_` tag for revenue/net income/operating cash flow throughout) also confirmed for both symbols, so the lookup itself doesn't need per-symbol special-casing — only the cumulative-to-discrete derivation does.

    **Finnhub's 60-calls/min free-tier limit is actually two separate buckets by endpoint category, not one flat pool — confirmed with exact predictive math across four independent script runs.** `/stock/profile2` and `/stock/financials-reported` (any `freq`) share one 60/min bucket: pre-burst consumption against that bucket has matched `(profile2 calls) + (financials-reported calls, all freqs)` exactly every time, e.g. 9 pre-burst calls + 1 burst call → 60−10 = 50 remaining, observed 50. `/calendar/earnings` and `/company-news` share a second, separate 60/min bucket: 6 pre-burst calls + 1 burst call → 60−7 = 53 remaining, observed 53, same session. Practical effect: `FundamentalsProvider`'s refresh cadence competes with itself (profile + financials calls draw from the same pool) but not with `NewsFlagProvider`; `CalendarProvider` and `NewsFlagProvider` do compete with each other since both are already built/planned against the calendar/news bucket.

    **`/company-news` confirmed usable for `NewsFlagProvider`, with one real scope restriction.** Per-article `datetime` is a genuine unix-seconds timestamp (not just a calendar date), so `recency_seconds`/`count_15m` (decision #90's output shape) are derivable. But `/company-news` for an ETF ticker (SPY) returns generic broad-market news about unrelated single names, mislabeled `"related": "SPY"` (a sampled headline was about Nio and XPeng) — not fund-specific news. `NewsFlagProvider` should only ever be pointed at single-name Context symbols, never SPY/QQQ/IWM, or it will flag constantly on stories that have nothing to do with the fund.

    **Where the evidence lives:** `M0-SPIKE-NOTES.md` (now superseded by this entry as the authoritative record — written before any of the above results existed), `backend/scripts/check_finnhub_context_data.py`. Still Stage 0, no code — `FundamentalsProvider`/`NewsFlagProvider` implementation itself not started.

Daily bars over a 14-day window returned exactly the expected weekday count for all three (10 bars, no gap beyond ordinary weekends), zero zero-volume days, healthy and plausible volume ranges (SPY 27–46M, QQQ 20–37M, IWM 11–23M shares/day) and continuous price action.     **Finnhub's free-tier WebSocket trade feed is real but IEX-only, not the consolidated tape — confirmed via Finnhub's own documentation, not assumed.** `wss://ws.finnhub.io`'s trades stream is documented as "real-time last-price updates for US stocks (IEX), LSE, Forex and Crypto." IEX's own published Q2 2026 figures put its overall market share at 3.8% (4.7% intraday), and even for ETFs specifically — its strongest category — at "nearly 10% of intraday ETF volume." So even generously, roughly 90% of SPY/QQQ/IWM's true trading activity never reaches this feed.

    **This fully explains an otherwise-alarming live result, ruled out as a script bug first.** A 30-second live capture returned 47 trades for QQQ and zero for both SPY and IWM — surprising on its face, since SPY's own Polygon daily volume is *higher* than QQQ's. Real, uneven per-symbol IEX order routing in a short window is the only explanation that fits both the ordering evidence and the market-share numbers above.

    **Tick-rule signed volume is mechanically proven derivable from data already flowing through the system, with zero new external dependencies — but must be scoped and named as IEX-specific, not general market participation, given the above.** The QQQ capture's 47 trades classified cleanly into 14 upticks / 11 downticks / 21 unchanged against consecutive trade prices, with real (if sparse) condition-code data (`c` field) alongside — confirming the mechanism works end to end. But a signal built on a venue that sees ~10% of ETF volume, unevenly across symbols and short windows, is not a general participation measure — the same capture showing 47 real trades for QQQ against zero for SPY and IWM in the identical window is itself the demonstration. If this gets built: name it for what it is (e.g. `iex_signed_volume`, not a bare `signed_volume` implying full-market coverage) and prefer a longer aggregation window (1–5 minutes) over raw tick-by-tick, given the demonstrated sparsity even for the most liquid instruments in the market.

    **Participation's status is unchanged by this entry.** Still exactly as blocked as decision #91 left it — this documents what building it would need to account for once that trigger condition is met, not a decision to build it now.

96. **M1's remainder built — `symbol_fundamentals`, `FundamentalsProvider`, `NewsFlagProvider`, `FundamentalsRefreshJobs`, and decision #94's TTM math reimplemented as pure, tested functions.**

    **The architectural gap this surfaced, and how it's resolved.** `ContextProvider` (decision #92) is implicitly market-wide — `evaluate()` takes no symbol, `ContextEngine.evaluate_all()` publishes one `ContextChanged(symbol=None)`. That was never a problem while `CalendarProvider` was the only provider, but `FundamentalsProvider`/`NewsFlagProvider` are inherently per-symbol (§5 itself says "a symbol's recent headlines"), and nothing in §5 ever actually resolved how "one `ContextChanged` event" was supposed to work once some providers are global and others aren't. Resolved with a second interface, `SymbolContextProvider` (`evaluate(self, symbol) -> dict`), and a second aggregation method, `ContextEngine.evaluate_for_symbol(symbol)`, publishing its own `ContextChanged(symbol=X)` — `evaluate_all()` stays exactly as #92 built it, completely untouched.

    **The per-symbol trigger — confirmed directly, not guessed:** a 15-minute timer per tracked symbol, matching `count_15m`'s own window and sitting comfortably under decision #94's calendar/news 60/min bucket. `FundamentalsProvider` rides the same timer as `NewsFlagProvider` rather than getting its own — it's a cheap DB read with no reason to run on a different cadence. Symbols come from `scanner_universe_symbols`, snapshotted once at `ContextEngine.start()` — a symbol added to the universe afterward doesn't get a loop until a restart, a real v1 limitation, flagged rather than silently accepted.

    **`sector` is a real column, permanently `NULL` in this build.** Finnhub's `/stock/profile2` provides exactly one classification field (`finnhubIndustry`), not a separate sector-and-industry pair decision #90's schema assumed — not discovered by M0's spike, which only dumped raw profile output for a human to read, never parsed named fields out of it. Mapping the one available field into both columns would be fabricating a second dimension that doesn't exist in the source data — `industry` gets the real value, `sector` stays `NULL`, flagged here rather than silently duplicated.

    **NewsFlagProvider never calls `/company-news` for SPY/QQQ/IWM at all** — decision #94's finding that ETF tickers return generic broad-market news mislabeled as related, load-bearing immediately rather than a future concern: `SPY` is already in the seeded Scanner Universe (`app/scanner/universe.py`'s `TEST_UNIVERSE`). Guarded symbols get `present: false` unconditionally, never even make the API call, rather than calling it and discarding misleading results.

    **`importance`'s keyword list is an explicit first pass, not a validated one** — §5 itself calls this "a keyword/volume heuristic, explicitly not language understanding," so there's no correct list to look up. ~20 terms (`earnings`, `fda`, `lawsuit`, `bankruptcy`, ...), high on a keyword hit OR 3+ articles in 15 minutes, medium on 1-2 articles, low on presence outside the 15-minute window. Worth iterating on with real data.

    **TTM derivation (`app/context_engine/fundamentals_derivation.py`) reimplements decision #94's validated reasoning as pure, independently-testable functions** — M0's own spike script only had a diagnostic function, nothing clean enough to lift verbatim. Same candidate concept-tag lists and cumulative-to-discrete logic (a quarter's cumulative value dropping relative to the prior quarter is a structurally reliable fiscal-year-reset signal, not just a heuristic that usually works — standalone 10-Qs are always exactly 3-per-year, so a decrease between chronologically-adjacent quarterly reports can only happen at a rollover). **A real off-by-one bug was found and fixed during this build, before it ever touched real data:** the first implementation gap-filled a Q4 the instant it hit ANY reset-flagged quarter, even when three more real quarters were already available afterward and no gap-fill was needed at all — caught by a synthetic test shaped exactly like decision #94's own validated TSLA sequence (19.3B→41.8B→69.9B climbing, resetting to 22.4B), whose expected value was itself wrong in the same way on the first pass. Fixed properly: a Q4 gap-fill is only inserted when the collection would otherwise run out of quarterly history before reaching 4 discrete quarters, v1-scoped to at most one gap (a window needing two or more returns `None` rather than a guess).

    **The "gate financials refresh on `next_earnings_date`" idea from §5 was simplified away.** §5 originally proposed checking daily against `next_earnings_date` and only refreshing financials once a new filing was expected. Built instead: an unconditional daily `/stock/financials-reported` check for every tracked symbol, writing new TTM figures only when something newer is actually derived (a day where nothing changed just bumps `financials_updated_at`, per that column's own "last confirmed" semantics — never blanks out yesterday's good numbers with a failed derive). At 6 symbols × 2 calls/day this costs nothing against either of decision #94's buckets, and it's simpler than the original gate while landing on the same outcome. Flagged as a deviation from §5's stated design, not a silent substitution.

    **Persistence architecture reuses decision #84's cancellation-safety fix, same reasoning decision #93 already applied to Market State Engine.** `FundamentalsRefreshJobs` writes to `symbol_fundamentals` via partial UPSERTs but uses a plain `task.cancel()`-based `stop()`, not a poison-pill drain — deliberately, not an oversight: every write is a partial UPSERT of freshly-fetched data, not a checkpoint anything depends on being crash-consistent, so a cancelled mid-flight batch just gets re-fetched and re-written identically next run. `ContextEngine`'s new per-symbol path (`FundamentalsProvider`/`NewsFlagProvider`) is safe with a plain cancel for a different reason: neither does a write at all (nothing behind `NewsFlagProvider` is ever persisted, §5, and `FundamentalsProvider` only reads) — an orphaned in-flight read outliving cancellation is harmless, its result just never gets published.

    **A second real gap found and fixed, this one in the test suite itself.** `ContextEngine.start()`'s new per-symbol bootstrap unconditionally reads the Scanner Universe from the DB, even for callers that pass `symbol_providers=[]` — silently making four previously DB-free tests in `test_context_engine.py` DB-dependent for the first time, contrary to that file's own stated design ("fake providers so these tests don't depend on ... real-time behavior"). Caught by actually stopping Postgres and re-running the file, not by inspection. Fixed by monkeypatching `_load_scanner_universe_symbols` in the two `start()`-calling tests that don't exercise the per-symbol path; re-confirmed DB-free by re-running with Postgres stopped a second time. A related race was also closed proactively: `start()` spawns the bootstrap as fire-and-forget, so a `stop()` racing an in-flight bootstrap could previously miss tasks created after `stop()`'s own iteration over `_symbol_tasks` already began — fixed by having `stop()` cancel-and-await the bootstrap task itself first, before touching `_symbol_tasks` at all.
