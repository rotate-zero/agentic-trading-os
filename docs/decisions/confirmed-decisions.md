80. **Volume Bars opacity confirmed already shipped (decision #77, no change needed); the real bug behind Saqib's report was `useDropdownPlacement` inflating a settings panel's max-height past the actual viewport space in the chosen direction — fixed once, in the shared hook, closing it for every dropdown panel in the app at once.**

    **Volume Bars opacity — verified, not re-implemented.** Checked `VolumeBarsConfig` (`types/workspace.ts`), its `createDefaultVolumeBarsConfig()` and `WorkspaceContext.tsx` backfill, `volumeBarColor()` in `ChartWidget.tsx`, and the `SubWindowMenu.tsx` "Volume Bars" panel directly against a fresh pull, rather than assuming Saqib's report meant the feature was missing: `upOpacity`/`downOpacity`/`singleOpacity` are full first-class fields, wired through `ColorField`'s existing opacity slider (the same shared control every other color field uses, per decision #76), rendered via `hexWithOpacity()` at draw time, and backfilled for sessions saved before the fields existed. Nothing here needed building — it already matches every other color field in the app exactly.

    **Root cause, found by re-deriving what the report screenshot implied rather than guessing:** the screenshot showed a settings panel (Daily Levels, but Volume Bars' own panel is taller still — color-mode toggle plus two color+opacity rows plus a reset button) cut off flush against the bottom of a narrow viewport, with no scrollbar. `useDropdownPlacement` (decision #76) already measures real anchor position and caps `maxHeight` to the genuine remaining space — but its floor, `Math.max(spaceBelow, MIN_USABLE_HEIGHT)` / `Math.max(spaceAbove, MIN_USABLE_HEIGHT)`, was inflating that cap to 160px whenever the true remaining space was smaller, e.g. on a short/narrow viewport where an anchor sits close to both screen edges at once. `overflow-y-auto` only produces a scrollbar when a panel's own content exceeds ITS max-height box — it does nothing when the panel's max-height itself was set larger than the space actually available, which is exactly what an inflated floor does: the panel gets positioned partly past the visible viewport, the browser window's edge clips it first, and no scrollbar ever appears. This is the same failure mode decision #76 already diagnosed once, reintroduced by its own floor value in the one case (both directions under `MIN_USABLE_HEIGHT`) it hadn't been checked against.

    **Fix, in the one shared hook, not per-panel:** `MIN_USABLE_HEIGHT` (160px) now only decides WHICH direction to open in — it no longer floors the returned `maxHeight`. The returned value is always `Math.max(spaceBelow, 0)` or `Math.max(spaceAbove, 0)` — the real measured space, never inflated past it. Because `useDropdownPlacement` is shared by `SubWindowMenu.tsx`, `LayoutsMenu.tsx`, `GridPicker.tsx`, and `FeatureEnginePanel.tsx`'s ticker search (all four already wire its `maxHeight` into `style={{ maxHeight: placement.maxHeight }}` alongside their own `overflow-y-auto`, confirmed by re-reading each), this one change gives every long settings panel in the app — Volume Bars, Daily Levels, and anything added later — a working scrollbar on short/narrow viewports, not just the two panels in the report.

    **Docs housekeeping done in the same change, per decision #79's own maintenance rule, not a separate ask:** `confirmed-decisions.md` had grown to 105,956 bytes (past the ~100KB size trigger #79 itself set) by the time this entry was ready to append. Rolled over per that rule: `confirmed-decisions.md` (#61–#79) moved verbatim to `archive/061-079.md`, a fresh open file started, and this entry is the first one in it. `INDEX.md`'s file-location column updated for #61–#79 in the same change.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies here (same as decision #78's precedent for a doc/frontend-only change). **Not verified: an actual browser at the narrow viewport width from the report** — same standing gap flagged on every panel-affecting change so far; the fix is derived from re-reading `useDropdownPlacement`'s own math against the reported symptom, not confirmed by reproducing the clipped view and watching it resolve.

81. **Name half of an axis label ("PDH", "SMA 9", "VWAP") gained its own on/off toggle — `showNameLabel` — separate from the existing price-value toggle (`showPriceLabel`), on both `PriceIndicatorInstance` (SMA/EMA/VWAP) and `HorizontalLevelInstance` (PDH/PDL/PMH/PML/Camarilla/VPOC).**

    **The bug, confirmed against Lightweight Charts' own issue tracker rather than assumed:** for an overlay indicator (a Line series — SMA/EMA/VWAP), `lastValueVisible` (`showPriceLabel`) only ever hides the VALUE half of the price-scale label. The library's own maintainers confirm `title` renders unconditionally whenever it's a non-empty string, with no flag of its own to gate it — so unchecking "Show price tag" for SMA 9/20/50 (Saqib's report, screenshot 1) hid the number but left the name badge floating on the axis with nothing attached to it. Not a rendering glitch on this app's side — a real gap in what the two existing fields could express, closed by giving the name half a field of its own.

    **Two different renderer shapes, so two different fixes, not one:** overlay indicators are Line series with independently-settable `title`/`lastValueVisible` — decoupling them was a straight wiring fix in `ChartWidget.tsx`'s indicator effect: `title` now resolves to `""` when `showNameLabel` is off, instead of `ind.label` unconditionally. Horizontal levels (PDH/PDL/etc.) are `createPriceLine` price lines, where `title` and `axisLabelVisible` already draw as ONE combined tag — there's no equivalent library-side bug there. `showNameLabel` on `HorizontalLevelInstance` only drops the name prefix from that combined tag ("PDH 494.86" becomes "494.86"); `showPriceLabel`/`axisLabelVisible` still owns whether the tag shows at all, same as before this field existed. A genuine "name only, no price" mode for price lines isn't offered — Lightweight Charts has no per-price-line way to suppress just the numeric half while keeping `axisLabelVisible` on, and building one would mean replacing the native price-line label with a custom-drawn one (the `rectBoxes` div-overlay pattern this file already uses for rectangle objects) — out of scope for what the report asked for, flagged here rather than silently narrowed.

    **Where it's wired:** `types/workspace.ts` — new field on both instance types, defaulted `true` in `createPriceIndicatorInstance`/`createHorizontalLevelInstance` (matches the always-on behavior every existing session was already rendering). `utils/indicators.ts` — threaded through both `computePriceIndicator` (all three SMA/EMA/VWAP branches, backend and local) and `computeHorizontalLevel`. `ChartWidget.tsx` — both rendering effects (indicator Line series creation/update, and the horizontal-levels price-line effect) resolve the actual `title` string from the new flag instead of passing the label straight through. `SubWindowMenu.tsx` — a "Show label" checkbox added directly under "Show price tag" in both `OverlayIndicatorRow` and `HorizontalLevelRow`, same checkbox styling and placement pattern as every other toggle in those rows. `WorkspaceContext.tsx`'s `normalizeSubWindow` backfills `showNameLabel: true` for `priceIndicators` and `horizontalLevels` on sessions saved before this field existed, same partial-cast treatment `showPriceLabel`/opacity already get there — a session missing the field keeps showing the name badge exactly as it always did, rather than the badge silently disappearing on next load.

    **Deliberately not touched:** Volume Avg lines and Daily Levels also render via `createPriceLine` with their own `showPriceLabel`/`showPriceLabels`, but neither was in the report (screenshot 1's pink box circles only the SMA/VWAP/PDH/PDL tags), so they were left alone rather than folded in speculatively — same "don't write unrelated modules" boundary this project has held to on every prior report-driven change.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies here. **Not verified: an actual browser** — same standing gap every panel/chart-affecting change in this log has flagged; the fix is derived from re-reading Lightweight Charts' own documented `title`/`lastValueVisible`/`axisLabelVisible` behavior against the reported symptom, not confirmed by reproducing the floating badge and watching it resolve.

82. **The `showNameLabel` toggle from #81 extended to the two indicator types deliberately left out of it — Volume Avg lines (`VolumeAvgLineConfig`) and Daily Levels (`DailyLevelsConfig`) — so every label-bearing indicator on the chart follows the same convention, not just SMA/EMA/VWAP/PDH/PDL.**

    **Why #81 stopped short, and why that turned out to be the wrong call:** #81 scoped itself to exactly what screenshot 1's pink box circled (PDH/PDL/VWAP/SMA), reasoning that pulling in Volume Avg lines and Daily Levels too would be scope creep beyond the report. Saqib's own framing of the ask — "make this labels as an option just like price label is an option" — reads as a request about the *concept* (every indicator's name should be toggleable, the same way every indicator's price already is), not specifically about the four indicators visible in one screenshot. Deferring the other two was narrower than what was actually being asked for; corrected here on direct request rather than left as a judgment call.

    **Same mechanism as #81, no new pattern introduced:** both types already render via `createPriceLine` (same primitive as `HorizontalLevelInstance`), so this is the identical `title`-resolves-from-a-flag change, not a new design. `VolumeAvgLineConfig` gets `showNameLabel: boolean`, defaulted `true` in all four of `createDefaultVolumeAvgConfig()`'s hardcoded lines. `DailyLevelsConfig` gets `showNameLabels: boolean` (plural, matching its existing `showPriceLabels` naming — Daily Levels' fields have always been plural since one config fans out to many levels at once, unlike the other three types where one config is one line), defaulted `true` in `createDefaultDailyLevelsConfig()` — deliberately *not* matching `showPriceLabels`' own `false` default there, because the `"DL-N"` strength tag (not the price number) is Daily Levels' own documented primary way strength reads visually; defaulting names off too would have silently removed that on every existing session, not just made it optional.

    **A real gap surfaced while wiring `DailyLevelsConfig`, worth being upfront about:** re-reading Lightweight Charts' own shipped type declarations (`node_modules/lightweight-charts/dist/typings.d.ts`) while doing this, `PriceLineOptions.axisLabelVisible` and `.title` are documented as two independently-scoped things — `axisLabelVisible` governs only "the current price value... on the price scale," `title` is described as rendering "on the chart pane." That's a different, more permissive relationship than #81 assumed for `HorizontalLevelInstance` (that they draw as one fused tag, so a genuine "name only, no price" mode wasn't offered there). If the type declarations are accurate, "name only, no price" may actually work for all three `createPriceLine`-based types (`HorizontalLevelInstance`, `VolumeAvgLineConfig`, `DailyLevelsConfig`), not just the "drop the prefix, keep the price" version #81 shipped and described as the limit. **Not verified in a real browser** — this environment has no working browser (no snap/chromium connectivity — confirmed by attempting the install, not assumed), so this is read from the library's own shipped declarations, not confirmed by watching the label actually render. Flagging rather than either quietly upgrading #81's description or quietly leaving it uncorrected.

    **Where it's wired:** `types/workspace.ts` — new field on both types, defaulted `true` in both factory functions. `ChartWidget.tsx` — the `volumeAvg` price-line effect and the Daily Levels price-line effect both resolve `title` from the new flag the same way #81's two effects already do. `SubWindowMenu.tsx` — `VolumeAvgLineRow` gets a "Show label" checkbox under "Show price tag," matching #81's checkbox exactly. The Daily Levels panel gets a "Show "DL-N" label" toggle matching its own existing highlighted-button style (not a checkbox — Daily Levels' panel doesn't use checkboxes anywhere else, so a checkbox here would've been the inconsistent choice, not the button). `WorkspaceContext.tsx`'s `normalizeSubWindow` backfills both new fields to `true` for sessions saved before they existed, same partial-cast pattern as everywhere else in that function.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies. **Not verified: an actual browser** — same standing gap as #81, for the same reason (no browser available in this environment).
