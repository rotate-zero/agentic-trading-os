### 134. Backtest Panel and Backtest Results Panel linked by shared run_id — no more copy-paste

Both `BacktestPanel.tsx` (decision #131's frontend, the trigger) and `BacktestResultsPanel.tsx` (decision #133, the viewer) already worked independently; `useBacktestOutcomes.ts`'s own docstring named the gap explicitly ("triggered from a separate, unlinked panel per this task's own scope, so a manual refresh is the only way to see a just-finished run's rows"). This closes exactly that connection. Frontend-only — no backend/API change, no new route, no wire-shape change.

New shared state: `WorkspaceContext.tsx`/`MainWindowState.lastBacktestRunId` (`string | null`) + `setLastBacktestRunId`, modeled directly on `featureEnginePanelSymbol`'s own established "one panel writes, a sibling reads" pattern (decision #48) rather than a new mechanism (no new context, no event bus, no prop drilling through `App.tsx`). Scoped per-Main-Window, same as `featureEnginePanelSymbol`, since both panels are mounted once per active-window shell (`App.tsx`), not globally or per-sub-window — each Main Window tab tracks its own "most recent run." Persisted via the existing session-autosave path like every other `MainWindowState` field; `normalizeMainWindow()` back-fills `lastBacktestRunId: w.lastBacktestRunId ?? null` for sessions saved before this field existed, same convention `normalizeSubWindow()` already uses for its own fields.

`BacktestPanel.tsx`'s `BacktestForm` calls `setLastBacktestRunId(result.run_id)` in a `useEffect` keyed on `status === "done" && result` — the exact same moment it already renders that value in `ResultsView`, not a separate action. A plain, non-interactive note ("→ prefilled ... in the Backtest Results panel") was added next to the rendered run_id instead of a clickable "View in Results" link: the Results panel's own collapsed/width state is deliberately local component state, not threaded through `WorkspaceContext.tsx` (that panel's own header comment, unchanged by this decision) — making the run_id notification "actionable" would mean either reversing that local-state design for a convenience this task didn't ask for, or inventing a second, narrower coupling beyond the one piece of state this decision actually needed. Automatic prefill alone was judged sufficient; both options were explicitly defensible per this task's own scope.

**The one real design decision this task called for, stated explicitly rather than defaulted:** `lastBacktestRunId` is a DEFAULT for the Results panel's filter, never a forced value, and a run finishing elsewhere must never silently overwrite an in-progress manual lookup. Resolved with a small two-state mode machine local to `BacktestResultsBody`: it starts in `"auto"` (seeded from whatever `lastBacktestRunId` already is at mount, then continuously re-synced via a `useEffect` keyed on `[lastBacktestRunId, mode]`) and switches to `"manual"` the instant the person clicks Apply OR Clear — both are real, deliberate manual choices (Clear's own "show everything" is itself a choice, not a reset back to auto) — after which further runs finishing elsewhere update the shared value (so `BacktestPanel.tsx`'s own "prefilled" note stays true) but never touch this panel's own filter again. A small explicit "↺ Follow latest run" control is the only way back to `"auto"`; collapsing/re-expanding the panel would also reset it (the component unmounts on collapse) but isn't a discoverable way to ask for that, so the explicit control was added rather than relying on the side effect.

A useful, unplanned side effect: `useBacktestOutcomes.ts`'s own `[limit, backtestRunId]` dependency array was already reactive before this task and needed no changes — so once `"auto"` mode syncs `appliedRunId` to a newly-finished run, the hook's existing refetch logic fires on its own. Since `POST /backtest/run` is fully synchronous and only resolves after its own `StrategyOutcome` rows are already written (decision #128), this means the "manual refresh is the only way to see a just-finished run's rows" half of the original gap is *also* closed while a person is auto-following — not just the copy-paste half this task was framed around. Manual "Refresh" remains meaningful outside that path (a run triggered from a different tab/operator, or while pinned to a different run_id manually) — `useBacktestOutcomes.ts`'s own docstring updated to state this precisely rather than leave the now-stale "only way" framing in place.

Docs: `useBacktestOutcomes.ts`'s docstring corrected (see above). `strategy-engine-design.md` §7 gained one new as-built note with two diagrams — cross-component data flow (`BacktestPanel` → `WorkspaceContext` → `BacktestResultsPanel`) and the internal auto/manual mode state machine inside `BacktestResultsBody` — per this task's own diagram requirement.

### 135. Closed the historical-provider gap in Backtest Runner replay — `volume_regime_score`/`volatility_regime_score` were structurally always `0.0` in any replay, for any symbol; four of the seven v1 strategies (ORB, Gap, Volume Spike, Momentum) hard-gate MATCH on `volume_regime_score >= 45.0` and could never fire in a backtest as a result.

Named directly in decision #128's own diagram and restated in `scenarios.py`'s own module docstring as a real, confirmed-by-direct-execution ceiling, not a hypothetical. Root cause: `FeatureEngine`'s Daily Levels/ATR/RVOL refresh (`_maybe_refresh_daily_levels`) reads `self._daily_candle_cache`, populated exclusively via `broker_registry.get_historical_provider().get_historical(symbol, "1d", ...)` — a process-wide global `BacktestRunner` never touched, so this cache never populated during any replay, structurally, regardless of how a scenario's own candles were built.

    **The one real fork, presented to Saqib rather than resolved silently, with a recommendation and reasoning.** Two structurally different seams were possible: (1) a save/install/restore seam on `broker_registry`'s historical role, mirroring `engine_singleton_guard.py`'s already-accepted shape exactly, touching zero core engine files; or (2) a new optional constructor parameter on `FeatureEngine` itself, additive at the call-site level but requiring edits to `feature_engine/engine.py` AND `replay_state_producer.py` (which constructs `FeatureEngine` directly, with no such parameter today). Recommended (1), with reasoning checked against the real code rather than assumed: grepped every real call site of `broker_registry.get_historical_provider()` outside `feature_engine/engine.py` itself — exactly three, two of which are identity-comparison-only reads (`main.py`/`market_data.py`), and one real live-facing read (`GET /market/candles`, `market.py`), which gates on `adapter.is_connected()` before ever calling `get_historical()`. Since `FeatureEngine` itself never checks `is_connected()` (only `is None`), and the installed seam deliberately never calls `.connect()`, that live route keeps returning its existing honest 400 throughout a backtest run — no silent fixture-data leak, by construction. Decision #132's Finnhub/Polygon 409 already means `broker_registry`'s historical role is unclaimed going into every valid backtest run today. Saqib confirmed: go with (1).

    **A second, genuinely separate finding surfaced during this same investigation, also presented rather than resolved silently, with three concrete options and a recommendation.** Confirmed by direct execution against a real Postgres, not assumed: `_maybe_refresh_daily_levels()`'s real, unmodified `_reconcile_and_persist_daily_levels()` — reachable for the first time ever once ANY historical-provider seam exists, regardless of which of the two fork options above — writes real rows into the SAME shared `symbols`/`daily_levels_state` tables live trading reads, under whatever `symbol` label the caller supplies to `POST /backtest/run`, with no `is_backtest` flag on either table (unlike `strategy_outcomes`/`backtests`). Concretely: a second run against the identical `(symbol, scenario)` pair silently reverts `volume_regime_score`/`volatility_regime_score` to `0.0` for that run, since `_maybe_refresh_daily_levels()`'s own pre-existing "restart-survival" short-circuit finds the first run's persisted row and skips the raw-candle-cache population before ever asking the provider again — proven directly: RUN1 showed 119/119 `market_state_history` rows with non-zero scores, RUN2 (same symbol, same scenario, immediately after) showed 0/119 non-zero for its own rows. Three options presented: (a) accept and document loudly, (b) have `BacktestRunner` clean up the rows it caused in a `finally`, (c) flag as a new open item and ship (a) only. Recommended (a) + flag as a new D-item, given this session's own scope is "close the historical-provider gap," not "namespace backtest writes into shared live-trading state." Saqib confirmed: go with it. Documented prominently in `backtest.py`'s own route docstring (the disclosure a caller actually needs before picking a `symbol` label) and as new open item **D18** in `strategy-engine-design.md`'s D-items table — not resolved here.

    **Implementation.** New `backend/app/backtest_runner/historical_provider_guard.py` — `install_replay_historical_provider()`, an async context manager mirroring `engine_singleton_guard.py`'s save/install/restore shape exactly, own `asyncio.Lock`. New `backend/app/backtest_runner/fixture_daily_history.py` — `build_daily_history_candles()`, a deterministic, honestly-synthetic 20-trading-day daily history (15 genuinely needed: `feature_engine_atr_period + 1`; 5 for `feature_engine_rvol_lookback_days`; both confirmed by reading `atr.py`/`rvol.py` and their real callers directly, not assumed), walked backward using `MarketClock`'s own weekday/holiday logic, timestamped at real NYSE close via `ZoneInfo("America/New_York")` (DST-safe). One shared dataset regardless of symbol or named scenario, anchored to the scenario's own start date — mirroring `FixtureBacktestContextProvider`'s own "same synthetic facts regardless of which symbol" precedent, extended one step further. `fixture_provider.py`'s `FixtureCandleProvider.get_historical()` timeframe guard widened from `"1m"`-only to `{"1m", "1d"}` — confirmed by grep across `app/` that these are the only two timeframes any real code in this codebase ever requests from a historical-role provider. `backtest.py`'s route now builds both `(symbol, "1m")` and `(symbol, "1d")` entries into one `FixtureCandleProvider` instance, which serves both the replay's own candle feed AND (via `BacktestRunner.run()`, nested inside the existing `install_replay_engines()` block) the temporary `broker_registry` historical role. `scenarios.py`'s module docstring corrected — the "hard ceiling" is now historical, restated accurately with the checked-not-assumed per-strategy findings below.

### 136. `GET /intelligence/backtest-runs` — the `backtests` table's first reader, since decision #128 started writing real rows to it.

Every real backtest run since #128 has written a real row — `run_id`, `sweep_id`, `strategy_name`, `strategy_version`, `config_hash`, `symbol_universe`, `date_range_start/end`, `data_version`, `feature_version`, `walk_forward_fold`, `is_holdout`, `created_at` — and, before this delivery, not one of those rows had ever been read back by anything. `GET /strategy-outcomes?backtest_run_id=X` (decision #130) shows what a run *produced*; nothing showed a run's own metadata without already having kept its `run_id` from a prior `POST /backtest/run` response.

    **Route, filters, response shape — all discussed with Saqib before writing any code.** `GET /intelligence/backtest-runs` in `app/api/routes/intelligence.py`. `limit` (default 50, capped at 500, matching `/strategy-outcomes`'s own default/cap exactly), newest-first by `created_at` (`backtests` has no `exit_filled_at`-equivalent field; `created_at` is this table's own natural recency ordering). Three optional exact-match filters, AND-combined, never blended: `strategy_name`; `sweep_id` (`BacktestRun.sweep_id`'s own documented purpose — "groups every run belonging to the same grid-search session"); and `run_id`, added after discussion — the direct answer to this route's own motivating gap above: once a caller has a `run_id` (e.g. from a `POST /backtest/run` response, or eventually from `WorkspaceContext.tsx`'s `lastBacktestRunId`, decision #134), this is how that run's own metadata gets resolved without needing to have kept the original HTTP response around. `run_id` and `sweep_id` are real UUID columns; a malformed value for either is a 400 (`"... is not a valid UUID"`), the same posture `/strategy-outcomes` already takes for a malformed `backtest_run_id` — a silently-empty result would look identical to a genuinely-empty match and shouldn't. Response reuses the existing `schemas.performance.BacktestRun` Pydantic contract as-is (`model_validate(row, from_attributes=True)`) — not reshaped — and is wrapped `{"backtest_runs": [...]}`, matching this file's own envelope-naming convention (`outcomes`, `hourly_win_rates`, `session_expectancy`).

### 140. D18 resolved — live/backtest namespaces isolate replay persistence for the same ticker

Decision #135's historical-provider seam made Daily Levels/ATR/RVOL work during replay, but also exposed D18: a backtest using a real ticker wrote through the same `symbols` and `daily_levels_state` identity live trading used. Reproduced the mechanism standalone before touching any app code (mirroring decision #84's own verification method): a worker loop wrapping a real blocking call in `asyncio.to_thread`, cancelled mid-flight, returns in ~0ms while the real work keeps running detached — versus a poison-pill drain, which genuinely blocks until the real work finishes.

This is the concrete mechanism behind this file's own already-documented "async-timing race in Feature Engine cold-start backfill" lead: `FeatureEngine`'s worker loop does an UNCONDITIONAL `asyncio.to_thread` DB read (`_load_confirmed_daily_levels_for_today`, part of `_maybe_refresh_daily_levels`'s restart-survival check) on literally every never-before-seen (symbol, day) — independent of whether Daily Levels is even relevant to the test — and with `nproc=1` in this sandbox, the default `ThreadPoolExecutor` has only ~5 worker slots. Orphaned to_thread work surviving past a supposedly-clean `stop()` from an earlier test's engine instance can queue up behind a later test's own `asyncio.to_thread` calls, defeating a short fixed sleep — exactly the shape of bug already corroborated for the LevelInteractionEngine case in #84, just never closed for these two.

**Fix applied — the same, already-proven pattern #84 already shipped for the third engine, applied to the two it named:** `CandleRecorder.stop()` and `FeatureEngine.stop()` both converted from cancel-based shutdown to poison-pill drain — a `_STOP_SENTINEL` object enqueued onto the SAME queue the worker loop already reads, with `stop()` no longer calling `.cancel()` at all. Because the queue is strict FIFO, the sentinel is only ever dequeued after everything genuinely ahead of it — including an item already mid-`to_thread` — has fully finished. No timeout-then-cancel fallback, deliberately, matching #84's own explicit trade-off: correctness over shutdown latency for a background DB reader/writer.

**Two new deterministic regression tests added**, mirroring decision #84's own `test_stop_waits_for_an_in_flight_persist_before_returning` exactly:
- `test_candle_recorder.py::test_stop_waits_for_an_in_flight_write_before_returning`
- `test_feature_engine.py::test_stop_waits_for_an_in_flight_compute_before_returning`

Both wrap the real thread-offloaded method with an artificial delay, feed one item directly onto the engine's own internal queue (publishing through the Bus and immediately calling `stop()` was tried first and found to itself be flaky — the sentinel can race the real item into the engine's queue ahead of it, same lesson #84's own test docstring already recorded), then assert `stop()` blocks for close to the real delay AND that the work genuinely completed (no `ForeignKeyViolation` on an immediate `DELETE`, for the recorder; a real `FeaturesUpdated` event, for the engine). Verified in both directions, not just that they pass: reverted each `stop()` to the old cancel-based pattern and confirmed each new test fails deterministically (3/3, ~0.0000s elapsed each time) against it, then restored the fix and confirmed 3/3 passes.
