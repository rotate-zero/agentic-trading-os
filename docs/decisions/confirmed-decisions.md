# Confirmed Decisions

**Extracted from:** `../architecture/system-design.md` §9 (original numbering preserved for continuity with any existing references).
**Companion documents:** [`../architecture/system-design.md`](../architecture/system-design.md) (how it's built), [`../architecture/trading-intelligence-architecture.md`](../architecture/trading-intelligence-architecture.md) (how it thinks), [`future-ideas.md`](./future-ideas.md) (deferred, not rejected), [`../roadmap/phase-roadmap.md`](../roadmap/phase-roadmap.md) (when things ship).

This is the running log of settled architecture decisions — the "why did we choose X" record, kept in one place instead of scattered as inline asides across growing documents. **New confirmed decisions get appended here, numbered sequentially, as part of the same change that makes them** — not batched up and written after the fact.

1. **Broker order of implementation — REVISED.** Originally Alpaca first, then IBKR (simpler auth). Revised: **IBKR only, for now.** Alpaca requires a US-eligible account and isn't directly open to Bangladesh-resident account holders — this isn't a technical preference, it's an account-opening constraint, so there's no "try Alpaca first" path available. Not building an `AlpacaAdapter` stub for later — per `future-ideas.md`'s own discipline, that's speculative until there's an actual account to connect it to. Revisit if that constraint changes. (`../roadmap/phase-roadmap.md`, Phase 3)
2. **Candle storage** — plain PostgreSQL with native monthly partitioning for v1. TimescaleDB is deferred, revisited only once multi-timeframe backtesting at scale is a real, not hypothetical, requirement — since it's an additive extension, deferring costs nothing later. (`../architecture/system-design.md` §6.1, §4.13)
3. **Scanner cadence** — variable, config-driven schedule keyed to session windows (tight at open/close, sparse midday) rather than a fixed interval. (`../architecture/system-design.md` §4.7)
4. **Redis** — skipped for v1. Revisit if/when agents move to separate processes. (`../architecture/system-design.md` §6)
5. **Context Engine is a composed aggregator**, not a monolithic module — one provider per context question, so growth (news, OPEX, breadth, sentiment) means adding a provider, not editing a growing conditional block. (`../architecture/trading-intelligence-architecture.md` §5)
6. **Governor's decision schema is widened now, implemented narrow.** `GovernorDecision` supports `approved | approved_reduced | delayed | watch_only | rejected`; v1 rule logic only ever produces `approved`/`rejected`. A schema change now avoids a breaking change to every downstream consumer later. (`../architecture/trading-intelligence-architecture.md` §12)
7. **World View is a read-only composite facade**, not a shared mutable world model. Assembles Market State + Portfolio State + Context + Performance Intelligence for consumers that want the whole picture at once (debug tooling, a future LLM reasoning layer). No write path, no state of its own — single-writer-per-domain stays intact. (`../architecture/trading-intelligence-architecture.md` §15)
8. **Event data contracts are formalized before Phase 1 code**, not discovered along the way. (`../architecture/system-design.md` §10)
9. **Event Bus dispatch is two-lane, not multi-tier priority.** Execution-critical events (`OrderFilled`, `PlanRejected`, `GovernorDecision`, `OrderApproved`) get an isolated dispatch lane so they're never delayed behind market-data volume; everything else shares one normal lane. A general N-tier priority framework was considered and rejected as complexity without demonstrated need at this scale (single process, ~100-symbol universe, Scanner-narrowed to a handful). (`../architecture/system-design.md` §4.4)
10. **Stateful engines that need periodic-but-not-constant recompute (Market State Engine, Position Monitor) use a shared `DebounceScheduler` utility** — event-triggered, with a minimum interval (don't recompute more than once per N seconds) and a maximum interval (recompute at least once every M seconds even if nothing changed). Same pattern already used for Scanner cadence and Strategy triggers, implemented once and reused rather than each module inventing its own timer logic. Feature Engine, Governor, and Execution Engine do **not** use this — they react to every event with no debounce, since staleness there is either wrong indicator values or a safety issue. (`../architecture/system-design.md` §8, `core/debounce_scheduler.py`)
11. **`docs/` is the authoritative location for all architecture and design documentation**, organized into `architecture/`, `decisions/`, `diagrams/`, `roadmap/`, and `api/` subfolders. Implementation code stays separate from documentation. Any future architecture change updates the relevant document(s) here as part of the same change that makes the change — not a follow-up task. (`../README.md`)
12. **Partition-boundary literals in migrations must carry an explicit UTC offset (`+00`), never a bare date.** Found via a real local-Postgres run: a bare `'2026-07-01'` literal in `CREATE TABLE ... PARTITION OF` gets interpreted using the DB session's local `TimeZone` setting at migration-run time, not UTC — so the same migration produces a different physical partition boundary depending on who/where runs it (observed: a session with `TimeZone=Asia/Dhaka` produced a boundary six hours off from intended UTC midnight). Fixed in `0001_initial_symbols_and_candles.py` by writing boundaries as `'2026-07-01 00:00:00+00'`. Applies to every future partition-seeding migration, not just this one.
13. **Use `ib_async`, not `ib_insync`, for the IBKR adapter.** `ib_insync`'s original author passed away in 2024 and the library is unmaintained. `ib_async` (github.com/ib-api-reloaded/ib_async) is the community-maintained, API-compatible successor — verified by installing it and introspecting real method signatures (`connectAsync`, `reqHistoricalDataAsync`, `reqMktData`, `placeOrder`, `cancelOrder`, `positions`) rather than trusting training-data memory of the older library. `system-design.md` §6's tech stack table is corrected to match.
14. **IBKR 2FA: switch to IB Key, not SMS; Gateway set to auto-restart, not auto-logoff.** Verified against IBKR's own automation tool (IBC)'s documentation: unattended login with *zero* human interaction isn't possible for any 2FA method — IBC can fill in username/password, but the 2FA step still needs either a typed code or a tap in the IBKR Mobile app. Switching from SMS to IB Key (push notification + biometric/passcode tap) replaces "type a code into a script" with "tap approve on your phone," and combining that with Gateway's auto-restart setting (vs. auto-logoff) reduces how often that tap is needed to roughly once a week instead of once a day. This is a real reduction in friction, not a full bypass — don't oversell it as "headless" in any documentation or code comments referencing this.
15. **`BrokerAdapter`'s `Tick` type includes `symbol`, distinct from the Event Bus's `PriceUpdated` payload (which omits it).** Found while implementing `IBKRAdapter`: `on_tick(callback: Callable[[Tick], None])` (§4.1) passes only a `Tick` to the callback, with no separate symbol argument — but a single adapter instance serves many subscribed symbols, so `Tick` itself has to carry `symbol` for the callback to be usable. `PriceUpdated` (the Event Bus payload) deliberately omits `symbol` because the `EventEnvelope` carries it instead (§10.1) — reusing it directly for `Tick` would have silently dropped symbol identification. `app/broker_adapters/base.py`'s `Tick` is therefore its own small model, not a reuse of `PriceUpdated`; the ingest bridge is what converts one into the other when publishing onto the bus.
16. **Tick-to-candle bucketing lives above the adapter, not inside it.** `BrokerAdapter` (§4.1) has no `on_candle` — only `on_tick`. Building 1-minute candles from a raw tick stream is Market Data Engine's job (§4.2), not a broker-specific concern; putting it inside `IBKRAdapter` would mean every future adapter (a real Alpaca one, a replay adapter, etc.) has to reimplement the same bucketing logic. For Phase 3, `app/services/ibkr_ingest.py` does minimal, explicitly-throwaway bucketing as a stand-in for the real Phase 4 Market Data Engine — it gets replaced wholesale, not extended, when that engine is built.
17. **`is_connected()` is part of the `BrokerAdapter` ABC itself, not an IBKR-specific extension.** Every consumer of a `BrokerAdapter` — routes, health checks, future Market Data Engine — needs to ask "are you connected" regardless of which broker is behind the adapter. Originally added only to `IBKRAdapter`; promoted into the abstract interface once a second route (`GET /market/candles`) needed the same check, rather than leaving it as an untyped, adapter-specific method that happened to work by duck typing.
18. **One shared adapter registry (`app/services/broker_registry.py`), not per-route globals.** `app/api/routes/broker.py` (connect/disconnect) and `app/api/routes/market.py` (candle backfill) both need to know which adapter is currently active. A single global slot, not a dict keyed by broker — Phase 3 is "one adapter, one symbol at a time" by design (the Phase 3 roadmap exit criterion), so multi-broker support isn't a concern yet, and adding that flexibility now would be exactly the kind of speculative build this project avoids.

19. **Participation added as a 7th Market State dimension.** Computed from a new Feature Engine observable (signed volume / uptick-downtick imbalance) and tracked with the same duration/strength/confidence/previous shape as the other six dimensions. Deliberately scoped to the *observable* half of market psychology only — distinguishing panic from short-covering from options-hedging flow needs data (short interest, options gamma) this system has no confirmed source for yet, so that causal-inference layer stays in `future-ideas.md` (#13) rather than being approximated from data that can't support the distinction. (`../architecture/trading-intelligence-architecture.md` §4, §7)
20. **Context Engine v1 provider list expanded: `SectorCorrelationProvider` and `NewsFlagProvider`.** Sector/ETF correlation was a real gap — Decision Engine already checks correlation across a trader's own open positions but nothing read symbol-vs-sector correlation, and a breakout against a falling sector is a different trade than one moving with it. News flag is deliberately a headline-exists boolean/count, not NLP sentiment scoring — full sentiment stays deferred (`future-ideas.md` #13) until there's a way to validate it against real outcomes. (`../architecture/trading-intelligence-architecture.md` §5)
21. **`ContextProvider` is explicitly generalized to arbitrary refresh cadence, not just tick/seconds-scale.** Nothing in the interface ever assumed fast refresh — this makes it explicit, using the same event-triggered pattern already used elsewhere (decision #10) with a much sparser trigger (`EarningsReleased` instead of a volatility threshold crossing). This is what keeps a path open to slower-moving context — fundamentals, macro — for a possible future move into swing/position-holding-period trading, without committing to building any of it now; see `future-ideas.md` #9–#12 for the specific providers this unlocks. No new module, no new abstraction — a documentation change that makes an existing capability explicit and gives it somewhere to grow later. (`../architecture/trading-intelligence-architecture.md` §5)

22. **Manual trading reuses the existing pipeline via a single `plan(TradeRequest) -> TradePlan` interface, gated by a system-wide Execution Mode — not a parallel pipeline.** Manual entries join at Trade Planning Engine, not at Strategy/Opportunity/Decision — there's nothing for those to arbitrate when a human already picked the trade. Both AI- and manual-origin trades construct a `TradeRequest{origin: auto|manual, ...}`; Trade Planning Engine branches internally on origin but keeps one public method, rather than a second method (`plan_manual()`, proposed and rejected) that would need a new entry point per future origin. Governor and Execution Engine require zero new logic — they only ever see the resulting `TradePlan`, never its origin. A single `ExecutionMode` (`auto`/`manual`, account-level, one value system-wide) changes only where Execution Engine calls `BrokerAdapter.place_order`: in manual mode, an approved plan holds in a new Approval Queue for explicit human accept/ignore instead of firing immediately. A dedicated `ManualPlanBuilder` component, also initially proposed, was rejected as redundant once the Input Layer (#23) already owns translating raw input into `TradeRequest`. (`../architecture/trading-intelligence-architecture.md` §18)
23. **Manual trade input is abstracted behind a device-agnostic Input Layer, not built for a specific controller.** Physical input (gamepad, keyboard, Stream Deck, voice) is normalized in the frontend into one shared `InputCommand{command, symbol, order_type, size}` shape, sent over the existing WebSocket Gateway — no new transport, and the trading system never knows which device fired a command, mirroring `BrokerAdapter`'s broker-independence (`system-design.md` §4.1). Quantity is a `size` parameter, not encoded in the command name — a single `SELL` with a `size` parameter scales to any future sizing option without a new enum value, where `SELL_HALF`/`SELL_THIRD` would not. This iteration's command set is entry-only — `BUY`, `SELL` (opens a short, symmetric to `BUY`), `PROPOSE_LONG`, `PROPOSE_SHORT`, `CANCEL_PENDING` (Approval Queue only). Position-management commands (`MOVE_STOP`, closing/reducing an existing position) are explicitly deferred alongside Position Monitor/Trade Management integration for manual-origin positions — see `future-ideas.md` #14. *(Command vocabulary superseded in v1.7 — see #25.)* (`../architecture/trading-intelligence-architecture.md` §18.6)
24. **Hotkey targeting resolves against an explicit, per-tab `FocusedTile`, changed only by deliberate user action — never a background/system event.** Phase 1's multi-tab, 8×8-grid workspace had no "which symbol is currently active" concept; one had to be added specifically because a hotkey needs exactly one unambiguous target. `FocusedTile` is tracked per tab, set only by clicking a tile, and deliberately never moved by an Opportunity, alert, or approaching stop firing in the background — the Input Layer only reads it (same relationship §15's World View has to state it doesn't own), never writes it. With no focus set, symbol-targeted commands are refused outright rather than defaulting to an arbitrary tile. This is a separate concept from the Approval Queue's cursor (which pending plan `ManualConfirmOrder`/`CANCEL_PENDING` act on) — conflating the two would let a chart click accidentally change which trade is about to be confirmed. An idea in the same spirit — letting the system itself redirect focus toward whatever's most urgent — was considered and deferred specifically because it conflicts with this rule; see `future-ideas.md` #15. *(Renamed `TradeTarget` in v1.7 — see #27.)* (`../architecture/trading-intelligence-architecture.md` §18.6, §18.10)
25. **A single `LONG`/`SHORT` action per direction replaces the `BUY`/`SELL`/`PROPOSE_LONG`/`PROPOSE_SHORT` split — the branch moves from "which command was pressed" to "was a size given."** The four-command split encoded an execution decision (fire now vs. review first) into the hotkey itself, duplicating what Governor + `ExecutionMode` already decide, and required `SELL` to carry a footnoted meaning ("opens a short, not a close") to avoid colliding with a future exit verb. Collapsing to one action per direction removes both: `manual_size`'s presence or absence on the `TradeRequest` (decision #22) is what used to be the command choice. One exception preserved on purpose — an unsized request always lands in the Approval Queue for review regardless of `ExecutionMode`, so an algorithmically-sized idea nobody has seen can never fire unreviewed just because the account happens to be in Auto mode. (`../architecture/trading-intelligence-architecture.md` §18.5, §18.6)
26. **Hotkey actions are modeled generically: Action Categories route dispatch, Safety Levels gate commitment, Hotkey Context suppresses input during text entry or an open modal, and bindings map action-to-device rather than button-to-command.** None of these add a new component — they reshape the same amount of code the Input Layer (#23) already needed. Action Category (Trading/Queue/Navigation/UI/Emergency) determines whether an action ever reaches the backend at all — Navigation and UI actions never construct a `TradeRequest`, which is what "the Input Layer knows nothing about trading logic" means concretely. Safety Level (0–3, only 0–1 populated today) replaces a hardcoded arm-then-fire rule with a per-action declaration, leaving room for higher-friction levels a future Emergency action will need without another schema change. Hotkey Context is a real gap this closes — nothing previously stopped a bound action from firing while a text field had focus or a modal was open. Binding-keyed-by-action (not button) means multiple devices can bind the same action simultaneously, which a single button-keyed table couldn't express. (`../architecture/trading-intelligence-architecture.md` §18.10)
27. **`FocusedTile` renamed `TradeTarget`; explicit non-triggers documented.** Same concept as decision #24, renamed because "focus" invites confusion with DOM/keyboard focus, which this state is explicitly not tied to. Non-triggers made explicit in the doc rather than left implicit: not hover, not keyboard tab-order, not mouse position — only a deliberate tile click. (`../architecture/trading-intelligence-architecture.md` §18.6)
28. **Split `BrokerAdapter` into `MarketDataProvider` (base) + `BrokerAdapter(MarketDataProvider)` (adds execution), so pure market-data vendors don't need a broker interface.** IBKR account access is taking longer than expected — a passport renewal added roughly 20 more days on top of the original wait — so Polygon.io API access was obtained in parallel to keep live-data momentum going; this doesn't replace IBKR, which remains the target for execution (Phase 6) regardless of which data vendor is used meanwhile. Before this split, a data-only adapter would have had to implement `place_order`/`cancel_order`/`get_positions` and raise `NotImplementedError` from all three — but for `IBKRAdapter` that error means "not wired up yet, but could be" (a real broker sits behind it, per decision #6's "widen now, implement narrow" pattern), while for a pure data vendor it would mean "can never work." Conflating those two meanings was dishonest interface design. `MarketDataProvider` now holds exactly what a data-only vendor can honestly implement (connect, subscribe, get_historical, on_tick); `BrokerAdapter` extends it with the three execution-only methods. `IBKRAdapter` is unchanged behaviorally — it already implemented everything, now split cleanly across two classes via inheritance. No concrete data-only adapter (e.g. a `PolygonAdapter`) is built yet — see `future-ideas.md` #17 for the vendor evaluation itself. (`../architecture/system-design.md` §4.1)
29. **`ib_async` pinned to `>=2.1,<3.0`, not `<2.0`.** Found via a real failure on Python 3.14: `ib_async<2.0` depends on `eventkit`, which calls `asyncio.get_event_loop()` unconditionally at import time — harmless on Python ≤3.13, but Python 3.14 removed `get_event_loop()`'s implicit loop creation (raises `RuntimeError: There is no current event loop` instead), so merely importing `ibkr_adapter.py` crashed both `pytest` collection and the live server on startup. `ib_async>=2.1.0` depends on `aeventkit` instead — a maintained fork (renamed only because the original `eventkit` PyPI listing is locked behind an inactive account, not a different project) that removed the eager top-level call; confirmed by reading its actual installed source, not assumed from a changelog entry. All method signatures this project depends on (`connectAsync`, `reqHistoricalDataAsync`, `reqMktData`, `placeOrder`, `cancelOrder`, `positions`, `qualifyContractsAsync`) re-verified identical across the version bump — one new optional parameter on `qualifyContractsAsync` (`returnAll`), nothing that affects how this codebase calls it. The original `<2.0` ceiling was set defensively in decision #13 without anticipating a major-version fix would be needed; this corrects it now that Python 3.14 usage has surfaced the gap.
30. **`PolygonAdapter` built around free-tier constraints, not against an assumed real-time feed.** Verified before writing any code: Polygon.io's free/Basic tier gives 15-minute-delayed data, only 5 REST calls/minute, and **no WebSocket access at all** — real-time streaming simply isn't offered at this tier, confirmed across multiple current sources, not assumed. This rules out mirroring `IBKRAdapter`'s push-based `on_tick` design. Instead: a shared `app/core/rate_limiter.py` token bucket (5 calls/60s) gates every REST call the adapter makes — both polling and `get_historical()` backfill draw from the same budget, since Polygon enforces the limit per API key, not per endpoint. `on_tick()` is backed by polling `get_aggs` (confirmed free-tier-available, unlike `get_snapshot`/`get_last_trade`, which have less certain entitlement at this tier) once per `POLYGON_POLL_INTERVAL_SECONDS` (default 60s, matching the underlying 1-minute bar granularity — polling faster would just re-fetch the same bar and waste budget). Each `Tick`'s `exchange_ts` carries the bar's actual (delayed) timestamp from Polygon, not "now" — the delay is reflected honestly in the data itself, not hidden. `get_aggs` returning an empty list for a bad ticker (rather than raising) is the same "silently succeeds" trap `qualifyContractsAsync` had (decision #16's sibling finding) — checked explicitly here too, raising `SymbolNotFoundError`. Auto-connects on app startup if `POLYGON_API_KEY` is set (soft-fail — a missing key or connect error must not crash the app over an optional data source), unlike `IBKRAdapter`, which stays manual-connect-only because it depends on an external Gateway app being already logged in.
31. **`IBKRIngestBridge` renamed `TickIngestBridge`, retyped against `MarketDataProvider`.** Its bucketing logic never actually depended on IBKR — it only ever called `provider.on_tick()`, which is defined on `MarketDataProvider`, not `BrokerAdapter` specifically (decision #28 already put it there). Once `PolygonAdapter` needed the exact same tick-to-candle bucketing, keeping the IBKR-specific name and type would have meant either duplicating the logic or the class lying about what it does. Works correctly for both: IBKR's genuine multi-tick-per-minute stream buckets normally; Polygon's one-tick-per-new-bar polling just means each bucket ends up holding exactly one tick — an honest reflection of that tier's real granularity, not a bug.

**Deferred, not rejected** — Knowledge Engine, Attention Engine, uncertainty propagation across the pipeline, the full write-everywhere World Model, Replay Engine, Simulation Mode, a quarterly-tier `FundamentalsProvider`, an Expectation/Surprise provider, fundamentals-informed sizing, a macro slow-tier provider, causal psychology / market-participant inference, Position Monitor/Trade Management integration for manually-initiated positions, an auto-focus/attention-directing hotkey target, and Emergency actions (`PANIC`/flatten/cancel-all) all live in [`future-ideas.md`](./future-ideas.md) with the reasoning for why each is parked, and what would trigger revisiting it.

32. **`FinnhubAdapter` built for genuine real-time streaming; historical stock candles explicitly not supported.** Verified before writing code: Finnhub's free tier gives real, independently-confirmed real-time WebSocket streaming (an April 2026 third-party latency test found ~150ms, rate limit not hit), unlike Polygon's 15-min-delayed free tier — but `/stock/candle` (historical OHLCV) was moved behind a paywall and returns a real 403 on free keys (confirmed via an actual GitHub issue from a user hitting exactly that, not assumed from older tutorials predating the change). `finnhub-python` ships no WebSocket client at all (confirmed by inspecting the installed package) — the WS layer is built directly on `websockets` (already a dependency), following Finnhub's documented protocol (`wss://ws.finnhub.io?token=...`, `{"type":"subscribe","symbol":...}`, trade/ping message types). `get_historical()` raises the new `HistoricalDataUnavailableError` rather than silently failing or faking data — same honesty principle as `BrokerAdapter.place_order()` raising `NotImplementedError` for a provider with no execution capability (decision #28), just for a capability gap instead of a not-yet-wired one. Verified against a real local WebSocket server mimicking Finnhub's exact protocol (this sandbox can't reach the real `ws.finnhub.io` — not in its network allowlist), since that's meaningfully stronger than mocking the message handler in isolation.
33. **`broker_registry` split into two independent named roles — `streaming` and `historical` — replacing the original single-slot design.** The trigger for this (documented as hypothetical when the single-slot design was built) has now actually fired: Finnhub (streaming-only, real-time) and Polygon (historical-capable, streaming-capable-but-delayed) both need to be connected at once, each doing the job it's actually good at. Fixed priority decided once at startup (`app/main.py`), not dynamic runtime negotiation: Finnhub claims streaming first if configured; Polygon always claims historical, and only also claims streaming as a fallback if Finnhub isn't configured. A single provider can hold both roles (`IBKRAdapter`, once connected, takes over both — manually connecting it is a deliberate action, so it's allowed to override automatic startup ordering). `broker_registry.take_over_streaming()` centralizes the one genuinely tricky part: safely retiring whatever was previously streaming without disconnecting it if it's still needed for the historical role (e.g. Polygon serving both roles as fallback, then Finnhub connects — Polygon must stay connected for backfill, only its streaming "ownership" changes). Unit-tested directly (`tests/test_broker_registry.py`), not just exercised incidentally through route tests.
34. **`main.py`'s auto-connect calls the same shared `connect_polygon()`/`connect_finnhub()` functions the manual `/market-data/connect` and `/finnhub/connect` routes use, rather than constructing adapters inline.** Found via an actual startup test against a running server, not caught by unit tests: an earlier version had `main.py` construct `PolygonAdapter()`/`FinnhubAdapter()` directly and register them into `broker_registry`, which auto-connected successfully (visible in the startup logs) but left `market_data.py`/`finnhub_data.py`'s own module-level `_provider` references still `None` — meaning `GET /market-data/status`, `POST /finnhub/subscribe`, etc. were silently useless after a successful auto-connect, reporting `not connected` for a provider that very much was. Unit tests didn't catch this because they call routes directly, bypassing `main.py`'s lifespan entirely — this needed an actual `uvicorn` process to surface. Fixed by extracting one shared connect function per provider that both the route and the lifespan call, so there's exactly one place "how to connect X" is implemented, and both callers stay in sync by construction rather than by convention.
35. **Frontend mock-swap resumed and completed for `candles.ts`; a new generic `POST /market/subscribe` route added to support it.** The paused plan (from before the IBKR/Polygon/Finnhub detour) is unchanged: `chartObjects.ts` and `opportunities.ts` stay mocked, correctly, per their own file comments (Phase 4/5 producers don't exist yet) — only `candles.ts` was ever in scope. New pieces: `frontend/src/config.ts` (backend URL config), `services/websocket-client.ts` (one shared multiplexed WS connection, reference-counted channel subscriptions, reconnect with backoff — matches system-design.md §4.12's design), `services/api-client.ts` (REST + the one real shape seam: `Candle.time` is unix seconds, backend's `candle_ts` is an ISO string), `hooks/useLiveCandles.ts` and `hooks/useLatestPrices.ts`. `POST /market/subscribe` is new (`app/api/routes/market.py`) — provider-agnostic like `GET /market/candles` already was, so the frontend calls one route regardless of whether Finnhub, Polygon, or IBKR is actually connected, rather than needing to know which. Verified: full TypeScript build (`tsc -b` + `vite build`) succeeds; CORS and error-response shapes checked against a real running backend, not assumed. Two pre-existing, unrelated bugs found and left alone rather than silently fixed as a side effect: `GridPresetPicker.tsx` references a `GRID_PRESETS` export and `preset`/`setPreset` context fields that don't exist anywhere in the codebase — it's also not imported by anything, so it's dead code, not something blocking this or any other build via Vite's actual bundler (only `tsc -b`'s full-project check catches it). Flagged for you to decide whether to fix or delete; out of scope to touch as part of a data-source swap.

36. **`generateMockOverlays` (`mocks/chartObjects.ts`) needed an empty-candles guard, since `useLiveCandles` legitimately starts empty.** Found via a real browser crash on first load, not caught by the TypeScript build (`candles[Math.floor(candles.length * 0.7)].time` with `candles = []` is a runtime `undefined` read, not a type error). The old `generateMockCandles` always returned a full synchronous array — there was never an empty-array case for `generateMockOverlays` to handle before decision #35's swap. Audited `resampleCandles`, `sma`/`ema` (`utils/indicators.ts`), and `ChartWidget.tsx`'s data-setting effects for the same class of bug — all loop/map-based, all degrade to empty output on empty input without crashing. This was the one unguarded direct array index in the whole chain.
37. **`UnhandledExceptionMiddleware` (`app/core/error_handling.py`) added as a plain ASGI middleware, NOT `@app.exception_handler(Exception)` — the two are not interchangeable.** Found via a real browser bug report: `/market/candles` showed a "CORS policy" error while `/market/subscribe` worked fine, both hit at the same time from the same origin — an asymmetry that only makes sense if `/market/candles` was throwing something uncaught (confirmed: the first attempt at a fix used `@app.exception_handler(Exception)`, which *looked* correct and even appeared in `app.exception_handlers`, but a test proving CORS headers were actually present on the resulting response failed — not skipped, actually run and actually failed, twice, before the real mechanism was found by reading Starlette 0.46.2's own source). The root cause: `Starlette.build_middleware_stack()` routes any handler registered for the bare `Exception` class to `ServerErrorMiddleware` specifically, which is unconditionally the *outermost* layer — always wrapping `CORSMiddleware`, never wrapped by it. A response built by that handler is sent via the raw ASGI `send`, bypassing `CORSMiddleware`'s header injection entirely, confirmed by reading `ServerErrorMiddleware.__call__`'s actual source rather than assumed. This is true on a real production `uvicorn` server exactly as much as in a test — not a testing artifact. Fixed with a plain ASGI middleware class instead, registered via `app.add_middleware()` *before* `CORSMiddleware` is added — Starlette's `add_middleware()` prepends, so call-order is the reverse of wrap-order, meaning `CORSMiddleware` ends up wrapping `UnhandledExceptionMiddleware` only with this specific ordering. Reversing it silently breaks the fix again with no error at registration time — this ordering is load-bearing and non-obvious, which is exactly why it's written down here instead of left implicit in the code. Verified: a test asserting the actual `access-control-allow-origin` header is present on a genuinely-thrown, genuinely-uncaught exception's response — not just that a JSON body comes back — against a real running `uvicorn` process as a regression check on top of the `TestClient`-based test.
38. **Tests now blank `FINNHUB_API_KEY`/`POLYGON_API_KEY` for the duration of every test (`tests/conftest.py`), regardless of what's actually in a real `.env` file.** Found via a real, reproduced bug, not a hypothetical: once real API keys were configured locally for actual usage, `TestClient(app)`'s `__enter__` started running `main.py`'s *real* lifespan startup on every single test — auto-connecting real Finnhub/Polygon providers as a side effect and silently overwriting whatever fake registry state a test had carefully set up before opening the client. Reproduced exactly (same failure count, same failure shapes) by setting fake-but-present keys and re-running the suite; the captured traceback showed a genuine outbound HTTPS request to `api.polygon.io` firing mid-test. Six tests failed from this, none because of an actual application bug — the `UnhandledExceptionMiddleware` fix (#37) was independently re-verified correct once this was fixed. `monkeypatch.setenv(..., "")`, not `delenv`: pydantic-settings' `BaseSettings` reads a `.env` *file* as a source independent of `os.environ`, and only a `set` (even to empty string) takes priority over that file — `delenv` would just remove an OS-level override that was probably never set in the first place, leaving the real `.env` file's value to win regardless. `get_settings()`'s `lru_cache` must be explicitly cleared both before (so the blanked env is actually read) and after (so real settings resume for anything running after the fixture) each test.

    **`sessions.ts`'s US-Eastern trading-day/pre-market/regular-session classification is real infrastructure, not a stub**: it uses `Intl.DateTimeFormat` with an explicit `America/New_York` IANA zone (DST-correct across the EST/EDT transition) rather than a fixed UTC offset, since a fixed offset would be off by an hour for roughly half the year — this was worth getting right up front since four of the seven new indicators depend on it. VPOC is a coarse, explicitly-documented approximation: it buckets the previous day's candles by typical price `(H+L+C)/3` into 24 bins and sums candle volume per bin, since this app only has OHLCV bars, not tick-level trade prices — a true volume profile needs the latter, and the code says so rather than presenting bucket-approximation as more precise than it is.

    **Thickness bug fix, root-caused rather than patched around**: read the installed `lightweight-charts` v4.2.3 source directly (`node_modules/lightweight-charts/dist/lightweight-charts.production.mjs`) rather than guessing. Two different renderers handle `lineWidth` differently: the overlay line-series renderer (`addLineSeries`, used by SMA/EMA/VWAP) passes the configured width straight into the canvas 2D context's `lineWidth` — a float-valued property — with no rounding anywhere in that path; only the `LineWidth = 1|2|3|4` TypeScript type restricts it, not the runtime. The price-line renderer (`createPriceLine`, used by every horizontal level) explicitly does `Math.floor(configuredWidth * horizontalPixelRatio)`, flooring to an integer physical-pixel count. So overlay indicators now step by 0.5 (1, 1.5, 2, 2.5...) — genuinely rendering at intermediate thickness, not a rounded/fake value — directly answering "1 is almost okay, 2 is too thick" with a real in-between option; horizontal levels stay on integer 1-4 steps since their renderer would floor a fractional value back down anyway, at best inconsistently depending on display DPI. 42. **Chart zoom-reset bug fixed; candle-close latency bug fixed; volume bars made fully customizable; 4h/1d timeframes added; multi-monitor pop-out built.** Five items delivered together; grouped here because they were reported and worked through in one session, not because they're one change.

    **Zoom reset on every live candle (`ChartWidget.tsx`), root-caused rather than patched around.** The data effect was calling `setData()` *and* unconditionally re-running `setVisibleLogicalRange()`/`fitContent()` on every single run — including a live candle refresh, which silently re-pinned the view to the configured candle-count window every time, overriding any zoom/pan set manually. Root cause was that re-pin call, not `setData()` itself (`setData()` alone does not reset zoom). Fix: a new `diffCandles()` distinguishes a genuine reset (symbol/timeframe switch, or the candle-count stepper changing) from a live update (the last bar refreshing in place, or exactly one new bar appended — the only two shapes `useLiveCandles`' `[...prev, candle]` append plus `resampleCandles`' deterministic index-based bucketing can ever produce for the array `ChartWidget` receives). Only a genuine reset still calls `setData()` + re-pin; a live update instead calls `series.update()`, which Lightweight Charts never uses to reset the visible range — and which the library auto-scrolls to reveal *only* when the person is already viewing the live edge, i.e. exactly "fixed zoom, oldest candle pushed off the left when there's no room" as reported, with no special-cased scroll logic needed on this app's side at all. `update()` is also materially cheaper than a full `setData()` re-render on every tick, which matters across however many sub-windows are live at once, though that wasn't the reported problem.

    **Candle arriving up to tens of seconds after its minute boundary (`tick_ingest.py`), root-caused rather than patched around.** `TickIngestBridge` closed a candle bucket *only* when a tick for the following minute happened to arrive — on a quiet moment with no trade right at `:00`, the previous candle (and so the new one's on-chart appearance) was late by however long the gap to the next trade was; reported case was a 09:34 candle not appearing until 09:34:42. Fixed with a new wall-clock-driven `_flush_loop` that wakes ~250ms after every minute boundary and force-closes any bucket whose minute has fully elapsed regardless of tick arrival — self-healing across any gap (a provider hiccup that misses several minutes still gets caught on the very next wake-up), and still correctly produces no candle at all for a symbol with genuinely zero trades in a minute, since bucket *opening* is untouched. `TickIngestBridge.stop()` added and wired into `broker_registry.take_over_streaming()`/`clear_streaming_provider()` so the new background task doesn't leak across reconnects — every connect route already builds a fresh bridge per connection, so without this every reconnect would leave one more loop running forever. Regression test drives `_flush_stale_buckets()` directly with a controlled timestamp rather than sleeping for a real wall-clock minute, reproducing the exact reported symptom (`09:34:00` tick, then simulated `09:35:42` with no second tick) and asserting the candle closes anyway.

    **Volume bars made fully customizable, distinct from the volume-average lines already on top of them.** New `SubWindowConfig.volumeBars` (`VolumeBarsConfig`): master on/off, two-color (up/down, each independently hex-customizable) or one flat hex color — same `ColorField` control already used everywhere else in this menu, not a new interaction pattern. Previously this was a hardcoded 50%-alpha green/red baked into `ChartWidget.tsx` with no way to turn it off; the new default (full-opacity hex matching the old green/red) is a deliberate small visual change for consistency with every other color picker in the app, none of which force an alpha. Disabling collapses the volume price scale's `scaleMargins` to zero height, not just hiding the bars, so the candle pane actually reclaims the vertical space.

    **`4h`/`1d` added to `Timeframe`, ahead of the data to fill them.** Same "build the option now, let the data catch up" posture decision #40 already took once — `resampleCandles` (`MINUTES_PER_TIMEFRAME`) and `currentBarProgressPct` (`SECONDS_PER_TIMEFRAME`) both already handled `Timeframe` generically, so this was two map entries each, not new logic. Known, explicitly-flagged limitation carried forward rather than fixed here: `resampleCandles`' bucketing is index-position-based, not calendar/session-aligned, which matters more the larger the bucket gets — not worth fixing until real multi-day historical backfill exists to feed it (still blocked on #39), since today's short-lived in-memory buffer rarely spans enough history for the misalignment to be visible.

    **Multi-monitor pop-out — discussed before building, per standing instruction, then built as discussed.** A Main Window can now pop out into its own real browser tab (`window.open`, triggered by a new ⧉ button on each `MainWindowTabs.tsx` tab) and land on a second monitor, which switching between this app's own *virtual* tabs inside one browser window could never allow. Two new pieces, confirmed before implementation: a minimal hand-rolled router (`App.tsx`, no library — exactly two shapes, `/` and `/window/:id`, reached only via a fresh `window.open()`, never client-side navigation) and `frontend/src/state/crossTabSync.ts`, a `BroadcastChannel`-based live sync layer. The sync layer doesn't transmit state directly — every tab already persists its full session to `localStorage` synchronously (pre-existing since Phase 1); a broadcast is just "go re-read `localStorage`," so there's exactly one code path (the existing `loadSession()`/`loadSavedLayouts()`) that turns storage into state, whether that's first load or a live update from another tab. A last-synced-JSON ref set *before* applying an incoming update, and checked before every local persist+broadcast, stops the two tabs from echoing the same update back and forth indefinitely — without it, applying a receive triggers this tab's own persistence effect, which would otherwise re-broadcast right back. Chosen behavior, confirmed with the user rather than assumed: the original tab keeps showing a popped-out window as a live-mirrored tab (simpler than removing it from the strip until the popped-out tab closes, which would need "is this currently popped out" tracked and synced too) — either tab can be closed independently without losing the other's view. A popped-out tab's own `activeMainWindowId` is pinned via `WorkspaceProvider`'s new `lockedMainWindowId` prop and exempted from an incoming sync's `activeMainWindowId`, so it keeps showing the one window it was opened for regardless of which tab the main workspace has active. If that window is closed elsewhere, the popped-out tab shows an explicit "this layout no longer exists" message rather than silently falling back to some other window — not a defensive nicety on a trading app, a real requirement. Degrades gracefully (no cross-tab sync, same single-tab-only behavior as before this existed) if `BroadcastChannel` isn't available. Not yet handled, flagged rather than silently skipped: a production static-file deployment (as opposed to the Vite dev server, and `vite preview`, both confirmed to already serve `/window/:id` correctly via SPA fallback) will need its host configured for SPA fallback too (e.g. nginx `try_files`) — out of scope until an actual deployment target exists.
