80. **Volume Bars opacity confirmed already shipped (decision #77, no change needed); the real bug behind Saqib's report was `useDropdownPlacement` inflating a settings panel's max-height past the actual viewport space in the chosen direction — fixed once, in the shared hook, closing it for every dropdown panel in the app at once.**

    **Volume Bars opacity — verified, not re-implemented.** Checked `VolumeBarsConfig` (`types/workspace.ts`), its `createDefaultVolumeBarsConfig()` and `WorkspaceContext.tsx` backfill, `volumeBarColor()` in `ChartWidget.tsx`, and the `SubWindowMenu.tsx` "Volume Bars" panel directly against a fresh pull, rather than assuming Saqib's report meant the feature was missing: `upOpacity`/`downOpacity`/`singleOpacity` are full first-class fields, wired through `ColorField`'s existing opacity slider (the same shared control every other color field uses, per decision #76), rendered via `hexWithOpacity()` at draw time, and backfilled for sessions saved before the fields existed. Nothing here needed building — it already matches every other color field in the app exactly.

    **Root cause, found by re-deriving what the report screenshot implied rather than guessing:** the screenshot showed a settings panel (Daily Levels, but Volume Bars' own panel is taller still — color-mode toggle plus two color+opacity rows plus a reset button) cut off flush against the bottom of a narrow viewport, with no scrollbar. `useDropdownPlacement` (decision #76) already measures real anchor position and caps `maxHeight` to the genuine remaining space — but its floor, `Math.max(spaceBelow, MIN_USABLE_HEIGHT)` / `Math.max(spaceAbove, MIN_USABLE_HEIGHT)`, was inflating that cap to 160px whenever the true remaining space was smaller, e.g. on a short/narrow viewport where an anchor sits close to both screen edges at once. `overflow-y-auto` only produces a scrollbar when a panel's own content exceeds ITS max-height box — it does nothing when the panel's max-height itself was set larger than the space actually available, which is exactly what an inflated floor does: the panel gets positioned partly past the visible viewport, the browser window's edge clips it first, and no scrollbar ever appears. This is the same failure mode decision #76 already diagnosed once, reintroduced by its own floor value in the one case (both directions under `MIN_USABLE_HEIGHT`) it hadn't been checked against.

    **Fix, in the one shared hook, not per-panel:** `MIN_USABLE_HEIGHT` (160px) now only decides WHICH direction to open in — it no longer floors the returned `maxHeight`. The returned value is always `Math.max(spaceBelow, 0)` or `Math.max(spaceAbove, 0)` — the real measured space, never inflated past it. Because `useDropdownPlacement` is shared by `SubWindowMenu.tsx`, `LayoutsMenu.tsx`, `GridPicker.tsx`, and `FeatureEnginePanel.tsx`'s ticker search (all four already wire its `maxHeight` into `style={{ maxHeight: placement.maxHeight }}` alongside their own `overflow-y-auto`, confirmed by re-reading each), this one change gives every long settings panel in the app — Volume Bars, Daily Levels, and anything added later — a working scrollbar on short/narrow viewports, not just the two panels in the report.

    **Docs housekeeping done in the same change, per decision #79's own maintenance rule, not a separate ask:** `confirmed-decisions.md` had grown to 105,956 bytes (past the ~100KB size trigger #79 itself set) by the time this entry was ready to append. Rolled over per that rule: `confirmed-decisions.md` (#61–#79) moved verbatim to `archive/061-079.md`, a fresh open file started, and this entry is the first one in it. `INDEX.md`'s file-location column updated for #61–#79 in the same change.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies here (same as decision #78's precedent for a doc/frontend-only change). **Not verified: an actual browser at the narrow viewport width from the report** — same standing gap flagged on every panel-affecting change so far; the fix is derived from re-reading `useDropdownPlacement`'s own math against the reported symptom, not confirmed by reproducing the clipped view and watching it resolve.

81. **Name half of an axis label ("PDH", "SMA 9", "VWAP") gained its own on/off toggle — `showNameLabel` — separate from the existing price-value toggle (`showPriceLabel`), on both `PriceIndicatorInstance` (SMA/EMA/VWAP) and `HorizontalLevelInstance` (PDH/PDL/PMH/PML/Camarilla/VPOC).**

    **The bug, confirmed against Lightweight Charts' own issue tracker rather than assumed:** for an overlay indicator (a Line series — SMA/EMA/VWAP), `lastValueVisible` (`showPriceLabel`) only ever hides the VALUE half of the price-scale label. The library's own maintainers confirm `title` renders unconditionally whenever it's a non-empty string, with no flag of its own to gate it — so unchecking "Show price tag" for SMA 9/20/50 (Saqib's report, screenshot 1) hid the number but left the name badge floating on the axis with nothing attached to it. Not a rendering glitch on this app's side — a real gap in what the two existing fields could express, closed by giving the name half a field of its own.

    **Two different renderer shapes, so two different fixes, not one:** overlay indicators are Line series with independently-settable `title`/`lastValueVisible` — decoupling them was a straight wiring fix in `ChartWidget.tsx`'s indicator effect: `title` now resolves to `""` when `showNameLabel` is off, instead of `ind.label` unconditionally. Horizontal levels (PDH/PDL/etc.) are `createPriceLine` price lines, where `title` and `axisLabelVisible` already draw as ONE combined tag — there's no equivalent library-side bug there. `showNameLabel` on `HorizontalLevelInstance` only drops the name prefix from that combined tag ("PDH 494.86" becomes "494.86"); `showPriceLabel`/`axisLabelVisible` still owns whether the tag shows at all, same as before this field existed. A genuine "name only, no price" mode for price lines isn't offered — Lightweight Charts has no per-price-line way to suppress just the numeric half while keeping `axisLabelVisible` on, and building one would mean replacing the native price-line label with a custom-drawn one (the `rectBoxes` div-overlay pattern this file already uses for rectangle objects) — out of scope for what the report asked for, flagged here rather than silently narrowed.

    **Where it's wired:** `types/workspace.ts` — new field on both instance types, defaulted `true` in `createPriceIndicatorInstance`/`createHorizontalLevelInstance` (matches the always-on behavior every existing session was already rendering). `utils/indicators.ts` — threaded through both `computePriceIndicator` (all three SMA/EMA/VWAP branches, backend and local) and `computeHorizontalLevel`. `ChartWidget.tsx` — both rendering effects (indicator Line series creation/update, and the horizontal-levels price-line effect) resolve the actual `title` string from the new flag instead of passing the label straight through. `SubWindowMenu.tsx` — a "Show label" checkbox added directly under "Show price tag" in both `OverlayIndicatorRow` and `HorizontalLevelRow`, same checkbox styling and placement pattern as every other toggle in those rows. `WorkspaceContext.tsx`'s `normalizeSubWindow` backfills `showNameLabel: true` for `priceIndicators` and `horizontalLevels` on sessions saved before this field existed, same partial-cast treatment `showPriceLabel`/opacity already get there — a session missing the field keeps showing the name badge exactly as it always did, rather than the badge silently disappearing on next load.

    **Deliberately not touched:** Volume Avg lines and Daily Levels also render via `createPriceLine` with their own `showPriceLabel`/`showPriceLabels`, but neither was in the report (screenshot 1's pink box circles only the SMA/VWAP/PDH/PDL tags), so they were left alone rather than folded in speculatively — same "don't write unrelated modules" boundary this project has held to on every prior report-driven change.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies here. **Not verified: an actual browser** — same standing gap every panel/chart-affecting change in this log has flagged; the fix is derived from re-reading Lightweight Charts' own documented `title`/`lastValueVisible`/`axisLabelVisible` behavior against the reported symptom, not confirmed by reproducing the floating badge and watching it resolve.

82. **The `showNameLabel` toggle from #81 extended to the two indicator types deliberately left out of it — Volume Avg lines (`VolumeAvgLineConfig`) and Daily Levels (`DailyLevelsConfig`) — so every label-bearing indicator on the chart follows the same convention, not just SMA/EMA/VWAP/PDH/PDL.**

    **Why #81 stopped short, and why that turned out to be the wrong call:** #81 scoped itself to exactly what screenshot 1's pink box circled (PDH/PDL/VWAP/SMA), reasoning that pulling in Volume Avg lines and Daily Levels too would be scope creep beyond the report. Saqib's own framing of the ask — "make this labels as an option just like price label is an option" — reads as a request about the *concept* (every indicator's name should be toggleable, the same way every indicator's price already is), not specifically about the four indicators visible in one screenshot. Deferring the other two was narrower than what was actually being asked for; corrected here on direct request rather than left as a judgment call.

    **Same mechanism as #81, no new pattern introduced:** both types already render via `createPriceLine` (same primitive as `HorizontalLevelInstance`), so this is the identical `title`-resolves-from-a-flag change, not a new design. `VolumeAvgLineConfig` gets `showNameLabel: boolean`, defaulted `true` in all four of `createDefaultVolumeAvgConfig()`'s hardcoded lines. `DailyLevelsConfig` gets `showNameLabels: boolean` (plural, matching its existing `showPriceLabels` naming — Daily Levels' fields have always been plural since one config fans out to many levels at once, unlike the other three types where one config is one line), defaulted `true` in `createDefaultDailyLevelsConfig()` — deliberately *not* matching `showPriceLabels`' own `false` default there, because the `"DL-N"` strength tag (not the price number) is Daily Levels' own documented primary way strength reads visually; defaulting names off too would have silently removed that on every existing session, not just made it optional.

    **A real gap surfaced while wiring `DailyLevelsConfig`, worth being upfront about:** re-reading Lightweight Charts' own shipped type declarations (`node_modules/lightweight-charts/dist/typings.d.ts`) while doing this, `PriceLineOptions.axisLabelVisible` and `.title` are documented as two independently-scoped things — `axisLabelVisible` governs only "the current price value... on the price scale," `title` is described as rendering "on the chart pane." If the type declarations are accurate, "name only, no price" may actually work for all three `createPriceLine`-based types (`HorizontalLevelInstance`, `VolumeAvgLineConfig`, `DailyLevelsConfig`), not just the "drop the prefix, keep the price" version #81 shipped and described as the limit. **Not verified in a real browser** — this environment has no working browser (no snap/chromium connectivity — confirmed by attempting the install, not assumed), so this is read from the library's own shipped declarations, not confirmed by watching the label actually render. Flagging rather than either quietly upgrading #81's description or quietly leaving it uncorrected.

    **Where it's wired:** `types/workspace.ts` — new field on both types, defaulted `true` in both factory functions. `ChartWidget.tsx` — the `volumeAvg` price-line effect and the Daily Levels price-line effect both resolve `title` from the new flag the same way #81's two effects already do. `SubWindowMenu.tsx` — `VolumeAvgLineRow` gets a "Show label" checkbox under "Show price tag," matching #81's checkbox exactly. The Daily Levels panel gets a "Show "DL-N" label" toggle matching its own existing highlighted-button style (not a checkbox — Daily Levels' panel doesn't use checkboxes anywhere else, so a checkbox here would've been the inconsistent choice, not the button). `WorkspaceContext.tsx`'s `normalizeSubWindow` backfills both new fields to `true` for sessions saved before they existed, same partial-cast pattern as everywhere else in that function.

    **Verified:** `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. No backend files touched, so no `pytest` run applies. **Not verified: an actual browser** — same standing gap as #81, for the same reason (no browser available in this environment).

83. **SMA/EMA slope, expressed as an angle in degrees, computed in the Feature Engine (both live and historical paths) for every configured SMA/EMA period/timeframe, and surfaced in the chart's indicator menu as a numeric label suffix — `∠+35.2°` appended to the name tag.**

    **Normalization is percentage-of-current-value, NOT ATR — a deliberate rejection, not an oversight.** The original ask was ATR-normalized slope. `atr_14` (decisions #67/#69) is a Wilder range over the last 14 *daily* candles, full stop — there is no version of "intraday SMA/EMA slope ÷ daily ATR" that avoids the exact unstated cross-timeframe unit conversion decision #67 already ruled out for Regression/KAMA's own slope normalization (that decision chose local window stdev specifically to dodge this). Since the slope here can be measured on any of `1m`/`5m`/`15m`/`1h` (decision #51's uniform SMA/EMA fan-out), the mismatch is structural, not incidental — reusing ATR would have the same problem every time, not just at some periods. Resolved as percentage-of-current-value instead (`slope ÷ current SMA/EMA value × 100`, %/bar) — self-contained, no dependency on the daily-candle cache, correct at every timeframe without a second setting to express which one.

    **Lookback for the OLS fit is tied 1:1 to each period itself, not a separately configurable window** — a 9-period SMA fits its slope over its own last 9 values, a 50-period SMA over its own last 50. Deliberately not decoupled the way the original design sketch (percent/ATR/z-score conversation, k=5–10 bars) suggested, on direct instruction: one fewer independently-tuned knob, and the slope's own "memory" scales with how smoothed the line already is.

    **The math itself, `indicators/sma.py::sma_slope()` / `indicators/ema.py::ema_slope()`:** an OLS fit over the average's own trailing `period` values (NOT a fit against raw closes — that's `regression.py`'s different question), reusing `sma()`/`ema()` themselves at each point rather than a parallel recursion, matching this engine's standing "recompute from window" convention. `sma_slope` needs `2*period-1` closes; `ema_slope` needs `period*seed_multiplier + period - 1` (one bar more than `ema()`'s own stricter warm-up floor, staggered `period` times). Both return `{}` below that — the same honest-gap convention as every other indicator here, not a fabricated zero. `r2` (fit quality, 1.0 on a perfectly flat window) rides along free, same as `regression.py`'s. `slope_angle = arctan(slope_pct)` in degrees — arctan of the ALREADY-×100 `slope_pct` number, not the raw fraction, a deliberate calibration choice: the raw-fraction version compresses nearly every real SMA/EMA slope into single-digit degrees, defeating the point of an at-a-glance angle. This way, 45° means exactly "1%-of-value per bar" — an explicit, documented anchor, flagged as worth revisiting once this runs against real symbols rather than assumed correct on paper.

    **Applies uniformly to every currently-configured period, no new setting.** Rides `feature_engine_sma_periods`/`feature_engine_ema_periods` directly (SMA 9/20/50, EMA 9/20 by default) — since lookback is tied to period, there's nothing left for a dedicated config list to express. `FeatureEngine._window_capacity`'s formula gained explicit `sma_slope_max`/`ema_slope_max` terms for correctness, though at today's defaults both stay under KAMA's own 159-close requirement, so capacity didn't actually grow — computed explicitly anyway rather than assumed dominated, so a future config change can't silently under-size the window.

    **Both the live path (`engine.py::_apply_close`) and the historical/backfill path (`historical.py::compute_series`, `GET /intelligence/series`) compute this now — a gap caught mid-build, not designed in from the start.** `useFeatureEngineSeries.ts`'s live-append is fully generic over `FeaturesUpdated.features` keys, so the live path needed no frontend change at all; but `compute_series()` had its own independent forward-walk that only knew about `sma`/`ema`/`vwap` — without extending it, a fresh page load would show no angle until the next live tick. Fixed by reusing `sma_slope()`/`ema_slope()` verbatim on the same walk, same "exact same pure functions, only the orchestration differs" guarantee this module's docstring already makes for `sma`/`ema`/`vwap`.

    **A correction, made mid-conversation, worth recording plainly: chart-pane SMA/EMA rendering is NOT client-side-only** — an earlier turn in this same work claimed it was (reading only `engine.py`'s decision-#40-era module comment) and proposed building a new bridge to backend data as part of this decision. That was wrong. Decision #50/#54 already migrated the chart onto Feature Engine as its source of truth (`computePriceIndicator` sources SMA/EMA/VWAP from `useFeatureEngineSeries.ts`, falling back to `frontend/src/indicators/` — labeled `" (local)"` — only when the backend can't serve a given period/timeframe). The bridge already existed; this decision only needed to extend it, not build one. Caught by re-reading `system-design.md` §4.5/§4.11 properly before writing frontend code, not assumed from the older comment.

    **Representation: numeric label only, not a visual glyph, on direct instruction.** No separate rotated-arrow/gauge widget — the angle rides as a suffix on the SAME name-tag `showNameLabel` (#81) already controls, e.g. `"SMA 9 ∠+35.2°"`.

    **Where it's wired:** Backend — `indicators/sma.py`/`ema.py` (new `sma_slope()`/`ema_slope()`), `indicators/__init__.py` (re-exports), `engine.py` (`_apply_close`'s SMA/EMA loops, `_window_capacity` formula), `historical.py` (`compute_series()`'s forward walk), `config.py` (comment only — no new setting), `schemas/events/features.py` + `system-design.md` §10.3 (documentation of the new keys). Frontend — `types/workspace.ts` (`showSlopeAngle: boolean` on `PriceIndicatorInstance`, defaulted `false` in `createPriceIndicatorInstance` — genuinely new behavior, not a preserved prior always-on state like #81/#82's `true` defaults, so off-by-default is the correct choice here), `WorkspaceContext.tsx` (`normalizeSubWindow` backfills `false` for existing sessions, including the hand-built legacy-EMA-migration literal that doesn't go through the factory function), `utils/indicators.ts` (new `withSlopeAngle()` helper, called only from `computePriceIndicator`'s BACKEND-sourced SMA/EMA branches — never the `"(local)"` fallback, since slope is Feature-Engine-only with no client computation of it at all, by direct instruction), `SubWindowMenu.tsx` (`OverlayIndicatorRow` gets a "Show slope angle" checkbox, gated on `hasPeriod` — SMA/EMA only, not VWAP, same gate the Bars stepper already uses; `HorizontalLevelRow`, a different component despite sharing field names, is untouched — no slope concept applies to a fixed horizontal price level).

    **A pre-existing staleness found and corrected while touching `system-design.md` §10.3's `FeaturesUpdated` mirror table, not newly introduced:** the table still listed `atr_14`/`rvol`/`gap_pct`/Regression/KAMA as "still the target shape, not yet computed," even though decisions #67–#71 built all of them well before this session. Corrected in the same edit rather than left contradicting the paragraph one section above it, since decision #38's own standing rule is that this table mirrors what's built, not aspirational.

    **A pre-existing pattern flagged, deliberately NOT fixed here:** `LevelInteractionEngine._process_one` iterates every key in `FeatureSet.features` unconditionally and runs touch/reject/conquer tracking against each one as if it were a price level — already true today for `atr_14`, `gap_pct`, `rvol`, `regression_9_r2`, etc. The new `sma_9_slope_angle`-style keys join that same existing pattern, not a new one. A level-key allowlist would fix it for every affected feature at once, but that's a cross-cutting change touching many already-shipped features — out of scope for a slope-specific change, flagged for a separate decision rather than folded in speculatively.

    **Verified:** Full backend suite — **266 passed** — run against a real local Postgres 16 (installed and migrated fresh in this environment specifically to verify this, not skipped/mocked; confirmed decisions #34/#37/#38's own "real Postgres, not mocked" standard applied here too), including 9 new pure-math + end-to-end `EventBus` tests for `sma_slope`/`ema_slope` and 2 new tests for `compute_series`'s slope series. `npx tsc -b` and `npx vite build` both clean (filtered for the same pre-existing, unrelated, unimported `GridPresetPicker.tsx` errors #80–#82 already filter). A same-session upstream commit ("Premarket volume ratio," unrelated to this work) was merged in cleanly mid-build — real overlap in `config.py`/`engine.py`/`test_feature_engine.py`, auto-merged with no conflicts, full suite re-verified green after. **Not verified: an actual browser** — same standing gap every chart-affecting decision in this log has flagged; the label-suffix rendering is derived from re-reading `ChartWidget.tsx`'s existing `title`-resolution logic (confirmed decision #81) against the new field, not confirmed by watching `"SMA 9 ∠+35.2°"` actually render on screen.

84. **The reported `test_intelligence_routes.py` FK-violation-on-teardown race root-caused to `LevelInteractionEngine.stop()` — a `task.cancel()` + `await task` pattern that looks like it waits for real completion (the same shape decision #47 gave CandleRecorder) but doesn't, for an item already mid-`_process_one` at the moment `stop()` is called. Fixed with a poison-pill queue drain instead of cancellation.**

    **Root cause, reproduced with a standalone script before touching any app code, not assumed from reading asyncio's docs.** `_worker_loop` awaits `asyncio.to_thread(self._process_one, item)` — internally `loop.run_in_executor`, which hands the awaiting Task a plain `asyncio.Future` wrapping a `concurrent.futures.Future` that actually runs on a real OS thread. `Future.cancel()` on that plain asyncio Future transitions it to CANCELLED synchronously, REGARDLESS of whether the underlying thread has finished — cancelling the wrapped `concurrent.futures.Future` is attempted too, but only best-effort, and a `concurrent.futures.Future` that's already RUNNING can't be cancelled and just keeps executing, orphaned, fully detached from anything the caller of `stop()` can see or wait on. Measured directly, isolated from this codebase entirely: a bare `asyncio.to_thread(slow_fn)`-awaiting task, cancelled while `slow_fn` (a plain 0.5s `time.sleep`) had 500ms left to run, had its `await task` return in **~0ms** — `slow_fn` kept running to completion regardless, unobserved. For an engine whose thread-pool work WRITES rows keyed on `symbol_id` (`_persist_state`), that orphaned write is exactly what raced a test's post-`stop()` `DELETE FROM symbols` into a real, intermittent `ForeignKeyViolation` on teardown.

    **A second, previously-unexplained flake in the same file turned out to be the identical bug's fingerprint, not a coincidence.** A full-suite run taken before this fix, for comparison, failed `test_daily_levels_carry_level_interaction_once_touched` on a wrong zone (`"above"` instead of `"inside_aura"`) — passing 5/5 in isolation, only failing embedded in the full suite. Not chased down independently or treated as a separate bug: an orphaned background thread from an EARLIER test's now-abandoned `LevelInteractionEngine` instance (each test gets a fresh singleton per `conftest.py`'s reset, but an orphaned OS thread from a prior instance doesn't know or care that its owning instance was discarded) contends for the same process-wide default `ThreadPoolExecutor` and the same Postgres connection pool as the CURRENT test's own `to_thread` calls, skewing exactly the kind of fine-grained timing this file's own `_wait_until_*` helpers already document as fragile. Re-ran the full suite 5x after the fix below — **270 passed, 0 failed, every run** — with no other change made to that test or its fixture. Treated as corroborating evidence for the diagnosis, not proof on its own; flagged as such rather than claimed with more confidence than one fix + 5 clean runs actually supports.

    **Fix: a poison-pill drain, not cancellation.** `stop()` no longer calls `.cancel()` at all — it enqueues a private sentinel object (`_STOP_SENTINEL`, identity-checked, never confusable with a real `FeaturesUpdated`-derived dict) onto the SAME queue `_worker_loop` already reads, then awaits the worker task with nothing cancelled. Because the queue is FIFO and `main.py`'s shutdown already stops the Event Bus before this engine (cutting off any new arrivals here — that ordering was already correct, per decision #47's own note, and didn't need to change), the sentinel is only ever dequeued after every item genuinely ahead of it — including one already running inside `to_thread` — has fully finished, `_persist_state` writes and all. This is what `main.py`'s own shutdown-order comment already claimed ("await engine.stop() actually means what it says") — true for the queued backlog even before this fix, just not for an item already mid-flight inside `to_thread` at the exact moment `stop()` was called. Now it's true for that case too. `_worker_loop` gained one check (`if item is _STOP_SENTINEL: task_done(); break`) ahead of its existing per-item try/except; nothing else in the processing path changed.

    **Trade-off made deliberately, not left implicit: no timeout-then-cancel fallback if the DB is genuinely wedged during shutdown.** Considered and rejected — a timeout that falls back to `.cancel()` would just reintroduce this exact race at lower probability instead of removing it, which defeats the point of fixing it at all. Correctness over shutdown latency is the right call for a background worker that writes to the database: a slower-than-usual shutdown is a strictly better failure mode than a nondeterministic foreign-key violation, and a DB wedged badly enough to hang a single `SessionLocal()` write is already a degraded scenario independent of this engine.

    **Scope, deliberately held to the one engine actually implicated by the reported race.** `CandleRecorder.stop()` and `FeatureEngine.stop()` share the exact same `task.cancel()` + `await task`-around-a-`to_thread`-worker-loop shape — confirmed by direct inspection of both files while root-causing this, not assumed by pattern-matching the name — and very likely carry the identical latent bug (a stray `CandleRecorder._write_one` or `FeatureEngine._compute_one` write landing after a test's own teardown). Not fixed here: neither was the engine named in the reported race, no reproduction was attempted against either, and folding both in speculatively would have meant shipping two unverified fixes alongside one verified one. Flagged explicitly as real, likely-live follow-up work — not a hypothetical "might also want to check someday" — rather than either silently expanding this change's scope or silently leaving a known-probable bug undocumented.

    **New regression test, deterministic rather than timing-hopeful:** `test_stop_waits_for_an_in_flight_persist_before_returning` in `test_level_interaction_engine.py`. Wraps the engine's own `_persist_state` with an artificial 0.3s `time.sleep` (a real blocking delay inside the executor thread, not a mock), feeds one item directly onto the engine's internal queue (see the test's own docstring for why: publishing through the Bus and immediately calling `stop()` raced the sentinel into this engine's queue ahead of the real item often enough to make the first version of this test flaky even against the FIXED code — an unrelated Bus-dispatch-timing gap, not a flaw in the fix itself, caught and removed before this test was considered done), waits 0.05s for the worker to genuinely start the slow write, then calls `stop()` with nothing else queued behind it. Asserts two things together, not just one: `stop()` must take meaningfully longer than "basically instant" (proving it actually blocked on the in-flight write, not that it happened to finish fast), and deleting the symbol row immediately afterward must not raise (the actual bug's real-world symptom). Confirmed this test fails deterministically (3/3) against the old cancel-based `stop()`, restored, and confirmed it passes deterministically (5/5) against the fix — both directions verified, not just the one that was expected to pass.

    **Verified:** Backend suite run 5x against a real local Postgres 16 (installed and migrated fresh in this environment) — **270 passed, 0 failed, every run**, including the one new regression test. No frontend files touched, so no `tsc -b`/`vite build` applies (same precedent as decision #78/#80 for backend-only changes). **Not verified: production shutdown under real load** — this fix changes shutdown TIMING (now genuinely bounded by in-flight DB work rather than near-instant), which is correct by design per the trade-off above, but hasn't been observed against a live, running instance under real traffic, only against this test suite's synthetic races.

    **Ledger tier gains real definition, not just new fields — this is where an undocumented meaning would have become a silent schema-semantic bug later.** `realized_pnl` is now explicitly defined as NET of `commission_total` (a `gross_pnl` field may be added later if isolating commission drag becomes useful — not v1). `entry_qty`/`exit_qty` gain a stated invariant — equal for a fully closed row — enforced by assertion at write time, not just documented, same discipline already used for multi-site structural edits elsewhere in this project. `commission_total` and new `slippage_entry` (`entry_price - TradePlanned.entry`, separating execution quality from strategy edge) are both nullable — `None`, never estimated, when the broker adapter doesn't surface the underlying figure, per the project's standing honest-state rule. `exit_reason`'s enum gains `eod_flatten`, specific to this project's day-trading-only rule (no overnight holds): a position cut off by session close is a materially different signal from a thesis-driven `time` exit, and conflating the two would corrupt exactly the kind of "why is this strategy losing" query Performance Intelligence exists to answer. `trading_day: date` (new) needs only one value per row, not an entry/exit pair, precisely because the day-trading rule guarantees both happen on the same ET calendar day — a simplification the schema gets for free from that trading rule, not one it has to build itself. `holding_seconds` (new) is a stored convenience derived from `entry_filled_at`/`exit_filled_at`, same precedent already set by storing `realized_r` rather than always recomputing it. `setup_detected_at`'s existing sibling `confirmed_at` (on `Opportunity`) is renamed `signal_confirmed_at` at the persistence boundary only — `Opportunity.confirmed_at` itself is unchanged; this is a translation on write, not a field rename upstream.

    **`backtests` table shape locked — the name `system-design.md` §4.13 already reserved, previously unshaped.** One row = one `(strategy_version, config_hash)` tested against one walk-forward fold, not one row per whole grid-search sweep — `walk_forward_fold`/`is_holdout` only mean something at that granularity. A `sweep_id` groups every run belonging to the same grid-search session instead. Two fields are the most consequential addition here: `data_version` and `feature_version`, without which two backtests using different market-data snapshots or a since-changed Feature Engine indicator implementation could look identical and produce different results for reasons that have nothing to do with the strategy being tested — a real reproducibility gap, caught in review, worth closing before Stage 1 rather than after. Full shape in `strategy-engine-design.md` §7.

    **One idea raised and deliberately not adopted yet: `exit_trigger` (who/what initiated the exit — strategy, Governor, broker, forced market-close — orthogonal to `exit_reason`, which captures why).** Not built because there's no live source that would populate anything but `strategy`/`market_close` today — Governor's derate/veto branches (`approved_reduced`/`watch_only`/`delayed`) remain unimplemented (`trading-intelligence-architecture.md` §12). Recorded with full reasoning in `future-ideas.md` #21 rather than re-argued from scratch when it becomes real.
