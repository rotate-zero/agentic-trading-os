### 185. Simulated EOD flatten policy and shared session-window foundation (`simulated-eod-flatten-contract`)

Saqib approved four simulated EOD policies on 2026-09-29: (1) a position-bound reduce-only close needs no new Governor decision and may be attempted only on the entry trading day within `[regular close - 60 seconds, regular close)`, with no next-day EOD catch-up; (2) the first later stop/target observation is a durable fallback, actionable only after EOD placement expires and prior orders/fills are safely settled; (3) an accepted order remains working at the bell, so an after-hours/later fill or indefinite non-fill is possible; and (4) EOD is labelled by a valid post-opening, entry-day tick, with no extra maximum age and no candle label. This is a best-effort flatten attempt, never a guarantee of closure. It extends EX-5 option (a) to simulated EOD policy only; paper/live and EX-12 remain unresolved.

This delivery implements only the shared foundation: `core.session_window.eod_session_window(clock, opened_at, lead_seconds=60)` returns UTC `EodSessionWindow(flatten_at, close_at)` for a covered trading day; `contains(now)` implements the exact inclusive/exclusive bounds. A covered holiday/weekend returns `None`; a year without calendar coverage raises `UnsupportedEodCalendarError`. `MarketClock.has_calendar_for_year()` exposes read-only 2026 coverage without changing existing session methods. Settings validates the configured lead in `1..900`. The new tests cover both half-days, DST, exact boundaries, invalid inputs, unsupported years and parity with Backtest Runner's close derivation on every supported 2026 trading day. The 78 relevant focused and existing tests passed. Position Monitor timing/handoff, durable exit request and dispatch transitions, migration, Execution wiring, reconciliation and frontend are subsequent tasks; no EOD order can execute from this foundation alone. §6.6 contains the approved contract, diagrams and remaining acceptance cases.

### 186. Simulated OutcomeRecorder owns strategy-attributed non-backtest outcomes (`outcome-recorder-contract`)

Saqib approved EX-12 option (a): a dedicated `OutcomeRecorder` is the sole writer of non-backtest `strategy_outcomes`; the ledger supplies every outcome fact and `PositionClosed` only wakes the worker. This delivery covers closed, strategy-attributed simulated auto trades. The strict outcome schema stays unchanged. Missing required evidence, a valid structural R basis, exit reason, or consistent ledger attribution marks `trades.outcome_status = blocked` and logs a reason code; it never invents evidence, a snapshot, commission, or R. An earlier approval without `trades.thesis["evidence"]` is not backfilled and blocks as `evidence_unavailable`. The Governor's strict JSON evidence persistence was merged earlier at `79650ad` and is reused unchanged; `signal_confirmed_at` stays NULL because no producer sets it.

The recorder captures entry snapshots best-effort at the first entry fill, without holding up fill persistence, and exit snapshots only within 60 seconds of closure; unavailable snapshots use NULL with machine-readable reasons. It replays only the target position's durable receipts through canonical `apply_fill`, preserves partial-fill VWAPs, gross/known-fee rules and the closing order's `exit_reason`, and computes direction-aware R from the authorization-time structural invalidation. A same-session performance writer stages all fields without owning the caller's commit; the Backtest Runner's existing wrapper remains. The recorder acquires ledger table locks before the trade row lock, rechecks closure and outcome linkage, then inserts the outcome and links `trades.outcome_id` atomically. Startup scan and a bounded 60-second sweep recover lost events and closures applied before recorder subscription. Recorder startup failure logs CRITICAL without changing an otherwise ready execution startup; reconciliation-blocked startup does not run it, and shutdown stops it after Portfolio State. No migration or paper/live/manual path is included. §6.7.1 contains the as-built source map and diagrams; `TESTING.md` records real PostgreSQL verification and the full backend suite.

### 187. One non-backtest strategy outcome per opportunity, enforced by the database (`outcome-unique-opportunity-guard`)

Implements the optional guard that decision #186 left as a follow-up (`execution-engine-design.md` section 6.7.1). Migration `0017` creates the partial unique index `uq_strategy_outcomes_non_backtest_opportunity` on `strategy_outcomes(opportunity_id) WHERE is_backtest IS FALSE`; `StrategyOutcomeRecord` declares the same index so the model and the schema agree. A second simulated, paper or live outcome for one opportunity is now rejected by PostgreSQL even from a second writer; backtest rows (`is_backtest IS TRUE`) stay outside the predicate and keep sharing an opportunity ID across runs. The guard is `is_backtest IS FALSE`, not `execution_mode = 'simulated'`, so it also covers future paper/live outcomes.

The upgrade is additive and never chooses a row: it takes `SHARE` mode on `strategy_outcomes` (the lock `CREATE INDEX` needs), and if any non-backtest `opportunity_id` already has more than one row it raises, names up to ten of them with their counts, and leaves the revision, rows and schema unchanged. An operator must decide which outcome is authoritative and resolve the duplicates before re-running. The downgrade drops only this index. `OutcomeRecorder`'s retry and blocking policy, outcome payloads and read routes are unchanged; its existing under-lock duplicate recheck stays the first line of defense and the index is the backstop.

### 188. Retain and replay Position Monitor protective ticks after temporary snapshot loss (`position-monitor-trigger-recovery`)

Valid `PriceUpdated` ticks are now journaled before the subscriber reads a position snapshot or filters held symbols. The monitor's worker replays retained ticks for a newly visible or recovered position in arrival order, considering only exchange timestamps at or after `opened_at`. The first stop or target touch creates the existing pending observation with its original exchange timestamp and level price; stop still wins if one event touches both levels. A per-position cursor advances only after evaluation or safe observation registration. Recovery wakes are coalesced and serialized with candles and EOD pulses through their own arrival-sequence boundaries, including when the EOD timer is disabled. Portfolio State retries transient ledger synchronization failures through its existing accounting worker with bounded backoff; ledger anomalies and unresolved order IDs keep snapshots unavailable. The ledger and existing observation/acknowledgment handoff remain authoritative for accounting and durable exit identity.

The in-memory journal has validated, configurable starting limits of 100 symbols, 2,000 ticks per symbol, and 60 seconds of monotonic retention for unowed ticks. Unavailable snapshots, fill-pending symbols, and visible positions with unevaluated ticks make ticks owed; the latest EOD label and a queued pulse's candidate remain owed while relevant. Capacity can still evict owed ticks, and process downtime loses the journal. The additive `/intelligence/exit-intents` diagnostics expose availability, bounded journal and incident history, cumulative loss counts, and sticky lost-window evidence. They do not claim unconditional exactly-once protection or first-touch certainty after loss. No entry gate, broker action, external alert, emergency liquidation, or historical-candle policy changes. The architecture and verification are in `execution-engine-design.md` §6.6 and `TESTING.md`.

### 189. Continuous scanner cadence, manual-first activation and protected feed capacity (`continuous-scanner-design`)

Saqib selected a fixed **60-second scan interval** for the first continuous-scanner slice. This corrects decision #3's variable, config-driven schedule for this slice; the original decision body and `system-design.md` §4.7's draft schedule remain historical context. Session coverage beyond the interval is not approved here.

Scanner-driven promotion remains **manual by default**. An operator may explicitly switch to automation only after external feed obstacles are resolved. Before that switch, verify the active provider's effective general subscription capacity and delivery against the distinct union of the entire scanner universe, manual subscriptions, open-position symbols and working-order symbols. Top-N and `LiveTickRelay`'s eight-symbol chart limit are not substitutes for this full-feed check. Unknown/insufficient capacity, subscription failures, stale data or an unhealthy provider must be visible and cannot be silently clipped into an apparently complete automated scan. The exact operator-control interface and transition behavior remain to be specified in the implementation design.

Manual subscriptions stay under operator control; scanner demotion or universe removal does not remove market observations required by open positions or working orders. The protective feed need must survive startup restoration and reconnect independently of scanner eligibility. Scanner scoring remains an activity observation, never an execution authorization or a new Governor policy. The exact top-N, threshold, hysteresis, session coverage and manual chart-relay priority remain unapproved. This decision records design direction only; continuous scanning is not implemented by this delivery. See `scanner-design.md` §18 for the verified data path, implementation plan and acceptance criteria.

### 190. Finnhub adapter owns supervised streaming recovery (`finnhub-stream-reconnect`)

This supersedes decision #143's historical observation that Finnhub had no automatic reconnect and required the manual button after a WebSocket close. One `FinnhubAdapter` now supervises its established socket: unexpected closure, including clean iterator completion, disconnects the current generation and retries with configurable positive delays capped by exponential backoff. Initial connect failures remain synchronous caller errors and do not start background retry. The adapter retains desired subscription intent separately from requests successfully sent on its current socket, restores desired requests after reconnect, and retries a partially failed restoration without claiming complete local inventory. Manual disconnect and streaming-provider takeover settle the adapter's task and socket; neither may leave a retired owner able to resume. Existing tick callbacks and the one `TickIngestBridge` survive retries. The current-socket inventory is request evidence only, never acknowledgement, delivery or capacity evidence.

Backtest replay excludes a Finnhub owner that is connecting or able to resume, even while its `is_connected()` flag is false. Finnhub route connection establishment shares the existing replay-singleton lock, and replay repeats the Finnhub owner check under that lock before installing process-wide engines. This keeps an outage retry or concurrent new Finnhub connection from crossing the replay boundary while leaving Polygon, IBKR and replay serialization behavior unchanged. The broader Phase 4 Market Data Engine remains separate. See `system-design.md` §4.2, `scanner-design.md` §18.13 and `backtest-runner-design.md` for the as-built flows and test limits.

### 191. Wake protected-feed reconciliation after durable exposure and provider changes (`protected-feed-event-wake`)

The application-owned `ProtectedFeedReconciler` keeps one serialized cycle and a single coalesced pending wake. Its synchronous `request_reconcile()` does no database or provider work. New simulated entry-order inserts, new close-order reservations and positive open/closing position commits signal only after their durable operation returns; the earlier `OrderApproved` and `OrderFilled` events are not commit evidence for those respective rows. Registry streaming-role installation and a same-instance Finnhub reconnect signal the current owner. The owner always rereads the authoritative protected set and current registry provider before additive requests; a retired provider and a stopped owner cannot schedule further work. A wake during a cycle survives for one follow-up. Failed or deferred cycles have a short retry cooldown, while the 60-second periodic cycle remains the fallback for missed signals, process interruption and failures. Lifecycle stop unregisters the signal and settles the owner before provider shutdown. The immutable status contract and its request-evidence meanings remain unchanged. This reduces request delay without promising instant protection, provider acknowledgement, capacity or continuing tick delivery. See `scanner-design.md` §18.13, `execution-engine-design.md` §6.9 and `system-design.md` §4.2.

### 192. Explicit simulated-session ownership for scheduled scanner observation (`scanner-observation-lifespan`)

The existing `ScannerObservationWorker` may now be owned by the application lifespan as an observation-only service, disabled by default. Enabling it requires a nonempty, explicit set of supported MarketClock trading-session labels; `closed`, duplicates and unknown labels are invalid. The service is simulated-only, starts only after execution startup is `ready`, and retains decision #189's fixed 60-second cadence. The eligibility predicate checks both the selected label and verified calendar-year coverage, failing closed beyond covered years. A worker that starts successfully is the only reader installed for `GET /scanner/observation`; failure or shutdown clears the slot and settles the worker before FeatureEngine and providers stop. It scores existing FeatureEngine state and does not acquire scanner-universe feeds, promote symbols into StrategyScheduler or activate LiveTickRelay.

Because backtest replay temporarily replaces the process-wide FeatureEngine singleton, an observation skips a due point while the existing replay/connection slot is occupied and rechecks that slot, the selected session and calendar coverage after its asynchronous universe read, immediately before synchronous scoring. No second lock is introduced; replay serialization and on-demand scanner behavior remain unchanged. A replay or session change during the read cannot enter a retained observation. The service does not verify provider capacity, acknowledgement, delivery or data freshness. C2 promotion thresholds and C4 relay/manual priority remain open. See `scanner-design.md` §18.15 and `phase-roadmap.md` for the as-built boundary.

### 193. Explicit saved-universe feed request uses the current streaming owner (`scanner-universe-feed-request`)

The operator may explicitly request feeds for a point-in-time capture of the persisted scanner universe through `POST /scanner/request-universe-feeds`. The route reads that set in an offloaded, session-owning database read without the on-demand scanner's `TEST_UNIVERSE` fallback. It neither constructs nor connects a provider: a current connected streaming registry owner is required. It skips symbols already in that adapter's optional local `SubscriptionInventory`, sends remaining single-symbol requests sequentially, and returns the captured set, provider identity and local per-symbol outcomes, preserving partial results. One in-process batch is admitted; duplicates are rejected rather than queued. Each step rechecks owner and connection, leaving remaining symbols unattempted after takeover or loss. The existing replay/connection singleton slot excludes sends while replay engines are installed. The Universe tab invokes this only on an operator click and retains the response's captured set even if the editable universe changes meanwhile.

This implements decision #189's manual-first direction without enabling automated promotion or reconciliation. An inventory hit or returned subscription call is request evidence only, not provider acknowledgement, verified capacity or actual delivery. The action never unsubscribes, edits the universe, activates chart relay symbols or changes scanner/strategy eligibility. Automated universe acquisition, full-union capacity verification, real-feed delivery, C2 promotion thresholds and C4 relay/manual priority remain open. See `scanner-design.md` §18.16 and `system-design.md` §4.2.
