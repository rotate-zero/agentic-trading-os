122. **Performance Intelligence's read-side query layer built — `app/trading_intelligence/performance_queries.py`, decision #120's real GROUP BY queries over `strategy_outcomes`, §5.** Re-checked the decision-log tail immediately before writing — #121 was still latest, `confirmed-decisions.md` still empty of entries since its own rollover, so #122 was free, no collision to reconcile this time. File-disjoint from the sibling parallel track's own route/frontend work — confirmed by `diff -rq` against a freshly-pulled, untouched second clone: the only files touched are `app/trading_intelligence/performance_queries.py` (new), `backend/tests/test_performance_queries.py` (new), this entry, the matching `INDEX.md` row, a small §5 pointer note, and `TESTING.md`.

    **Placement: new sibling module, not a section inside `performance.py`.** `performance.py`/`test_performance_intelligence.py` (decision #120) stay completely untouched. `performance.py` is a write-time-invariant-then-persist concern; this module is read-only aggregation with no invariant to enforce and no single-row session lifecycle. Same "read-side view sits one layer above the thing it reads, as its own file" shape `state_snapshot.py` (decision #98) and `opportunity_view.py` (decision #121) already established in this codebase — followed here rather than invented fresh.

    **Two real queries, exactly the two with an unambiguous grouping key.** `get_win_rate_by_hour()` groups by `entry_filled_at` converted to `Settings.market_timezone` ("America/New_York" by default) — confirmed by grep that `core/market_clock.py`'s own `get_market_clock()` singleton already reads this same setting rather than a hardcoded literal, so this module reads it the same way instead of introducing a second, divergent source of truth for "which zone is market time." Bucket is `hour_et` (0-23, named explicitly so it can't be mistaken for a UTC hour) via real Postgres `entry_filled_at AT TIME ZONE :market_timezone` (DST handled by Postgres's own tzdata, no custom logic), `EXTRACT(HOUR FROM ...)`, cast to integer, ordered `hour_et ASC`. `get_expectancy_by_session_type()` groups by `context_at_entry->>'session_type'` (real Postgres JSONB `->>`, exercised against real Postgres in this build's own tests, not assumed from reading the code), ordered `session_type ASC`. `session_type` was chosen over the other two candidates §5's own field comment names ("gap day?, session type, VIX regime") for two checked reasons: decision #117 already confirmed by grep that no `vix` field exists anywhere in this codebase to back a VIX-regime grouping, and `gap_day` is a boolean flag, not a genuine multi-valued regime dimension the way `session_type` is. **This is Performance Intelligence's first concrete regime dimension, not "regime" solved generally** — no `regime_dimension` parameter, no generic JSONB-key abstraction; a second regime dimension would be a new function, not a parameter added to this one.

    **"Parameter sensitivity" is explicitly out of scope — no code, no stub, no narrowed version.** `StrategyConfig.params`'s shape varies per strategy (§3); there is no single column or JSON key to group by without a per-strategy params schema decision this task doesn't make.

    **Metrics defined exactly, not left implicit.** Both use `realized_r`, never `realized_pnl` (§5: R is size-comparable, raw PnL isn't). `realized_r` confirmed `NOT NULL` at both the ORM (`Numeric(10,4), nullable=False`) and Pydantic (`float`, no default, no `| None`) layers before writing any code — no NULL-population policy needed for either metric, and no test exercises one. Expectancy = `AVG(realized_r)` per group, computed in Postgres. Win rate = `win_count / total_trades`, where `win_count` is real Postgres `COUNT(*) FILTER (WHERE realized_r > 0)` — `realized_r <= 0`, including exactly `0`, is explicitly not a win. The division itself is done in Python, deliberately: Postgres `COUNT(*)` returns `bigint`, and `bigint / bigint` truncates there, so `COUNT(*) FILTER (...) / COUNT(*)` as one SQL expression would silently collapse every real ratio to `0` or `1`. Both operands are already fully reduced, one row per hour bucket, by the real `GROUP BY` — this is arithmetic on an aggregate result, not client-side row aggregation.

    **Live/backtest isolation enforced in SQL, not caller discipline.** `is_backtest: bool = False` on both functions is a strict either/or selector — `False` filters `is_backtest = false` (live only), `True` filters `is_backtest = true` (backtest only); there is no call shape that blends both populations in one result. §5/§7's "never blended with live in a live query" is a hard invariant, verified in this build's own tests by writing both live and backtest rows with deliberately different counts/results and confirming each query returns exactly one population's aggregate, never a mix.

    **Version filtering never silently blends strategies.** `strategy_version` without `strategy_name` raises `ValueError` — grepped first for an existing strategy_name+strategy_version filtering abstraction elsewhere in this codebase to reuse instead; found none, so this is new, narrowly-scoped validation, not a copy of a pre-existing pattern.

    **Empty-result semantics.** No matching rows -> `[]`, never `None`, a fabricated zero row, or a NULL-populated aggregate — `strategy_outcomes` has zero real production rows today, and this is the normal case, not an edge case.

    **Implementation shape.** Real SQL-level `GROUP BY` per query, never fetch-then-aggregate-in-Python — each public function is a thin wrapper around a private, pure `_build_*_query()` (returns a `Select`, no session) that opens its own `SessionLocal()`, executes, shapes rows into a local `@dataclass(frozen=True)` (`HourlyWinRate`, `SessionTypeExpectancy` — not new entries in `schemas/performance.py`, which this task leaves untouched), and closes the session, same lifecycle convention `record_strategy_outcome()` already uses in this same package. No caching, no persisted query results (§5's own "computed on demand" framing — persisting these would reintroduce the "stored rank" anti-pattern §5 opens by rejecting), no route (future work, sibling-track collision risk on `routes/intelligence.py`), no change to `StrategyOutcomeRecord`.

    **Tests: `backend/tests/test_performance_queries.py`, 8 new, real Postgres, all synthetic outcomes written via the real `record_strategy_outcome()` write path** (never a raw INSERT). Covers: empty table (both queries -> `[]`); win-rate-by-hour grouping + exact arithmetic across 2 hour buckets with win/loss/breakeven mixed; expectancy-by-session_type grouping + exact `AVG` across 2 session_type values, plus the honest-`None` group for a missing key; backtest isolation (mixed live/backtest rows, deliberately different counts so blending would be detectable, verified for both queries); strategy_version isolation (two versions of one strategy_name); strategy_name filtering; the `ValueError` guard for a version-only filter. Verified against real local Postgres 16 (provisioned directly in this session — `apt-get install postgresql`, `alembic upgrade head`), full suite run 3 times against a freshly wiped-and-recreated DB each time (this project's own established practice): 625-627 passed depending on run (the documented #119 flaky pair flickers as already described there), same two known tests each time (`test_vwap_publishes_even_while_sma_is_still_warming_up`, `test_daily_levels_carry_level_interaction_once_touched`), zero unexpected failures, zero regressions. This build's own touched area (`test_performance_queries.py` + `test_performance_intelligence.py`, 16 tests total) run 3x in isolation: 100% stable every time.
