62. **Daily Levels: root-caused Saqib's "no levels showing" report, then shipped a price-range filter, a configurable lookback window, and shorter labels — all in response to real usage, not speculative polish.**

    **"No levels showing" turned out to be the design working as intended, not a bug.** Confirmed via a direct question rather than guessed at: Daily Levels only computes when a live 1m candle closes for that symbol — it has no schedule of its own, it piggybacks on the exact same trigger as every other Feature Engine indicator. Levels appeared roughly two hours before market open, once a candle actually closed. Nothing to fix here, but worth recording as a known, real characteristic of the current design (an on-demand trigger, not a cron), in case it comes up again for an infrequently-traded symbol.

    **"Levels only appear under 1D, and turning them on nearly hides every other indicator" — investigated, not assumed to be an autoscale bug.** `daily_levels` is symbol-scoped and was already attached identically to every timeframe's `FeatureSet` (confirmed by re-reading `_apply_close`/`_compute_aggregated`'s own wiring, not re-derived from scratch) — so the DATA was never missing on 5m/15m, this was always a rendering/visibility symptom, not a data gap. Checked Lightweight Charts' own typings for a documented price-line-affects-autoscale mechanism before writing a fix for one; found no such flag on `PriceLineOptions`, and no way to verify the actual rendering behavior without a live browser. Rather than ship a speculative `autoscaleInfoProvider` override I couldn't test, addressed the reported symptom directly and honestly: a price-range filter that constrains what gets drawn at all, which fixes the clutter regardless of which exact mechanism was causing it.

    **New: `DailyLevelsConfig.minPrice`/`maxPrice`** (`types/workspace.ts`) — null means no bound on that side. A second, more direct filter than `minStrength` alone, since the reported problem was specifically about *how far* a level sits from the current price, not how weak it is. Applied client-side in `ChartWidget.tsx`'s existing filter chain — no backend change needed, since the full set was already being sent.

    **New: `DailyLevelsConfig.lookbackDays`** — a lookback selector (30/60/90 days, or the server default), genuinely cheap to implement because of how Stage 1 was already built, not despite it: `engine.py` now caches the RAW daily candles per symbol (`_daily_levels_state[symbol]["candles"]`), not just the final clustered `levels`, and a new `FeatureEngine.get_daily_levels(symbol, lookback_days)` re-clusters on demand from a slice of that cache — zero new provider calls, just a fast in-memory re-run of the same `cluster_daily_levels` function already proven correct in decision #60. `GET /intelligence/state` gained an optional `daily_levels_lookback_days` query param; omitted, behaves exactly as before. A requested lookback larger than what's actually cached is silently clamped, not an error — same "return what's available" honesty as the provider-gap handling in decision #60. Proven with a real test using genuinely different candle sets at different distances, not just re-labeling the same cached result — confirms a shorter lookback actually drops the far-away cluster, not just that the number changed.

    **Labels shortened, per Saqib's direct instruction:** `"Daily Level · Strength N"` → `"DL-N"` on each price line's title. Uniform color/width across all levels, unchanged from decision #61 — strength still communicated as a number, just a shorter one.

    **Verified:** `pytest` — **168/168** passing (2 new: the lookback re-clustering test and a never-seen-symbol edge case for the new `get_daily_levels` method). `npx tsc -b` (filtered for the pre-existing `GridPresetPicker.tsx` errors) and `npx vite build` both clean. **Not verified: an actual browser** — same standing gap as decision #61; the price-range/lookback fix addresses the reported symptom on the evidence available, but hasn't been visually confirmed to look right.

63. **Daily Levels Stage 2 built and tested — persistent, price-proximity-reconciled level identity, and restart survival, against real local Postgres.**

    **New table, one not two:** `daily_levels_state` (migration 0003) — a single current-state-per-`level_id` table, not an append-only log like `level_interaction_state`/`level_interaction_events`'s pair. `level_id` is derived from the row's own DB identity at first mint (`f"{symbol}-DL-{row.id}"`, set once, never recomputed) — globally unique with zero extra counter-tracking, and stable for the row's entire life regardless of price drift or rank changes among other levels.

    **Reconciliation (design doc §4), confirmed NOT rank-based, matching what was already decided:** greedy nearest-price matching between today's freshly clustered zones and yesterday's still-`active` persisted rows, within `daily_levels_identity_match_pct` (decision #60's own config knob, sitting unused until now). Every (cluster, row) pair within tolerance gets built, sorted by distance ascending, then claimed greedily — each side used at most once, closest pairs first. A matched cluster carries its row's level_id forward with updated price/strength/distinct_candle_count; an unmatched survivor is archived (`status="archived"`, `archived_day` set) — kept, not deleted, so a level's full price history stays queryable even after it stops appearing live; an unmatched cluster mints a brand-new row.

    **Restart-survival, proven adversarially, not just by coincidence:** a fresh `FeatureEngine` instance (empty in-memory cache, simulating a process restart) checks `daily_levels_state` for today's already-confirmed levels BEFORE ever considering a provider fetch. Tested by pointing the "restarted" instance at a SECOND fake provider that would return visibly different prices (99x the real ones) if it were ever reached — the test asserts that provider's call count stays at zero AND that the recovered level_id and price exactly match the pre-restart values, not just that the numbers happened to agree.

    **Where this runs, and why it couldn't just reuse the existing sync-DB pattern:** `LevelInteractionEngine`'s own persistence (decision #46) is sync `SessionLocal` code that's already safe off-loop because ITS caller is thread-offloaded a level up. `_maybe_refresh_daily_levels` is called directly from the ASYNC worker loop (decision #60's own docstring explains why: `MarketDataProvider.get_historical()` is itself async and needs a real event loop to await), so its NEW DB calls needed their own explicit `asyncio.to_thread` wrapping — the same discipline extended one step further, not a new pattern invented from scratch.

    **The custom-lookback preview (decision #62) deliberately stays untracked:** `get_daily_levels()` with an explicit `lookback_days` still mints ephemeral, `-preview-`-marked ids via `_mint_adhoc_daily_levels` — ad-hoc, not persisted, not reconciled. It's a what-if display control, not the tracked default; reconciling every possible lookback value a user might click through would multiply complexity for a feature that's explicitly meant to be disposable. The same `_mint_adhoc_daily_levels` fallback also covers a DB-reconciliation failure — Daily Levels should still show SOMETHING on a transient DB hiccup rather than nothing, same soft-fail posture as `CandleRecorder`/`LevelInteractionEngine`'s own persistence.

    **Two real bugs found and fixed while testing, both worth recording plainly:**
    - Several of this session's own test tickers exceeded `symbols.ticker`'s `VARCHAR(16)` limit — invisible in Stage 1 (which never wrote to `symbols` for Daily Levels at all) and only surfaced once Stage 2 actually persisted rows, via a real `StringDataRightTruncation` from the INSERT. Fixed by shortening every offending test ticker to ≤16 characters, with an explicit `assert len(ticker) <= 16` left in the newer tests so this can't silently reappear.
    - `test_intelligence_routes.py`'s own `_clean_test_symbol` cleanup helper didn't know about the new table, so any ticker Daily Levels had ever persisted a row for would throw a real `ForeignKeyViolation` on cleanup — caught by running the FULL suite, not just this feature's own tests, exactly the kind of cross-feature consequence that's easy to miss testing one file in isolation. Fixed by adding the new table's cleanup to that shared helper.

    **Verified:** `pytest` — **170/170** passing (167 + 3 new Stage-2-specific: reconciliation match/archive/mint, restart-survival, plus two older tests updated for the new DB-identity-derived level_id format), confirmed stable across repeated full-suite runs against real local Postgres with migrations applied through 0003. The 3 pre-existing, wall-clock-time-sensitive `test_feature_engine.py` failures flagged in decisions #61/#62 recurred again this session (confirmed once more directly from the failure payloads — `pmh`/`pml` firing because it's genuinely premarket hours right now, `daily_levels` correctly empty and uninvolved) — same pre-existing issue, not re-investigated, not part of this task. **Not verified: real-browser anything** (no frontend changes this round) **and D1** (Polygon empirical depth check — still no network route to Polygon in this environment).

    **Still open:** D1, and Stage 3 (`LevelInteractionEngine` reading `daily_levels` — now has a genuinely stable `level_id` to key its state against, which is exactly what this stage was for).


64. **Daily Levels Stage 3 built and tested — LevelInteractionEngine now tracks touch/holding/rejected/conquered on `daily_levels`, the deliberate exception to its own "zero code changes for a new level type" property flagged back in decisions #59/#61, now actually built.**

    **The extension itself is exactly as small as predicted, confirmed by writing it, not just assumed.** `_process_one` gained one sibling loop alongside its existing `features.items()` loop, walking `item.get("daily_levels", [])` and calling `_process_level(symbol, timeframe, level_id, price, close, candle_ts)` — the SAME method, completely unmodified, since `level_key`/`level_value` were always generic parameters with no assumption about where they came from. `get_snapshot()` needed zero changes at all: it's keyed purely by whatever `(symbol, timeframe, level_key)` shows up in `self._state`, so a Daily Level's `level_id` appears there automatically once `_process_level` has been called for it even once.

Before Stage 2, Daily Levels minted a fresh `level_id` every day; wiring THIS engine in against that would have silently reset every level's touch history daily, defeating the entire point. With Stage 2's persistent, price-reconciled `level_id` in place, this integration is exactly as safe as wiring in any other level type.

    **`GET /intelligence/state` closes the gap decision #61 left explicitly open:** each `daily_levels` entry now carries a `level_interaction` dict keyed by timeframe (not a single flat value) — interaction state genuinely differs per timeframe for every level type already, and `daily_levels` itself stays the same flat, symbol-scoped list decision #61 deliberately chose, so per-entry-per-timeframe was the only shape consistent with both existing decisions at once. 67. **Feature Engine indicator expansion — direction locked for five new families (ATR, Session % / $ Change, Gap % / $, Linear Regression, KAMA), full plan in the new `docs/architecture/feature-engine-indicator-expansion.md`. No application code written yet — same "Stage 0, direction lock" shape decision #59 used for Daily Levels.**

    **Saqib brought a full design brief for this** (ATR(1D,14) methodology, session/gap semantics, regression and KAMA output lists, a cross-cutting normalization requirement, an explicit request to review against the existing Feature Engine architecture before building) — reviewed against `feature_engine/engine.py`, `market_clock.py`, and `schemas/events/features.py` directly rather than answered from the brief alone, and several real conceptual conflicts surfaced that needed resolving before any code:

    **Config model doesn't fit as-is.** SMA/EMA's existing shape (`feature_engine_sma_periods: list[int]`, applied uniformly across whichever timeframes the engine already fans out to) can't express "1m/9, 5m/9, later 1m/21, 5m/13" — independent `(timeframe, period)` pairs where the timeframe list itself is indicator-specific. Resolved: a new `list[dict]` config shape per indicator family (`feature_engine_regression_configs`, `feature_engine_kama_configs`), which becomes the single source of truth for both which periods and which timeframes — regression/KAMA start scoped to `1m`+`5m` only, not the full `1m`/`5m`/`15m`/`1h` SMA/EMA fan out to.

    **KAMA needed explicit `fast_period`/`slow_period`, not just `er_period`** — Saqib flagged this himself in the brief; confirmed and made a first-class config field (converted internally to `fastSC`/`slowSC`) rather than a hardcoded 2/30.

    **Normalization reference resolved as local intraday volatility (stdev of the same regression/KAMA window's closes), not the daily ATR family** — normalizing a 1-minute slope against a whole-day ATR range would need an unstated cross-timeframe unit conversion; stdev of the window itself is self-contained and scales correctly for both a low-priced/low-volatility stock and a high-priced/high-volatility one, which was the actual goal.

    **ATR(1D,14) reuses Daily Levels' existing daily-candle fetch (proposed, flagged as D1, not yet confirmed) instead of a second Polygon call per symbol per day** — Daily Levels (decision #59/#60) already caches up to 180 days of full-OHLCV `1d` candles per symbol, refreshed once per `(symbol, ET day)`; ATR(14) only needs the most recent 15 of those. Proposed as a shared `self._daily_candle_cache[symbol]` extraction rather than either duplicating the fetch or reaching into Daily Levels' private state field directly — a real, scoped touch to existing Daily Levels code, called out explicitly for sign-off rather than done quietly, with a documented one-line reversal to full independence if Saqib prefers zero coupling.

    **Look-ahead policy needed no new philosophy — reused the exact rule `_update_previous_day` already established for PDH/PDL/PDC (decision #56):** ATR only ever uses complete daily bars strictly before today, recomputed once per `(symbol, ET day)`, never today's still-forming bar. Directly resolves the brief's "no accidental look-ahead" requirement by following existing precedent instead of inventing a second timing model.

    **`indicators/regression.py`** — OLS fit of the trailing `period` closes against an equally-spaced bar index. Two degenerate-case conventions spelled out rather than picked silently, and deliberately opposite from each other: a perfectly flat window still publishes `r2 = 1.0` (a constant series is trivially, perfectly explained by its own mean — residuals are all exactly 0 too) while omitting only `_slope_norm` (its own denominator, the window's close stdev, is 0); KAMA's own Efficiency Ratio (below) takes the OPPOSITE convention for its own 0/0 case, mapping to the WORST value (0) rather than the best — both documented in-place so neither reads as an oversight.

72. **LiveTickRelay — throttled "tick fluidity" for the chart's currently-forming 1m bar, on a small (max 8), explicitly-set active-symbol set. New standalone Event Bus subscriber, not an extension of `TickIngestBridge`.**

    **The ask, pinned down over several turns:** show the CURRENTLY FORMING candle breathing with real trades rather than only jumping once a minute — not a new candle resolution (a separate, still-open idea from earlier in the same discussion, deliberately not built here), and not full-tick-rate pushes to the frontend. Final shape: at most one update per symbol every 5 seconds (`flush_interval_seconds`, configurable), across at most 8 symbols at a time (`max_active_symbols`) — sized for "whatever a scanning process currently flags as most active," not the full ~100-symbol universe. Which 8 symbols are active is explicit and external to this component: `set_active_symbols()` / `POST /market/active-symbols`, callable by anything (a manual call today; Market Scanner once it exists) — LiveTickRelay itself has no opinion on how the 8 are chosen.

    **Deliberately NOT built into `tick_ingest.py`.** That module is explicitly documented (decision #16) as Phase-3-throwaway, "replaced wholesale, not extended" once the real Phase 4 Market Data Engine exists. A throttle patched into its internals would be a direct, avoidable conflict with that decision. Instead, `live_tick_relay.py`'s `LiveTickRelay` is a second, fully independent subscriber to the SAME `PriceUpdated` events `TickIngestBridge` already publishes — its own per-symbol bar accumulator (`_LiveBar`), its own minute-rollover detection (computed the same way `TickIngestBridge` does, but independently — no shared state, no import of its internals). Zero coupling either direction: `TickIngestBridge` can be replaced wholesale later without this file changing, and this file can be deleted or folded into the real Market Data Engine without touching `tick_ingest.py`.

    **New EventType (`PRICE_SNAPSHOT`) and its own channel (`market.tick.snapshot`), not reused on the existing `market.tick`.** `market.tick`/`PriceUpdated` already has a real consumer at raw-tick frequency — `useLatestPrices` (the watchlist). Throttling that same channel to 5s would have silently changed the watchlist's update rate as a side effect of a chart-only feature. `PriceSnapshot` (schemas/events/market_data.py) deliberately mirrors `CandleClosed` field-for-field (open/high/low/close/volume/candle_ts/timeframe) rather than reusing that model directly — same reasoning as decision #15's Tick-vs-PriceUpdated split: conflating "closed" and "in-progress" into one type would make every future `CandleClosed` consumer newly responsible for checking which kind it received. The matching field shape is what lets the frontend reuse `toCandle()` (api-client.ts) and the chart's existing `update_last` path with zero new type plumbing.

    **Honest-state discipline applied at 5s granularity, same convention as everywhere else in this codebase:** a symbol with no new ticks since the last flush is skipped that cycle, never re-published as a stale duplicate (proven directly in `test_quiet_symbol_is_not_republished_on_the_next_flush`) — no fabricated flat bar, ever. A minute rollover starts a genuinely fresh bar rather than carrying over the prior minute's high/low/volume (`test_minute_rollover_starts_a_fresh_bar_not_a_carried_over_one`). `set_active_symbols()` rejects (`ValueError` → `400`) rather than silently truncates a set larger than `max_active_symbols` — a caller expecting all N symbols tracked finds out immediately, not via a buried log line.

    **Frontend: `useLiveCandles` gained an optional `liveTick` param (`SubWindowConfig.liveTick: boolean`, decision #72), and a real pre-existing gap got fixed as part of wiring it in.** The hook's `candles` array previously only ever held CLOSED bars — nothing represented the in-progress bar at all, so a naive "subscribe to `market.tick.snapshot` and update the last element" wouldn't have worked correctly the first time a new minute's first snapshot arrived (there'd be no matching last-element timestamp to revise). Fixed with a shared `_upsertLast` helper — same-timestamp revises in place, newer-timestamp appends provisionally, older/stale is dropped — used by BOTH the snapshot handler AND the existing `market.candle` (`CandleClosed`) handler, which previously did an unconditional append. That append had to change too: once a provisional snapshot bar can already occupy the array's last slot, the real `CandleClosed` for that same minute must replace it, not duplicate it, or `liveTick` would produce visibly doubled bars on every close. `ChartWidget.tsx` itself needed NO changes — its existing `diffCandles`/`update_last` logic (confirmed by reading it directly before writing any of this) already handles a same-length, same-last-timestamp array revision correctly.

    **UI: "Tick" lives in the same Timeframe menu list as 1m/5m/15m/1h/4h/1d (`SubWindowMenu.tsx`), not a separate section** — matches how it was actually asked for ("alongside timeframes... where logically suited best"). Selecting it sets `{ timeframe: "1m", liveTick: true }` together in one call; selecting any real timeframe sets `liveTick: false` — the two can never end up in an inconsistent combination through the UI. `useLiveCandles` also defensively no-ops the tick subscription if `timeframe !== "1m"` at the moment a snapshot arrives, rather than trusting that pairing to always hold.

    **Tested at the same tiers as the rest of this codebase:** 6 new tests in `test_live_tick_relay.py`, real in-process `EventBus` (not mocked), matching `test_tick_ingest.py`'s own style — throttled-collapse-to-one-snapshot, inactive-symbol-never-published, quiet-symbol-not-republished, minute-rollover-fresh-bar, over-max rejection, and removed-symbol-drops-its-bar. All 6 pass; full suite (excluding the Postgres-dependent tests, no local DB in this sandbox) shows zero regressions. `conftest.py`'s singleton-reset fixture (decision #38's own fix) was extended to also reset `live_tick_relay._live_tick_relay` — the same event-loop-binding hazard that fixture already exists to prevent for `_event_bus`/`_feature_engine`/`_level_interaction_engine` would otherwise apply here too the first time a route-level test exercises `POST /market/active-symbols` through the real app lifespan. `npx tsc -b` (filtered for the known pre-existing `GridPresetPicker` errors) and `npx vite build` both clean.

76. **Dropdown-panel clipping fixed for all 5 real panels in the app — a shared placement hook (`useDropdownPlacement.ts`) replaces the earlier flat `max-h-[80vh]` fix, which was insufficient.**

    Saqib reported the HUD panel (and others before it — this had been patched once already) getting cut off mid-content with no scrollbar visible, screenshotted from a bottom-row sub-window. Root cause, confirmed by reasoning through the actual CSS rather than guessing: every dropdown in this app is `position: absolute; top-full` anchored to a `position: relative` wrapper. The existing fix (`max-h-[80vh] overflow-y-auto` on `SubWindowMenu`'s panel) caps the panel's OWN height, but does nothing about WHERE it's anchored — a sub-window near the bottom of a busy grid has its toolbar already most of the way down the viewport, so "80% of the viewport" measured from there still runs well past the bottom of the screen. `overflow-y-auto` only produces a scrollbar when content exceeds the panel's own max-height box, not when the panel itself is positioned beyond the visible viewport — which is exactly what was happening; no scrollbar ever appeared because the panel wasn't "too tall for its own box," it was simply positioned off-screen.

    One shared hook rather than 5 copies of flip/measure logic: `useDropdownPlacement(open, anchorRef)` measures the anchor's real `getBoundingClientRect()` when the panel opens (and on resize/scroll while open), and picks whichever direction — down or up — has more room, capping `maxHeight` to the ACTUAL remaining space in that direction rather than a fixed viewport fraction. Every consumer still keeps `overflow-y-auto` on the panel itself, since the hook only picks a better anchor point and an accurate ceiling — that class handles the case where even the larger of the two directions still isn't enough (e.g. a very short browser window). Deliberately biased toward "down" (matching every panel's existing markup, so the common case renders identically to before) unless there's genuinely not enough room and "up" offers meaningfully more, avoiding flip-flopping right around the screen's midpoint.
