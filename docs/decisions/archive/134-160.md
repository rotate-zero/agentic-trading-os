### 134. Backtest Panel and Backtest Results Panel linked by shared run_id — no more copy-paste

Both `BacktestPanel.tsx` (decision #131's frontend, the trigger) and `BacktestResultsPanel.tsx` (decision #133, the viewer) already worked independently; `useBacktestOutcomes.ts`'s own docstring named the gap explicitly ("triggered from a separate, unlinked panel per this task's own scope, so a manual refresh is the only way to see a just-finished run's rows"). This closes exactly that connection. Frontend-only — no backend/API change, no new route, no wire-shape change.

New shared state: `WorkspaceContext.tsx`/`MainWindowState.lastBacktestRunId` (`string | null`) + `setLastBacktestRunId`, modeled directly on `featureEnginePanelSymbol`'s own established "one panel writes, a sibling reads" pattern (decision #48) rather than a new mechanism (no new context, no event bus, no prop drilling through `App.tsx`). Scoped per-Main-Window, same as `featureEnginePanelSymbol`, since both panels are mounted once per active-window shell (`App.tsx`), not globally or per-sub-window — each Main Window tab tracks its own "most recent run." Persisted via the existing session-autosave path like every other `MainWindowState` field; `normalizeMainWindow()` back-fills `lastBacktestRunId: w.lastBacktestRunId ?? null` for sessions saved before this field existed, same convention `normalizeSubWindow()` already uses for its own fields.

`BacktestPanel.tsx`'s `BacktestForm` calls `setLastBacktestRunId(result.run_id)` in a `useEffect` keyed on `status === "done" && result` — the exact same moment it already renders that value in `ResultsView`, not a separate action. A plain, non-interactive note ("→ prefilled ... in the Backtest Results panel") was added next to the rendered run_id instead of a clickable "View in Results" link: the Results panel's own collapsed/width state is deliberately local component state, not threaded through `WorkspaceContext.tsx` (that panel's own header comment, unchanged by this decision) — making the run_id notification "actionable" would mean either reversing that local-state design for a convenience this task didn't ask for, or inventing a second, narrower coupling beyond the one piece of state this decision actually needed. Automatic prefill alone was judged sufficient; both options were explicitly defensible per this task's own scope.

**The one real design decision this task called for, stated explicitly rather than defaulted:** `lastBacktestRunId` is a DEFAULT for the Results panel's filter, never a forced value, and a run finishing elsewhere must never silently overwrite an in-progress manual lookup. Resolved with a small two-state mode machine local to `BacktestResultsBody`: it starts in `"auto"` (seeded from whatever `lastBacktestRunId` already is at mount, then continuously re-synced via a `useEffect` keyed on `[lastBacktestRunId, mode]`) and switches to `"manual"` the instant the person clicks Apply OR Clear — both are real, deliberate manual choices (Clear's own "show everything" is itself a choice, not a reset back to auto) — after which further runs finishing elsewhere update the shared value (so `BacktestPanel.tsx`'s own "prefilled" note stays true) but never touch this panel's own filter again. A small explicit "↺ Follow latest run" control is the only way back to `"auto"`; collapsing/re-expanding the panel would also reset it (the component unmounts on collapse) but isn't a discoverable way to ask for that, so the explicit control was added rather than relying on the side effect.

A useful, unplanned side effect: `useBacktestOutcomes.ts`'s own `[limit, backtestRunId]` dependency array was already reactive before this task and needed no changes — so once `"auto"` mode syncs `appliedRunId` to a newly-finished run, the hook's existing refetch logic fires on its own. Since `POST /backtest/run` is fully synchronous and only resolves after its own `StrategyOutcome` rows are already written (decision #128), this means the "manual refresh is the only way to see a just-finished run's rows" half of the original gap is *also* closed while a person is auto-following — not just the copy-paste half this task was framed around. Manual "Refresh" remains meaningful outside that path (a run triggered from a different tab/operator, or while pinned to a different run_id manually) — `useBacktestOutcomes.ts`'s own docstring updated to state this precisely rather than leave the now-stale "only way" framing in place.

Docs: `useBacktestOutcomes.ts`'s docstring corrected (see above). `strategy-engine-design.md` §7 gained one new as-built note with two diagrams — cross-component data flow (`BacktestPanel` → `WorkspaceContext` → `BacktestResultsPanel`) and the internal auto/manual mode state machine inside `BacktestResultsBody` — per this task's own diagram requirement.

### 135. Closed the historical-provider gap in Backtest Runner replay — `volume_regime_score`/`volatility_regime_score` were structurally always `0.0` in any replay, for any symbol; four of the seven v1 strategies (ORB, Gap, Volume Spike, Momentum) hard-gate MATCH on `volume_regime_score >= 45.0` and could never fire in a backtest as a result.

Named directly in decision #128's own diagram and restated in `scenarios.py`'s own module docstring as a real, confirmed-by-direct-execution ceiling, not a hypothetical. Root cause: `FeatureEngine`'s Daily Levels/ATR/RVOL refresh (`_maybe_refresh_daily_levels`) reads `self._daily_candle_cache`, populated exclusively via `broker_registry.get_historical_provider().get_historical(symbol, "1d", ...)` — a process-wide global `BacktestRunner` never touched, so this cache never populated during any replay, structurally, regardless of how a scenario's own candles were built.

    **The one real fork, presented to Saqib rather than resolved silently, with a recommendation and reasoning.** Two structurally different seams were possible: (1) a save/install/restore seam on `broker_registry`'s historical role, mirroring `engine_singleton_guard.py`'s already-accepted shape exactly, touching zero core engine files; or (2) a new optional constructor parameter on `FeatureEngine` itself, additive at the call-site level but requiring edits to `feature_engine/engine.py` AND `replay_state_producer.py` (which constructs `FeatureEngine` directly, with no such parameter today). Recommended (1), with reasoning checked against the real code rather than assumed: grepped every real call site of `broker_registry.get_historical_provider()` outside `feature_engine/engine.py` itself — exactly three, two of which are identity-comparison-only reads (`main.py`/`market_data.py`), and one real live-facing read (`GET /market/candles`, `market.py`), which gates on `adapter.is_connected()` before ever calling `get_historical()`. Since `FeatureEngine` itself never checks `is_connected()` (only `is None`), and the installed seam deliberately never calls `.connect()`, that live route keeps returning its existing honest 400 throughout a backtest run — no silent fixture-data leak, by construction. Decision #132's Finnhub/Polygon 409 already means `broker_registry`'s historical role is unclaimed going into every valid backtest run today. Saqib confirmed: go with (1).

    **A second, genuinely separate finding surfaced during this same investigation, also presented rather than resolved silently, with three concrete options and a recommendation.** Confirmed by direct execution against a real Postgres, not assumed: `_maybe_refresh_daily_levels()`'s real, unmodified `_reconcile_and_persist_daily_levels()` — reachable for the first time ever once ANY historical-provider seam exists, regardless of which of the two fork options above — writes real rows into the SAME shared `symbols`/`daily_levels_state` tables live trading reads, under whatever `symbol` label the caller supplies to `POST /backtest/run`, with no `is_backtest` flag on either table (unlike `strategy_outcomes`/`backtests`). Concretely: a second run against the identical `(symbol, scenario)` pair silently reverts `volume_regime_score`/`volatility_regime_score` to `0.0` for that run, since `_maybe_refresh_daily_levels()`'s own pre-existing "restart-survival" short-circuit finds the first run's persisted row and skips the raw-candle-cache population before ever asking the provider again — proven directly: RUN1 showed 119/119 `market_state_history` rows with non-zero scores, RUN2 (same symbol, same scenario, immediately after) showed 0/119 non-zero for its own rows. Three options presented: (a) accept and document loudly, (b) have `BacktestRunner` clean up the rows it caused in a `finally`, (c) flag as a new open item and ship (a) only. Recommended (a) + flag as a new D-item, given this session's own scope is "close the historical-provider gap," not "namespace backtest writes into shared live-trading state." Saqib confirmed: go with it. Documented prominently in `backtest.py`'s own route docstring (the disclosure a caller actually needs before picking a `symbol` label) and as new open item **D18** in `strategy-engine-design.md`'s D-items table — not resolved here.

### 140. D18 resolved — live/backtest namespaces isolate replay persistence for the same ticker

Decision #135's historical-provider seam made Daily Levels/ATR/RVOL work during replay, but also exposed D18: a backtest using a real ticker wrote through the same `symbols` and `daily_levels_state` identity live trading used. The first replay could mutate or archive live Daily Levels; the next identical replay found that persisted checkpoint, skipped the provider fetch and raw daily-candle-cache population, and reverted `volume_regime_score`/`volatility_regime_score` to `0.0`.

**The fork was presented before implementation.** Option (b) was `BacktestRunner` cleanup in a `finally`; option (c) was real `is_backtest` namespacing, following the `strategy_outcomes`/`backtests` precedent. Option (c) was chosen. The source trace showed that cleanup was not actually the smaller or safer change: a replay-created `symbols` row can be referenced by `daily_levels_state`, `market_state_history`, `level_interaction_state`, `level_interaction_events`, `candles`, `scanner_universe_symbols`, and `symbol_fundamentals`, so deleting it requires a cross-table cascade. If the ticker already exists live, reconciliation can update or archive existing live rows, requiring a full snapshot-and-restore rather than deletion. Synthetic state would remain visible throughout the run, restoration could overwrite a concurrent live update, and process termination before `finally` would leave the contamination behind. Namespacing prevents the wrong rows from being selected or written in the first place.

**Schema and replay behavior.** Migration `0009_backtest_symbol_namespace.py` adds non-null `is_backtest` columns to `symbols` and `daily_levels_state`, backfilling every existing row to `false`. Symbol identity is now unique on `(ticker, is_backtest)`. A composite `(symbol_id, is_backtest)` foreign key from `daily_levels_state` to `symbols` enforces matching origin at the database boundary. `EngineBackedReplayStateProducer` constructs its Feature, Market State, and Level Interaction engines with `is_backtest=True`; their normal constructors default to live. Backtest Feature Engines deliberately skip the live restart-survival checkpoint read at the beginning of each run so every replay fetches its own daily fixture history and repopulates ATR/RVOL's raw cache. Downgrade removes replay-derived rows before restoring the legacy one-row-per-ticker constraint because the old schema cannot represent both namespaces; live rows remain and re-upgrade backfills them to `false` again.

**Every real lookup site was found before code, not inferred from subsystem names.** A fresh grep identified nine production files, and every read/insert now selects its namespace explicitly: `backend/app/feature_engine/engine.py`, `backend/app/market_state_engine/engine.py`, `backend/app/trading_intelligence/level_interaction_engine.py`, `backend/app/scanner/universe.py`, `backend/app/services/candle_recorder.py`, `backend/app/services/candle_store.py`, `backend/app/context_engine/engine.py`, `backend/app/context_engine/fundamentals_refresh.py`, and `backend/app/context_engine/providers/fundamentals.py`. Each has a real-Postgres regression with simultaneous live and backtest rows for the same ticker, proving the default path returns only the live row rather than merely re-testing the old live-only case.

**Validation, real PostgreSQL.** The unchanged pre-change baseline was 728 passed / 0 failed. The final suite was 737 passed / 0 failed — exactly nine new lookup-site regressions and the same zero-failure signature. A strengthened end-to-end regression seeded a live Daily Levels sentinel, ran the identical replay twice against the same ticker, confirmed the sentinel stayed unchanged, confirmed distinct live/backtest symbol identities, and confirmed both runs retained non-zero volume and volatility regime scores. Migration `0009 → 0008 → 0009` passed with both namespaces present: downgrade preserved only the live symbol/level rows and removed the new columns; re-upgrade restored the columns and backfilled the surviving rows to `false`. A fresh-main overlay showed exactly 19 changed files, all under `backend/`.

**Complete implementation footprint (19 files).** New: `backend/alembic/versions/0009_backtest_symbol_namespace.py`, `backend/tests/test_symbol_namespace.py`. Modified: `backend/app/api/routes/backtest.py`, `backend/app/backtest_runner/replay_state_producer.py`, `backend/app/backtest_runner/runner.py`, the nine lookup files listed above, `backend/app/models/market_data.py`, `backend/app/models/daily_levels.py`, `backend/tests/test_backtest_runner_regression.py`, `backend/tests/test_daily_levels.py`, and `backend/tests/test_fundamentals_provider.py`. ### 141. D19 resolved — Daily Levels backtest state is isolated by run_id

Decision #140 correctly separated live and backtest persistence for the same ticker, but a narrower gap remained inside the backtest namespace. `_reconcile_and_persist_daily_levels()` selected active rows by `(symbol_id, is_backtest, status)` only. Direct execution of two identical runs with distinct `run_id` values confirmed that run 2 reused all ten database rows and `level_id` values minted by run 1 and advanced every row's `updated_at`; a changed cluster set could likewise update prices/strengths or archive run 1's unmatched rows. Decision #140's existing live-sentinel/non-zero-regime regression passed unchanged. Migration `0010 → 0009 → 0010` passed: downgrade removed the column and restored the old index while preserving live and backtest fixture rows; re-upgrade preserved the live row, removed only the unassignable backtest Daily Levels row, retained its unrelated `backtests` record, and restored the FK, CHECK, and widened index. Focused affected modules passed 30 tests; Python compilation and diff whitespace checks passed.

Reproduced the mechanism standalone before touching any app code (mirroring decision #84's own verification method): a worker loop wrapping a real blocking call in `asyncio.to_thread`, cancelled mid-flight, returns in ~0ms while the real work keeps running detached — versus a poison-pill drain, which genuinely blocks until the real work finishes.

This is the concrete mechanism behind this file's own already-documented "async-timing race in Feature Engine cold-start backfill" lead: `FeatureEngine`'s worker loop does an UNCONDITIONAL `asyncio.to_thread` DB read (`_load_confirmed_daily_levels_for_today`, part of `_maybe_refresh_daily_levels`'s restart-survival check) on literally every never-before-seen (symbol, day) — independent of whether Daily Levels is even relevant to the test — and with `nproc=1` in this sandbox, the default `ThreadPoolExecutor` has only ~5 worker slots. Because the queue is strict FIFO, the sentinel is only ever dequeued after everything genuinely ahead of it — including an item already mid-`to_thread` — has fully finished. No timeout-then-cancel fallback, deliberately, matching #84's own explicit trade-off: correctness over shutdown latency for a background DB reader/writer.

- Fixture scenarios only — `/backtest/run/ibkr`'s real-data path is explicitly out of scope; a single IBKR acquisition already costs real minutes (#145), so looping that synchronously would be impractical.

**Execution model — no new locking mechanism.** Each `(symbol, scenario)` pair goes through the identical `BacktestRunner.run()` → `install_replay_engines()` → `engine_singleton_guard._RUN_LOCK` path `/backtest/run` already uses, acquiring and releasing that same process-wide lock once per run. Proved empirically, not just asserted: a test wraps the real `install_replay_engines` context manager with a timing spy (still delegating to the real implementation) across a multi-pair sweep and asserts the recorded lock-hold intervals never overlap.

**`sweep_id` threading — a small, additive constructor change, confirmed by inspection before building anything larger.** `BacktestRunner.run()` already minted its own `sweep_id = uuid4()` locally. `__init__` now accepts `sweep_id: UUID | None = None`, resolving to a fresh `uuid4()` when omitted and to the caller's value otherwise (`self._sweep_id = sweep_id if sweep_id is not None else uuid4()`); `run()` reads `self._sweep_id`. Every existing caller passes nothing and is unaffected — confirmed via the full existing backtest suite, unchanged pass count (783, matching #157's own reported figure) before the two new unit tests were added.

**A fresh `Strategy` instance per pair, not one reused across the loop — confirmed necessary, not assumed.** Read all 7 real strategy implementations directly: each holds `self._state: dict[str, ...]` keyed per symbol (`ORB`, `Gap`, `Volume Spike`, `FirstPullback`, `Reversal`, `Momentum`, `VWAP`). Reusing one instance across pairs would let one pair's per-symbol state leak into a later pair reusing the same symbol against a different scenario. Each pair instead calls `default_registry(now)` fresh and picks the matching strategy by name — the same mechanism `/backtest/run` already relies on per-request (confirmed `default_registry()` builds fresh instances every call, no caching).

**Partial-failure handling — decided from real precedent already in this codebase, not invented.** Pre-execution validation (strategy name, every requested scenario, batch size, non-empty lists) rejects the whole request before any run starts. Once execution begins, a genuine per-pair error (distinct from an honest `outcomes_recorded=0`, which is expected and not an error) is caught, logged, and recorded against that pair in the response — the loop continues, and every already-succeeded pair's real result is preserved. This mirrors an existing convention for independent-item batches found by inspection rather than assumed: `FeatureEngine`'s worker loop ("one bad symbol/candle must not stall the other ~100") and `websocket/manager.py`'s broadcast ("a dead socket must not break the broadcast"). Verified with a real test that forces a genuine failure (via a narrow, deterministic monkeypatch on candle loading — everything else runs through the real `BacktestRunner`/lock path) partway through a 4-pair sweep: the pair requested after the failure still completes for real, and only the two real successes land in `backtests`.

**The live-trading guard (#132) is checked once before the sweep starts, not per pair** — the same standard `/backtest/run` itself already applies (a single run's own several-second replay doesn't re-check mid-run either), so treating a sequence of those same runs identically is consistent, not a new weaker rule invented for sweeps.

**Response ordering is deterministic by construction.** `runs[]` is built by appending inside `itertools.product(symbols, scenarios)` (symbols outer, scenarios inner) — never re-sorted, never read back from the database in query order.

**A second, deeper finding surfaced during test verification — real, pre-existing, and out of this task's scope to fix.** Running the *same symbol* through two separate real runs can legitimately produce different `outcomes_recorded` between them — confirmed to have nothing to do with sweep code specifically: calling the existing, unmodified `POST /backtest/run` twice in a row against one fresh symbol reproduces the identical discrepancy (1, then 0). Root cause, confirmed by reading the models rather than assumed: `daily_levels_state` got per-run isolation via `backtest_run_id` (#141/D19), but `LevelInteractionState`/`LevelInteractionEvent` never did — `LevelInteractionState`'s own unique constraint is `(symbol_id, timeframe, level_key)`, with no `backtest_run_id` column, so a second run of the same symbol inherits real leftover touch/resolution state from the first. Not fixed here — a fix would mean giving those two tables the same per-run-isolation treatment D19 gave `daily_levels_state`, a change of that shape and size, and `strategy-engine-open-decisions.md` is this delivery's own parallel-session boundary, not touched. Flagged to Saqib directly; likely a new D-item for whoever owns that file next. The new test suite is written around this finding rather than papering over it — no test asserts that two real runs of the same symbol reproduce identical outcome counts.

**Route, response shape, validation.** `POST /backtest/sweep(strategy_name, symbols[], scenarios[])`, query-params style matching `/backtest/run`'s own convention (no request body used elsewhere in this file). `strategy_name`/each unique `scenario` validated via the exact `_validate_strategy_name()`/`_validate_scenario()` `/backtest/run` already uses — reused, not duplicated. `symbols` normalized (`.strip().upper()`, matching `/run`'s own convention) and rejected if empty after normalization; no real symbol registry exists to validate against (confirmed directly: `/backtest/run`'s own `symbol` param is documented as "an arbitrary label … not a real ticker lookup," unchanged here). ### 160. D20 resolved — Level Interaction persistence is isolated per backtest run

Decision #159 confirmed the defect through two independent calls to the existing `POST /backtest/run`: the same fresh symbol/scenario recorded one outcome on run 1 and zero on run 2. `LevelInteractionState` was a mutable checkpoint unique only by `(symbol_id, timeframe, level_key)`, so every replay in the same backtest Symbol namespace shared it. `LevelInteractionEvent` did not cause the inherited-state behavior, but its append-only rows likewise lacked run attribution.

**Database shape.** Migration `0011_level_interaction_backtest_run_isolation.py` adds `is_backtest` and nullable UUID `backtest_run_id` to both tables. Each row has a composite `(symbol_id, is_backtest)` FK to `symbols`, plus a CHECK requiring exactly live/NULL or backtest/non-NULL. Each run FK targets `backtests.run_id` with `ON DELETE CASCADE`: these checkpoints/events are replay-derived artifacts owned by the run, unlike durable `strategy_outcomes`. State's old unique constraint is replaced by two PostgreSQL partial unique indexes: `(symbol_id, timeframe, level_key)` for live rows and `(symbol_id, timeframe, level_key, backtest_run_id)` for backtest rows. This preserves live singleton semantics without relying on nullable-UUID uniqueness. Events remain append-only and receive no state-style uniqueness; both tables have partial run-ID indexes for run-scoped reads and cleanup.

**Legacy and downgrade policy.** Origin is backfilled from the related namespaced Symbol. Existing backtest Level Interaction rows cannot be assigned honestly to a run, so upgrade removes only those derived rows and preserves live rows. Downgrade removes replay state and events before dropping attribution and restoring the old state uniqueness constraint; otherwise multiple isolated runs for one backtest symbol could not fit the legacy schema, and retained events would lose honest provenance. A real PostgreSQL `0010 → 0011 → 0010 → 0011` exercise passed with legacy live/backtest fixtures and two post-upgrade runs sharing the same symbol/key.

**Runtime flow.** `LevelInteractionEngine` now enforces `is_backtest == (backtest_run_id is not None)` at construction. Cold-start load, state lookup/upsert, and event append all bind the engine's exact origin and run scope. Live singleton construction remains `(False, None)`. `EngineBackedReplayStateProducer` passes its already-required UUID to both Feature Engine and Level Interaction Engine. `BacktestRunner` is unchanged: it already minted the UUID, constructed the producer with it, and persisted the parent `BacktestRunRecord` before advancing the first candle.

**Regression proof.** The new route regression was written and run before the production fix and failed exactly `[1, 0]`; after the fix, the same two real calls return `[1, 1]` with distinct run-owned state IDs, directly inspected checkpoint fields, and correctly attributed event rows. The duplicate same-symbol sweep regression now proves the same isolation. Additional real-Postgres coverage checks constructor and database invalid combinations, live NULL-run behavior, namespace matching, producer threading, and deletion of one run without affecting live or another run.
