107. **First Pullback and Reversal — design note locked (Stage 0, no code) — the last two strategies from trading-intelligence-architecture.md §8's planned v1 set (ORB, Gap, Volume Spike built; Momentum still assigned elsewhere).** Full walkthrough, diagrams, and open items: `strategy-engine-design.md` §16. Both read `LevelInteractionEngine`'s touch/holding/rejected/conquered vocabulary (decision #46) as a settled input, the same "consume, don't rebuild" boundary discipline `orb_strategy.py` already applies to Market State's `trend_score`/`volume_regime_score` — neither strategy re-derives zone classification, Aura width, or touch counting itself.

    **First Pullback — is this the trend's first pullback to a key reference level today, and did the level hold?** GATE requires an established trend (`trend_score` past `trend_score_threshold`, same mirror-around-50 convention and `>50` guard as `match_direction()` in `orb_strategy.py`/decision #99) and `touch_count_today == 1` for the configured `level_key` (a `StrategyConfig.params` value, v1 default `"vwap"` — same "not its own strategy class" precedent §3 already sets for SMA 9/20). MATCH confirms the touch resolved back out the side it entered from (REJECTED, `LevelInteractionEngine`'s own definition) in the trend's favor; a touch that resolves CONQUERED (opposite side) is a non-match, not an error. Fires at most once per symbol per day.

    **Reversal — has an established trend's key level just been conquered against it?** Same touch-tracking mechanism, opposite confirming outcome: MATCH fires when a touch resolves CONQUERED while `trend_score` still shows the OLD, about-to-be-broken direction — deliberately not gated to the first touch only (`touch_count_today` read for SCORE, never gates MATCH), since a reversal is often the second or third test that finally breaks, not the first. Direction is the mirror of the trend being broken (an established uptrend conquered downward proposes SELL).

    **Real gap found and resolved without changing `base_strategy.py` (§10's new D9).** Neither strategy can read `LevelInteractionEngine`'s own `status` field (`"rejected"`/`"conquered"`) directly — that field only exists on the transient `LevelInteractionChanged` event; `get_snapshot()` (decision #47) exposes only the current steady `zone`, already moved on by the time a resolution is visible. Subscribing to `LevelInteractionChanged` directly would need `on_event(...)` triggers wired to a live Scheduler that doesn't exist — `base_strategy.py`'s own docstring already flags that Scheduler as unbuilt, downstream integration work no v1 strategy (ORB/Gap/Volume Spike, all `every_candle`) has needed yet. Rather than build that wiring for two strategies ahead of need, both call `get_level_interaction_engine().get_snapshot(symbol)` directly inside `evaluate()` — the same free-function-singleton pattern `orb_strategy.py` already uses for `get_market_clock()` — and re-derive rejected-vs-conquered themselves, one candle late, from their own private per-symbol state remembering `entered_from` while `zone == "inside_aura"`, then comparing it to whatever zone the level resolves to on a later candle. Deliberately does NOT read `get_snapshot()`'s `seconds_in_zone` field: computed off wall-clock `datetime.now()` (`level_interaction_engine.py`'s own `get_snapshot()`, built for the UI panel, decision #47), not `features.candle_ts` — reading it inside `evaluate()` would violate §7's backtest-safety invariant. Neither strategy's MATCH logic needs it.

    **`allows_waiting` stays `False` for both, v1.** First Pullback's "touch just started, not yet resolved" moment is a natural fit for a `status="waiting"` Opportunity (§8's ACT/WAIT/ABANDON model) rather than silently returning `None` until resolution — but D5 (the waiting-value model itself) is explicitly deferred until a real strategy needs it, and no strategy has triggered that yet. Flagged rather than built speculatively: First Pullback would be the first real trigger for D5, not decided here.

    **Still Stage 0 — no application code.** `first_pullback_strategy.py`/`reversal_strategy.py` and their tests are the next session's work on this thread.

108. **First Pullback/Reversal design review incorporated, and `LevelInteractionEngine.get_snapshot()` gains a `last_applied_candle_ts` field — both before any strategy code was written.** Full response to each review point: `strategy-engine-design.md` §16, "What the design review changed."

    **Two real gaps found by inspecting the actual engine implementation, not assumed equivalent.** The review asked for the touch-resolution reconstruction (decision #107) to be checked against `LevelInteractionEngine`'s own logic rather than trusted on the original sketch's word — doing so found it wasn't equivalent as drafted. **Gap-through** (price jumps straight between `below`/`above`, `inside_aura` never observed — the engine still counts it as a touch and always calls it `conquered`) was invisible to the original design, which only started watching on an `inside_aura` observation. **Cold-start-unknown-origin** (`entered_from is None`, the engine's own "can't determine which side," decision #46) would have been silently guessed at rather than left unclassified. Both fixed in a new shared module, `level_touch_tracking.py` — see its own module docstring for the exact mechanism — used by both strategies rather than duplicated, since two independent copies of "what counts as rejected vs. conquered" was the exact risk the review was checking for.

    **A third, more serious issue, not raised by the review, found by reading `_worker_loop`/`_process_one` directly: `get_snapshot()` is fed by an async queue + `asyncio.to_thread` worker, not computed synchronously on the triggering `FeaturesUpdated`.** No built-in guarantee a strategy's read reflects the candle it's currently evaluating, and — unlike Context Engine's own `get_snapshot()` (`evaluated_at`) — no recency field existed to detect this. Resolved with a small additive fix: `get_snapshot()` now exposes `last_applied_candle_ts` per entry, sourced from `_last_applied_ts`, a value the engine already tracked internally for its own out-of-order guard, just not previously surfaced. Backward-compatible (additive field only); full existing suite re-run clean against this change before any strategy code touched it. Both strategies check this field before calling into `level_touch_tracking.py` at all, skipping the candle entirely on a stale read rather than feeding it through the tracker (which would corrupt the tracker's own zone history — see that module's docstring).

    **MATCH/SCORE boundary and invalidation framing tightened per the review, confirmed elsewhere.** `volume_regime_score`/resolution-distance/touch-count were already SCORE-only in the original sketch (flagged in both strategies' docstrings as a deliberate divergence from `orb_strategy.py`'s own MATCH-stage volume floor — not retrofitted onto ORB/Gap/Volume Spike, an open question for later). `structural_invalidation = anchor_price` unchanged, but both docstrings now state explicitly it's a thesis boundary ("falsified if a later candle closes back through this value"), not an executable stop price — that translation is Trade Planning Engine/Position Monitor's job, neither built yet. `base_strategy.py` untouched throughout, per the review's own point 3 — the `get_level_interaction_engine().get_snapshot()` polling pattern (D9) stands as designed.

111. **Gap/Volume Spike design review's agreed changes made — six items, spanning `base_strategy.py`, `feature_engine/engine.py`, `gap_strategy.py`, `volume_spike_strategy.py`, and (discovered mid-change) `orb_strategy.py`/`first_pullback_strategy.py`/`reversal_strategy.py`.** Follows a structured design-level review of decisions #104/#105 (full review preserved in this session's own record, not duplicated here — this entry covers what changed and why, not the review's full reasoning). Six items, all six made:

    **1 — `regular_open` published by Feature Engine, no longer reconstructed.** The review's §1 questioned `gap_strategy.py`'s own `regular_open = pdc + gap_dollars` algebra: a generic market fact (same category as `pdc`/`pdh`/`pdl`, already published), reconstructed only because Feature Engine tracked it internally (`_update_gap`'s own state) without exposing it — an ownership smell, not a hard boundary violation. `_update_gap` now publishes `regular_open` as its own `features` key, independent of `gap_pct`/`gap_dollars` (known the moment today's regular session opens, even without a prior day to compare against). `gap_strategy.py` reads it directly; the reconstruction is gone.     **2 — Gap bounded to a maximum age since the open (`max_minutes_since_open`, v1 default 60, unvalidated).** The review's §2 found nothing previously stopped a match hours after the open — a 2pm reclaim of `regular_open` read identically to a clean 9:30 hold. "Gap and go" is conventionally early-session; unbounded, Gap would only grow more redundant with Momentum/VWAP once those exist. Checked in `match_direction()` via a plain `minutes_since_open` int computed by `evaluate()` (`MarketClock.minutes_since_open()`), keeping the pure function itself clock-free — same discipline every pure function in this codebase already follows. Does NOT resolve the review's deeper, separately-flagged D-level question (whether an instantaneous `close` vs. `regular_open` comparison, with no memory of the day's own history, actually proves "holding" rather than "currently on the right side") — that stays open, deferred pending real outcome data, same as the review recommended.

    **3 — Volume Spike gained an absolute-volume floor (`min_absolute_volume`, v1 default 500 shares) and a body/displacement check (`min_body_ratio`, v1 default 0.3).** The review's §3 found two concrete MATCH-stage gaps: `volume_ratio` alone can't distinguish a genuine spike from a small order against a thin/illiquid baseline (nothing else — not `volume_regime_score`, a day-level per-symbol-normalized read — protects against this); and a huge-volume, razor-thin-body candle (open/close a cent apart) previously passed as directional on `close != open` alone, despite being closer to indecision than conviction. `min_body_ratio` is computed from the same OHLC already on the candle — `body_ratio = abs(close-open)/(high-low)`, safe by construction since `close != open` (checked first) guarantees `high > low` for any valid bar. Two new pure tests plus two new end-to-end tests (a thin-illiquid-baseline scenario and a wide-range-thin-body scenario) pin both fixes against the exact failure modes the review described. Deliberately NOT addressed, both flagged by the review as needing real outcome data: whether a high-volume directional candle actually means continuation vs. exhaustion/climax, and whether sizing the stop off the spike candle's own wick can produce an impractically wide risk/target.

New `test_scoring_utils.py` (11 tests) covers the shared module directly, independent of any one strategy's own tests.

    **5 — `Opportunity.expected_horizon_minutes: int | None = None` added to `base_strategy.py`.** The review's §5 found every strategy (ORB included) had an implicit expectation of how long its setup should take to play out — a fast volume spike and a session-long gap continuation are not the same kind of bet — previously lost the moment `evaluate()` returned, since nothing on the schema carried it. Optional, honest-absence default: a strategy with no informed opinion leaves it `None`. Deliberately NOT an expiry mechanism (that's `wait_expires_at`'s job, WAITING-path only) — descriptive metadata for Performance Intelligence / a future Decision Engine, nothing currently reads it to auto-expire anything. Populated by ORB (45 min default, backfilled here since the schema addition would otherwise immediately reintroduce the exact gap being fixed in the very artifact meant to fix it), Gap (60 min), and Volume Spike (15 min) — each a v1 guess, unvalidated. **Deliberately NOT populated** by First Pullback/Reversal — that's a value judgment specific to those strategies' own thesis timing, left to whichever thread owns them next; the field is available to them automatically (optional, defaults to `None`) without this change speaking for that thread.

113. **Momentum and VWAP built — the sixth and seventh v1 strategies, closing out `trading-intelligence-architecture.md` §8's full planned set. `scoring_utils.ESTABLISHED_TREND_SCORE_THRESHOLD` extracted; `reversal_strategy.py` refactored onto it. Stage 2 (decision #112/D10) now unblocked.** Design went through an external (ChatGPT) review before any code was written — same "design note first, then code" practice as First Pullback/Reversal (decisions #107/#108) — with three fork-in-the-road questions decided directly by Saqib rather than left to the review's own preference. This entry covers what was decided and built, not the review's full back-and-forth.

    **1 — Momentum's acceleration threshold: chosen from the formula's own semantics, not from empirical distribution analysis.** `market_state_engine/scoring.py`'s `acceleration_score()` was read directly (not assumed from the field's name): it is `trend_score`'s own rate of change, no volume folded in. Saqib's explicit call — skip a live-data calibration pass for now, pick a sensible v1 number from the formula alone, tune later once Stage 2 produces real distributions. `DEFAULT_ACCELERATION_SCORE_THRESHOLD = 65.0`, flagged unvalidated same as every other v1 calibration constant in this codebase. Encoded as a real hierarchy, not just a flat AND of three conditions: acceleration is the MATCH-stage PRIMARY condition, `trend_score` a deliberately LIGHTER context confirmation (`DEFAULT_TREND_CONTEXT_THRESHOLD = 55.0`, its own distinct params key `trend_context_threshold` — NOT the same question as "established trend," see item 3 below), `volume_regime_score` a participation floor (`45.0`, same value ORB already uses) — and the same hierarchy reappears in SCORE's blend weights (acceleration 0.45, trend 0.25, volume 0.30).

    **2 — VWAP made disjoint from Reversal by construction, not left to downstream arbitration.** Two candidate designs were rejected first: relationship-persistence (risked being "Momentum with a different gating field," the review's own words) and a naive two-candle cross (would false-trigger on the exact chop `LevelInteractionEngine`'s Aura band already exists to absorb). What shipped: VWAP fires on a genuine `conquered` resolution — reused verbatim from `level_touch_tracking.observe_resolution()`, zero new touch/cross-detection code — gated to `trend_score`'s NEUTRAL band only. Direction comes from the actual resolved zone (`"above"` → BUY, `"below"` → SELL), never a mirror of `trend_score` — the structural opposite of `reversal_strategy.py`'s own `match_direction()`, which bets against whichever trend is established and never looks at which way the conquest itself moved. Saqib's explicit call, made directly rather than "co-firing is fine" (the accepted answer for Momentum/ORB, decision below): VWAP and Reversal read the same underlying event and would otherwise near-duplicate each other on almost every candle with opposite direction conventions — worth a real, structural gate.

    **3 — `ESTABLISHED_TREND_SCORE_THRESHOLD` promoted to `scoring_utils.py`, `reversal_strategy.py` refactored onto it.** Was `reversal_strategy.py`'s own private `DEFAULT_TREND_SCORE_THRESHOLD = 60.0`. Now the single authoritative constant both `reversal_strategy.py` (fires when established) and `vwap_strategy.py` (fires when NOT) read, so the two conditions partition every `trend_score` reading with no gap and no overlap by construction, rather than via two independently-hardcoded 60/40 pairs that could silently drift apart the moment either `StrategyConfig` is retuned. New `scoring_utils.trend_established_side()` holds the actual `>=`/`<=` classification (`validate_mirror_threshold()` internally); `reversal_strategy.py`'s own `match_direction()` now delegates to it — behavior unchanged, six new/adjusted tests in `test_scoring_utils.py`, all 6 pre-existing `test_reversal_strategy.py` tests re-run unchanged and still pass. **Still open, not resolved by this change** (`strategy-engine-design.md` §10, new item D11): each strategy's `StrategyConfig.params` stays independently overridable per its own versioning — this guarantees the DEFAULTS match, not that they stay matched forever if either is retuned in a later config version without touching the other.

    **Momentum vs. ORB — co-firing accepted, no arbitration added, confirmed directly by Saqib and the review.** Genuinely different questions (ORB: did a specific structural morning-range level break; Momentum: is the market already moving and gaining force, independent of any level or time-of-day) — the two can and are expected to fire on the same candle; nothing in either file or `base_strategy.py` arbitrates between them, matching the review's own explicit recommendation against adding an "if ORB fires, Momentum can't" rule.

    **Momentum's invalidation: a private rolling swing lookback (`DEFAULT_LOOKBACK_BARS = 10`), not ATR, not `LevelInteractionEngine`.** The review preferred "the structure supporting the move failed" over "price moved X against me" — genuinely different claims, not a style preference. `FeatureSet` publishes no swing-high/low, so this needed new private per-symbol state, same category as ORB's opening range / Volume Spike's rolling baseline. Deliberately NOT the review's own suggested ATR-during-warm-up fallback: this file simply doesn't fire during the first `lookback_bars` minutes of each trading day per symbol, honest-absence, same precedent `volume_spike_strategy.py`'s own baseline warm-up already set — one fewer code path, and the warm-up window is small enough that "don't fire yet" is a fully acceptable v1 answer.

    **`structural_target` — schema-required placeholder, not a strong claim, for both.** The review's recommendation was "don't force a strategy-specific projection." `Opportunity.structural_target: float` is currently REQUIRED (not `Optional`) on `base_strategy.py` — changing that schema would be a bigger, cross-cutting change touching all 5 other built strategies, out of scope here. Reconciled by using the same mechanical R-multiple (`close ± target_r_multiple * risk`, default 2.0) every other v1 strategy already computes — a schema-completeness value, not new invented target logic.

    **VWAP's SCORE uses `distance_pct`, not `touch_count_today`.** `get_snapshot()`'s `distance_pct` field was checked directly against `level_interaction_engine.py`'s source — computed from `_latest_close`/`_latest_level_value` (candle-derived, not `seconds_in_zone`'s wall-clock `datetime.now()`), so it's backtest-safe to read. `touch_count_today` is logged in `evidence.conditions` for future calibration but NOT weighted: unlike Reversal (more prior touches before a break is straightforwardly stronger evidence), the sign of that relationship for a VWAP conquest isn't obvious — could mean a well-tested level finally giving way, or an already-choppy, low-conviction session — and guessing at a direction wasn't worth doing before real outcome data exists to check it against.

    **VWAP's cadence: fires on a genuine control TRANSITION, via `_VWAPState.last_fired_zone`, not every conquered event.** Checked directly against `level_touch_tracking.py`'s own classification rule (`"rejected" if current_zone == entered_from else "conquered"`): two CONSECUTIVE conquered resolutions in the engine's own unbroken stream always alternate zones by construction, so raw same-zone-twice-in-a-row cannot happen there. The real, reachable repeat case is more specific: VWAP is a PARTIAL observer of that stream (it skips every conquest that happens while trend is established, per item 2 above), so the zone can drift back to a value VWAP already fired for while VWAP wasn't watching. `last_fired_zone` catches exactly that case; proven both ways in `test_vwap_strategy.py` — a same-zone repeat after an established-trend window is suppressed, and a genuinely new zone still fires immediately afterward.
